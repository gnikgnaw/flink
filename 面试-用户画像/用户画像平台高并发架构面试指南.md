# 用户画像平台高并发架构面试指南

> 场景：日均QPS 2000万，后端 SpringBoot + Redis + MySQL

---

## 一、整体架构设计

### 1.1 分层架构

```
Client → CDN/Nginx → Gateway(限流/熔断) → SpringBoot服务集群
                                              ├── L1: Caffeine本地缓存 (热点画像)
                                              ├── L2: Redis Cluster (全量画像缓存)
                                              └── L3: MySQL (分库分表持久化)
```

### 1.2 QPS拆解分析

| 层级 | 承担QPS占比 | 说明 |
|------|-----------|------|
| 本地缓存(L1) | ~70% (1400万) | 热点用户画像命中本地缓存，零网络开销 |
| Redis(L2) | ~25% (500万) | Redis Cluster分片，单片~50万QPS |
| MySQL(L3) | ~5% (100万) | 分库分表后，单库承担~10万读QPS |

## 二、高并发解决方案

### 2.1 多级缓存策略

#### L1：本地缓存（Caffeine）

```java
@Configuration
public class CacheConfig {

    @Bean
    public Cache<Long, UserProfile> localCache() {
        return Caffeine.newBuilder()
                .maximumSize(100_000)           // 10万热点画像
                .expireAfterWrite(30, TimeUnit.SECONDS) // 短过期，降低不一致窗口
                .refreshAfterWrite(10, TimeUnit.SECONDS) // 异步刷新，不阻塞读
                .build(userId -> redisTemplate.opsForValue()
                        .get(profileKey(userId)));
    }
}
```

**面试要点：**
- Caffeine的`refreshAfterWrite`实现**异步刷新**，过期前后台加载新值，读请求不阻塞
- `maximumSize`采用W-TinyLFU淘汰算法，比LRU命中率高~30%
- 本地缓存过期时间必须短（10-30s），否则节点间数据不一致严重

#### L2：Redis Cluster

```java
@Service
public class ProfileCacheService {

    // 画像缓存 Key 设计：profile:{userId} → Hash结构
    // Hash字段：age, gender, tags, interests, lastUpdate...

    public UserProfile getProfile(Long userId) {
        // 1. L1查
        UserProfile profile = localCache.getIfPresent(userId);
        if (profile != null) return profile;

        // 2. L2查
        Map<Object, Object> hash = redisTemplate.opsForHash()
                .entries("profile:" + userId);
        if (!hash.isEmpty()) {
            profile = convert(hash);
            localCache.put(userId, profile);
            return profile;
        }

        // 3. L3查 + 回填
        profile = profileMapper.selectById(userId);
        if (profile != null) {
            redisTemplate.opsForHash().putAll("profile:" + userId, toMap(profile));
            redisTemplate.expire("profile:" + userId,
                    randomTtl(3600, 7200), TimeUnit.SECONDS); // 随机TTL防雪崩
            localCache.put(userId, profile);
        }
        return profile;
    }

    // 随机TTL：基础时间 + 随机偏移，防止大量Key同时过期
    private long randomTtl(int base, int max) {
        return base + ThreadLocalRandom.current().nextInt(max - base);
    }
}
```

**面试要点：**
- Redis Cluster 10个分片，每片主从架构，理论承载 50万*10 = 500万 QPS
- Hash结构存画像，支持部分字段读取，减少网络传输
- 随机TTL（3600-7200s）防止缓存雪崩

### 2.2 热点Key处理

```java
@Component
public class HotKeyProtector {

    // 热点探测：基于滑动窗口计数
    private final Cache<Long, LongAdder> accessCounter = Caffeine.newBuilder()
            .maximumSize(10_000)
            .expireAfterWrite(1, TimeUnit.MINUTES)
            .build(k -> new LongAdder());

    public boolean isHotKey(Long userId) {
        LongAdder counter = accessCounter.get(userId, k -> new LongAdder());
        counter.increment();
        return counter.sum() > 1000; // 1分钟内访问超1000次视为热点
    }

    // 热点Key本地缓存加长 + 多副本打散
    public UserProfile getWithHotKeyProtection(Long userId) {
        if (isHotKey(userId)) {
            // 热点Key：本地缓存TTL加长，减少穿透Redis
            return localCache.get(userId, id -> loadFromRedis(id));
        }
        return normalGet(userId);
    }
}
```

**面试追问：如果某个明星用户画像被疯狂访问怎么办？**
1. **本地缓存兜底**：热点Key直接本地缓存，不走Redis
2. **Redis多副本**：`profile:{userId}:{0-9}` 随机读不同副本，分散单Key压力
3. **限流降级**：单用户画像查询限流，超限返回缓存的旧版本

### 2.3 缓存穿透防护

```java
// 方案1：布隆过滤器（Redisson实现）
@Bean
public RBloomFilter<Long> userBloomFilter(RedissonClient redisson) {
    RBloomFilter<Long> filter = redisson.getBloomFilter("user:bloom");
    filter.tryInit(100_000_000L, 0.01); // 1亿用户，1%误判率
    return filter;
}

// 方案2：空值缓存
public UserProfile getProfileSafe(Long userId) {
    // 布隆过滤器前置判断
    if (!userBloomFilter.contains(userId)) {
        return null; // 用户一定不存在
    }

    UserProfile profile = getProfile(userId);
    if (profile == null) {
        // 缓存空值，短TTL
        redisTemplate.opsForValue().set("profile:null:" + userId, "NIL",
                60, TimeUnit.SECONDS);
    }
    return profile;
}
```

## 三、缓存一致性解决方案

### 3.1 核心问题

用户画像更新场景：
- **实时更新**：用户修改个人信息（低频，强一致性要求）
- **异步更新**：行为标签计算、画像聚合（高频，最终一致性即可）

### 3.2 方案对比

| 方案 | 一致性 | 复杂度 | 适用场景 |
|------|--------|--------|---------|
| Cache Aside（旁路缓存） | 最终一致 | 低 | 默认方案 |
| 延迟双删 | 较强一致 | 中 | 写后立即读场景 |
| Binlog监听（Canal） | 最终一致 | 高 | 异步画像更新 |
| 写锁串行化 | 强一致 | 高 | 不推荐，严重影响性能 |

### 3.3 推荐方案：Cache Aside + 延迟双删 + Canal兜底

```java
@Service
public class ProfileUpdateService {

    /**
     * 用户主动修改画像 —— 延迟双删策略
     */
    @Transactional
    public void updateProfile(Long userId, UserProfile profile) {
        // 第1删：先删缓存
        evictCache(userId);

        // 更新DB
        profileMapper.updateById(profile);

        // 第2删：延迟删缓存（覆盖并发读回填的旧值）
        CompletableFuture.runAsync(() -> {
            try {
                Thread.sleep(500); // 延迟500ms，等并发读回填完成
            } catch (InterruptedException ignored) {}
            evictCache(userId);
        }, asyncExecutor);
    }

    private void evictCache(Long userId) {
        // 删Redis
        redisTemplate.delete("profile:" + userId);
        // 发消息通知其他节点删本地缓存
        redisTemplate.convertAndSend("cache:evict", userId.toString());
    }
}
```

#### 为什么先删缓存再更新DB？

**面试经典问题：先更新DB还是先删缓存？**

```
方案A：先更新DB，后删缓存（推荐）
  问题场景：删缓存失败 → 缓存中是旧值
  解决：重试 + Canal兜底

方案B：先删缓存，后更新DB
  问题场景：删缓存后、更新DB前，并发读将旧值回填缓存
  解决：延迟双删

实际生产中两种都用：
  主流程用方案A（先更新DB后删缓存）+ 消息重试
  Canal作为兜底，监听Binlog异步清理
```

### 3.4 Canal Binlog监听兜底

```java
/**
 * 监听MySQL Binlog，异步清理缓存
 * 解决：删缓存失败、延迟双删遗漏等边界case
 */
@Component
@CanalEventListener
public class ProfileBinlogListener {

    @ListenPoint(table = "user_profile")
    public void onProfileChange(CanalEntry.EventType eventType,
                                 CanalEntry.RowData rowData) {
        Long userId = extractUserId(rowData);

        // 删Redis缓存
        redisTemplate.delete("profile:" + userId);

        // 通知所有节点删本地缓存（Redis Pub/Sub）
        redisTemplate.convertAndSend("cache:evict", userId.toString());

        log.info("Binlog触发缓存清理: userId={}", userId);
    }
}
```

### 3.5 本地缓存一致性：Redis Pub/Sub

```java
@Component
public class LocalCacheInvalidator implements MessageListener {

    @Autowired
    private Cache<Long, UserProfile> localCache;

    @Override
    public void onMessage(Message message, byte[] pattern) {
        Long userId = Long.parseLong(new String(message.getBody()));
        localCache.invalidate(userId);
        log.debug("本地缓存失效: userId={}", userId);
    }

    @Bean
    public RedisMessageListenerContainer container(
            RedisConnectionFactory factory) {
        RedisMessageListenerContainer container = new RedisMessageListenerContainer();
        container.setConnectionFactory(factory);
        container.addMessageListener(this,
                new ChannelTopic("cache:evict"));
        return container;
    }
}
```

## 五、限流与降级

### 5.1 多层限流

```java
@Configuration
public class RateLimitConfig {

    // 网关层：Sentinel限流
    @Bean
    public void initSentinel() {
        FlowRule rule = new FlowRule();
        rule.setResource("getProfile");
        rule.setGrade(RuleConstant.FLOW_GRADE_QPS);
        rule.setCount(200_000); // 单机20万QPS上限
        rule.setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_WARM_UP);
        rule.setWarmUpPeriodSec(10);
        FlowRuleManager.loadRules(Collections.singletonList(rule));
    }
}

@RestController
public class ProfileController {

    @SentinelResource(value = "getProfile",
            fallback = "getProfileFallback")
    @GetMapping("/api/profile/{userId}")
    public UserProfile getProfile(@PathVariable Long userId) {
        return profileService.getProfile(userId);
    }

    // 降级兜底：返回基础画像
    public UserProfile getProfileFallback(Long userId, Throwable t) {
        return UserProfile.basic(userId); // 只返回基础信息
    }
}
```

### 5.2 降级策略分级

```
P0（核心）：用户基础画像（性别、年龄） → 永不降级，多级缓存保障
P1（重要）：用户标签、兴趣偏好       → 高峰期可返回缓存旧版本
P2（可选）：实时行为序列、临时标签    → 可直接降级不返回
```

## 六、面试高频追问

### Q1：缓存和数据库双写不一致怎么办？

**答：** 采用三层保障：
1. **主路径**：先更新DB，后删缓存（Cache Aside Pattern）
2. **补偿机制**：删缓存失败时发MQ重试，最多重试3次
3. **兜底方案**：Canal监听Binlog，异步清理缓存，确保最终一致

不一致窗口：正常情况<1s，极端情况<缓存TTL（30s本地/1h Redis）

### Q2：缓存雪崩怎么防？

**答：**
1. **随机TTL**：基础过期时间+随机偏移（如1h-2h随机）
2. **多级缓存**：Redis挂了还有本地缓存兜底
3. **限流熔断**：Sentinel限制穿透到DB的QPS
4. **预热**：大促前提前加载热点画像到缓存

### Q3：缓存击穿（热点Key过期瞬间大量请求穿透）怎么办？

**答：**
```java
// 方案：分布式锁 + 双重检查
public UserProfile getWithLock(Long userId) {
    UserProfile profile = getFromCache(userId);
    if (profile != null) return profile;

    String lockKey = "lock:profile:" + userId;
    boolean locked = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, "1", 5, TimeUnit.SECONDS);
    if (locked) {
        try {
            // 双重检查
            profile = getFromCache(userId);
            if (profile != null) return profile;

            profile = loadFromDB(userId);
            writeToCache(userId, profile);
            return profile;
        } finally {
            redisTemplate.delete(lockKey);
        }
    } else {
        // 未获锁：短暂等待后重试
        Thread.sleep(50);
        return getFromCache(userId);
    }
}
```

### Q4：如何保证Redis和MySQL的最终一致性？

**答：** 关键指标是**不一致窗口时间**，而非绝对一致：

| 场景 | 不一致窗口 | 方案 |
|------|-----------|------|
| 用户改资料 | <500ms | 延迟双删 |
| 标签计算更新 | <5s | Canal Binlog |
| 批量画像刷新 | <30s | MQ异步+本地缓存短TTL |

### Q5：2000万QPS，需要多少台机器？

**答：** 粗略估算：
- **应用服务器**：单机承载20万QPS（本地缓存命中为主），需要 ~100台
- **Redis Cluster**：10主10从，单片50万QPS，总计500万QPS
- **MySQL**：8主24从（3倍读扩展），承载穿透流量~100万QPS
- **实际还需考虑**：峰值系数（通常3-5倍均值）、容灾冗余（N+1）

### Q6：画像数据如何分层存储？

**答：**
```
实时层（Redis）：高频访问的画像标签、用户基础信息
  → Hash结构，TTL 1-2h

近线层（HBase/ES）：用户行为序列、历史标签
  → 按时间分区，保留近30天

离线层（Hive/HDFS）：全量画像快照、历史归档
  → 按天分区，用于离线分析和模型训练

Flink实时计算：消费Kafka行为日志 → 实时更新Redis画像标签
```

## 七、架构总结图

```
                    ┌─────────────┐
                    │   Nginx/LB  │  限流 + 负载均衡
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │   Gateway   │  Sentinel限流/熔断
                    └──────┬──────┘
                           │
              ┌────────────▼────────────┐
              │   SpringBoot 集群(100台) │
              │  ┌─────────────────┐    │
              │  │ L1: Caffeine    │    │ 命中率~70%
              │  │ 10万热点Key/节点 │    │
              │  └────────┬────────┘    │
              └───────────┼─────────────┘
                          │ 未命中
              ┌───────────▼─────────────┐
              │  L2: Redis Cluster      │ 命中率~95%（含L1）
              │  10主10从，500万QPS      │
              └───────────┬─────────────┘
                          │ 未命中
              ┌───────────▼─────────────┐
              │  L3: MySQL 分库分表      │
              │  8库64表，读写分离       │
              └───────────┬─────────────┘
                          │
              ┌───────────▼─────────────┐
              │  Canal Binlog → 缓存清理 │ 一致性兜底
              └─────────────────────────┘
```

**核心原则：** 用空间换时间，用最终一致换高可用，分层治理不同一致性要求的数据。
