# 设计模式知识迁移：数据集成平台 → 用户画像平台

> **核心面试策略**：不直接背画像平台的设计模式案例，而是从数据集成平台的真实实践出发，展现"理解问题本质后迁移模式"的能力。面试官更看重的是你对模式的理解深度，而非你是否在画像项目中用过。

---

## 一、核心论点：两个平台面临相同的底层问题

面试时先抛出这个判断，建立高度：

> "数据集成平台和用户画像平台在架构层面面临的核心问题高度一致——**多源异构数据的统一抽象与可扩展处理**。集成平台要对接几十种数据源做数据搬运，画像平台要对接多种存储后端做标签查询和计算。设计模式的选择不是跟着项目走的，是跟着问题走的。"

| 共性问题 | 数据集成 | 用户画像 |
|---------|---------|---------|
| 多源异构 | MySQL/Oracle/Kafka/FTP/HDFS 等数据源 | HBase/Redis/ClickHouse 等标签存储 |
| 流程编排 | ETL：抽取→转换→加载 | 标签计算：加载→清洗→计算→写入 |
| 状态通知 | 任务状态变更通知监控/告警 | 标签变更通知缓存/索引刷新 |
| 动态扩展 | 新数据源通过插件接入 | 新标签类型通过配置接入 |
| 多级校验 | 任务提交前校验链 | 圈选条件校验链 |
| 功能叠加 | 传输通道上叠加压缩/加密/限速 | 查询服务上叠加缓存/限流/监控 |

## 二、六大设计模式逐一对照

### 2.1 策略模式 — 解决"同一操作、不同实现"

#### 数据集成中的实践（你的真实经验）

不同数据源的读写行为差异巨大，但上层调度框架需要统一调用接口：

```java
// 策略接口：统一数据读取抽象
public interface DataSourceReader {
    /**
     * 从数据源读取一批数据
     * @param config 数据源配置（连接信息、表名、查询条件等）
     * @param channel 数据传输通道，读取到的数据写入 channel
     */
    void read(DataSourceConfig config, DataChannel channel);

    /** 声明支持的数据源类型 */
    boolean supports(DataSourceType type);
}

// MySQL 读取策略：基于 JDBC 分页查询
public class MysqlReader implements DataSourceReader {
    @Override
    public void read(DataSourceConfig config, DataChannel channel) {
        // 通过 JDBC 执行 SELECT，按主键范围分片读取
        // 使用流式读取（fetchSize = Integer.MIN_VALUE）避免全量加载到内存
    }
}

// Kafka 读取策略：消费消息
public class KafkaReader implements DataSourceReader {
    @Override
    public void read(DataSourceConfig config, DataChannel channel) {
        // 订阅 Topic，拉取消息，按 offset 范围读取
    }
}

// FTP 读取策略：文件下载 + 解析
public class FtpReader implements DataSourceReader {
    @Override
    public void read(DataSourceConfig config, DataChannel channel) {
        // 连接 FTP 服务器，下载文件，按行解析为记录
    }
}
```

#### 画像平台中的对应场景

画像平台的**标签存储层**采用了混合存储架构：不同类型的标签根据查询模式存储在不同的存储引擎中。这就需要策略模式来统一查询接口。

- **HBase**：存储用户标签明细宽表，按 rowkey（userId）查询单用户全量标签。HBase 适合存储几百列的宽表，按行键随机查询性能优秀（毫秒级）
- **Redis**：存储实时热标签（如"最近一次活跃时间"），提供微秒级响应。通常用 Hash 结构存储，`HSET profile:{userId} age 25 city beijing`
- **ClickHouse**：存储分析型标签的宽表，用于人群圈选（如"消费金额>500 且 城市=北京"的用户集合）。ClickHouse 的列式存储和向量化执行特别适合这种多条件过滤场景

```java
// 画像平台中的策略接口
public interface TagQueryStrategy {
    Map<String, Object> query(String userId, List<String> tagNames);
    boolean supports(TagStorageType type);
}
```

**面试话术**：

> "在数据集成平台中，策略模式的应用范围比画像更广——画像只需要区分 HBase、Redis、ClickHouse 三种存储后端的查询策略，而数据集成平台需要统一抽象几十种数据源的读写行为。我们定义了 `DataSourceReader` 和 `DataSourceWriter` 接口，每种数据源实现自己的连接、读取、写入策略，并通过 SPI 机制实现动态发现和加载。这个思路迁移到画像的 `TagQueryStrategy` 完全适用，核心都是**用接口屏蔽实现差异，用 supports() 做策略路由**。"

### 2.2 工厂模式 — 解决"运行时动态创建实例"

#### 数据集成中的实践

用户配置一个同步任务（如 MySQL→Hive），系统需要根据配置动态创建对应的 Reader 和 Writer 实例：

```java
public class ConnectorFactory {
    private final Map<String, Function<ConnectorConfig, DataConnector>> creators = new HashMap<>();

    @PostConstruct
    public void init() {
        creators.put("mysql", config -> new MysqlConnector(config));
        creators.put("oracle", config -> new OracleConnector(config));
        creators.put("kafka", config -> new KafkaConnector(config));
        creators.put("hdfs", config -> new HdfsConnector(config));
        creators.put("ftp", config -> new FtpConnector(config));
        creators.put("hive", config -> new HiveConnector(config));
        // 支持通过 SPI 动态注册第三方插件
        ServiceLoader.load(ConnectorPlugin.class).forEach(
            plugin -> creators.put(plugin.type(), plugin::createConnector)
        );
    }

    public DataConnector create(String type, ConnectorConfig config) {
        Function<ConnectorConfig, DataConnector> creator = creators.get(type.toLowerCase());
        if (creator == null) {
            throw new IllegalArgumentException("不支持的数据源类型: " + type);
        }
        DataConnector connector = creator.apply(config);
        connector.init(); // 初始化连接池等资源
        return connector;
    }
}
```

#### 画像平台中的对应场景

画像平台的 `TagSourceFactory` 根据标签元数据中配置的 `storage_type`（HBase / Redis / ClickHouse / Elasticsearch）创建对应的查询客户端。逻辑完全一致：**根据类型字符串 + 配置参数，创建具体实例并初始化**。

**面试话术**：

> "工厂模式在两个平台中的应用模式完全一样——都是根据配置中的 type 字段和连接参数动态创建实例。数据集成平台的 `ConnectorFactory` 还额外支持了 SPI 机制，允许第三方以插件形式注册新的数据源类型，不需要修改核心代码。如果画像平台未来要接入新的标签存储引擎（比如 TiKV 或 StarRocks），同样可以用 SPI + 工厂的组合实现零侵入扩展。"

### 2.3 模板方法模式 — 解决"流程固定、步骤可变"

**这是数据集成平台的灵魂模式，也是面试中最值得展开的。**

#### 数据集成中的实践

每个数据同步任务都遵循固定的生命周期流程，但具体步骤因数据源不同而异：

```java
public abstract class AbstractDataSyncTask<T> {

    // 模板方法：定义同步任务的执行骨架
    public final SyncResult execute(SyncTaskContext context) {
        // 1. 前置校验
        preCheck(context);

        // 2. 初始化连接
        initConnection(context);

        try {
            // 3. 数据切分（决定并行度）
            List<DataSlice> slices = splitChannel(context);

            // 4. 并行执行：读取 → 转换 → 写入
            List<Future<SliceResult>> futures = slices.stream()
                .map(slice -> executor.submit(() -> {
                    T batch;
                    while ((batch = readBatch(slice)) != null) {
                        T transformed = transform(batch, context);
                        writeBatch(transformed, context);
                    }
                    return SliceResult.success(slice);
                }))
                .collect(Collectors.toList());

            // 5. 汇总结果
            return aggregateResults(futures);
        } finally {
            // 6. 资源清理
            cleanup(context);
        }
    }

    // 子类必须实现的抽象方法
    protected abstract List<DataSlice> splitChannel(SyncTaskContext context);
    protected abstract T readBatch(DataSlice slice);
    protected abstract T transform(T data, SyncTaskContext context);
    protected abstract void writeBatch(T data, SyncTaskContext context);

    // 钩子方法：子类可选覆盖
    protected void preCheck(SyncTaskContext context) { /* 默认不校验 */ }
    protected void cleanup(SyncTaskContext context) { /* 默认关闭连接 */ }
}
```

#### 画像平台中的对应场景

画像平台的**标签计算流水线** `TagComputePipeline` 与此高度对应：

| 数据集成流水线步骤 | 画像计算流水线步骤 | 共同抽象 |
|-----------------|-----------------|---------|
| `preCheck()` — 校验任务参数 | `validate()` — 校验计算上下文 | 前置校验 |
| `splitChannel()` — 数据切分 | `loadData()` — 数据加载 | 数据获取 |
| `readBatch()` → `transform()` | `cleanData()` → `doCompute()` | 数据处理 |
| `writeBatch()` — 写入目标端 | `writeResult()` — 写入标签存储 | 结果输出 |
| `cleanup()` — 资源清理 | `validateResult()` — 结果校验 | 收尾动作 |

画像平台中不同标签类型的计算逻辑差异很大：消费能力标签需要聚合订单数据，活跃度标签需要统计行为事件，兴趣偏好标签可能需要调用算法模型。但它们的计算流程骨架（加载→清洗→计算→校验→写入）是固定的。

**面试话术**：

> "模板方法模式是数据集成平台的骨架级设计，每个同步任务的生命周期'校验→连接→切分→并行读写→汇总→清理'是固定的，而具体的读写实现因数据源不同而异。这与画像平台的标签计算流水线完全同构——'校验→加载→清洗→计算→写入'的骨架固定，不同标签类型实现各自的计算逻辑。它们的设计理念和 Flink 的 `AbstractStreamOperator` 也是一致的——框架定义生命周期骨架，开发者只需实现具体的处理逻辑。"

### 2.4 责任链模式 — 解决"多步骤串行校验"

#### 数据集成中的实践

数据同步任务提交前需要经过一系列校验，任何一环失败都要拦截提交：

```java
public interface TaskValidator {
    void validate(SyncTaskConfig config) throws ValidationException;
    int getOrder(); // 执行顺序
}

// 校验链（按 order 排序后依次执行）：
//
// 1. ParamValidator        — 必填参数、格式校验
// 2. PermissionValidator   — 用户是否有权操作该数据源
// 3. SourceConnValidator   — 源端数据源是否可连通
// 4. SinkConnValidator     — 目标端数据源是否可连通
// 5. SchemaValidator       — 源端和目标端字段映射是否兼容
//                            （如 VARCHAR→INT 是否有类型转换风险）
// 6. QuotaValidator        — 用户的并发任务数/流量配额是否已用尽
```

#### 画像平台中的对应场景

画像平台的**圈选条件校验**是责任链的典型应用场景。当运营人员在前端配置圈选条件（如"北京 + 近30天消费>500 + 非会员"）提交时，需要逐步校验：

1. **参数校验**：圈选条件是否为空、条件数是否超限（如不超过 20 个）
2. **权限校验**：当前用户是否有权限访问这些标签（不同业务线的标签有隔离）
3. **标签存在性校验**：条件中引用的标签是否存在、是否已下线

这与数据集成的任务校验链在模式上完全一致，区别只在于校验的具体内容不同。数据集成的校验链更长，因为要额外处理源端/目标端连通性和 Schema 兼容性。

**面试话术**：

> "数据集成平台的任务提交校验链比画像更复杂——除了参数和权限校验外，还需要验证源端/目标端的连通性（执行 test connection）、Schema 映射兼容性（如源端 BIGINT 映射到目标端 INT 是否有溢出风险）、以及资源配额检查。这些校验器通过 Spring 容器自动发现、按 order 排序组成链。迁移到画像场景，圈选条件的校验链完全可以复用这个模式，只是校验内容换成了标签存在性、权限和条件数量。"

### 2.5 观察者模式 — 解决"状态变更的多方异步通知"

#### 数据集成中的实践

同步任务的状态变更（启动/运行中/成功/失败/超时）需要通知多个下游系统：

```java
// 事件定义
public class TaskStatusChangedEvent {
    private final String taskId;
    private final TaskStatus oldStatus;
    private final TaskStatus newStatus;   // STARTED, RUNNING, SUCCESS, FAILED, TIMEOUT
    private final long timestamp;
    private final String errorMessage;    // 失败时的错误信息
}

// 监听器1：监控指标上报（记录任务成功率、耗时等）
// 监听器2：告警通知（任务失败时发送钉钉/邮件通知责任人）
// 监听器3：审计日志（记录任务执行历史，用于问题追溯）
// 监听器4：依赖触发（任务成功后触发下游依赖任务启动）
```

#### 画像平台中的对应场景

画像平台中**标签元数据变更**（创建、更新、删除标签定义）需要通知多方：

- **本地缓存刷新**：标签元数据通常在应用层有 Caffeine 本地缓存，变更后需要失效
- **集群节点同步**：通过 Redis Pub/Sub 通知集群中其他节点刷新缓存
- **搜索索引更新**：标签管理后台支持搜索标签，标签变更后需要同步更新 Elasticsearch 索引

两者都使用 Spring 的 `ApplicationEventPublisher` + `@EventListener` + `@Async` 实现异步解耦，核心理念一致：**发布者不关心谁在监听，监听者不阻塞主流程**。

**面试话术**：

> "数据集成平台中任务状态变更要通知监控、告警、审计日志、下游依赖四个系统，用的是 Spring Event 机制异步发布。画像平台的标签变更通知也是同一个模式，只是观察者从'监控/告警/审计/依赖触发'变成了'缓存刷新/集群同步/索引更新'。观察者模式的价值在于**发布者和订阅者的完全解耦**——新增一个监听器不需要修改任何已有代码。"

### 2.6 装饰器模式 — 解决"功能的正交组合叠加"

#### 数据集成中的实践

数据传输通道上可以按需叠加多种能力，每种能力独立封装、自由组合：

```java
// 基础接口
public interface DataChannel {
    void write(Record record);
    Record read();
}

// 基础实现：内存队列传输
public class MemoryChannel implements DataChannel { ... }

// 装饰器：数据压缩（Snappy/LZ4，减少网络传输量）
public class CompressedChannel implements DataChannel {
    private final DataChannel delegate;
    @Override
    public void write(Record record) {
        delegate.write(compress(record));
    }
}

// 装饰器：数据加密（AES，敏感数据传输场景）
public class EncryptedChannel implements DataChannel { ... }

// 装饰器：传输限速（令牌桶，避免打满源端/目标端带宽）
public class ThrottledChannel implements DataChannel { ... }

// 装饰器：传输监控（统计吞吐量、延迟、错误率）
public class MonitoredChannel implements DataChannel { ... }

// 运行时根据用户配置动态组装
DataChannel channel = new MonitoredChannel(
    new ThrottledChannel(
        new CompressedChannel(
            new MemoryChannel()),
        rateLimiter),
    meterRegistry);
```

#### 画像平台中的对应场景

画像平台在**标签查询服务**上叠加装饰器：

- **CachedTagQueryService**（缓存层）：先查 Caffeine 本地缓存或 Redis，命中则直接返回，未命中则穿透到底层存储
- **RateLimitedTagQueryService**（限流层）：每个接入方（appKey）有独立的 QPS 配额，使用令牌桶算法控制
- **MonitoredTagQueryService**（监控层）：记录每次查询的耗时、成功/失败状态，上报到 Prometheus

组装顺序：基础查询 → 缓存 → 限流 → 监控（从内到外）。

**面试话术**：

> "装饰器模式在两个平台中的应用完全对称。数据集成在传输通道上叠加压缩/加密/限速/监控，画像在查询服务上叠加缓存/限流/监控。核心思想一样——**每个装饰器只关注一个横切关注点，通过组合而非继承来扩展功能**。用户通过配置文件决定启用哪些能力，系统在运行时动态组装装饰器链。相比用继承实现（CachedRateLimitedMonitoredTagQueryService），装饰器的优势是各能力正交、可独立开关。"

## 三、面试回答模板

当面试官问"设计模式在你项目中的应用"时，推荐的回答结构：

### 第一层：抛出共性问题（10秒）

> "我做的是数据集成平台，和画像平台面临的核心问题高度一致——多源异构数据的统一抽象与可扩展处理。所以在设计模式的选择上，两个平台的思路是相通的。"

### 第二层：挑 2-3 个模式展开（各30秒）

**推荐优先展开的模式（按面试区分度排序）**：

1. **模板方法** — 最能体现架构思维，流程编排的核心模式
2. **策略模式** — 最基础也最实用，多源异构必用
3. **装饰器模式** — 最能体现设计功底，理解组合优于继承

### 第三层：展现迁移能力（10秒）

> "如果让我来做画像平台，这些模式可以直接复用，因为底层抽象问题是一致的——策略解决多实现路由，模板方法解决流程编排，装饰器解决功能叠加。模式是跟着问题走的，不是跟着项目走的。"

## 四、常见追问与应对

### Q1："你在数据集成中用策略模式，和简单的 if-else 有什么区别？"

> "三个数据源用 if-else 没问题，但我们平台对接了几十种数据源，而且还要支持第三方插件扩展。if-else 意味着每新增一种数据源都要修改核心代码，违反开闭原则。策略模式 + SPI 的组合让新数据源通过**加 jar 包**而非**改代码**来接入，核心流程零修改。"

### Q2："模板方法和策略模式都是在做'可替换'，有什么区别？"

> "**策略模式替换的是一个算法/行为**（比如用 MySQL 方式读还是 Kafka 方式读），替换发生在**同一步骤**内。**模板方法替换的是流程中的多个步骤**（preCheck、splitChannel、readBatch、writeBatch 都可以被子类覆盖），它管的是**步骤之间的编排关系**。在数据集成中，模板方法定义了'读→转→写'的骨架，策略模式决定了'读'这一步具体怎么读。两者经常配合使用。"

### Q3："装饰器和 AOP 有什么区别？你为什么不用 AOP？"

> "AOP（如 Spring @Aspect）适合做**统一横切**——比如所有 Service 方法都加日志、都加耗时监控。装饰器适合做**按需组合**——比如有些查询要缓存但不限流，有些要限流但不缓存。AOP 是全局生效的，装饰器是可以按实例单独组装的。在数据集成的传输通道场景中，不同的同步任务需要不同的能力组合（有些要压缩，有些要加密），所以用装饰器更合适。"

### Q4："责任链模式中，某个校验器很慢怎么办？"

> "两个策略：一是把耗时的校验器排在链的后面（比如连通性测试排在参数校验之后），让前面的快速校验先拦截明显错误的请求。二是对耗时校验设置超时（比如 test connection 超时 3 秒），超时即视为校验失败。数据集成平台中源端/目标端连通性测试就是最慢的环节，我们把它排在参数校验和权限校验之后，大约 70% 的无效请求在前两步就被拦截了。"

### Q5："画像平台的 RoaringBitmap 你了解吗？"

> "了解原理。RoaringBitmap 是高效的压缩位图数据结构，画像平台用它来表示人群包——每个用户 ID 对应一个 bit 位。人群圈选的交集（AND）、并集（OR）、差集（ANDNOT）操作本质上就是 Bitmap 的位运算，时间复杂度和数据压缩率都远优于传统的 ID 列表。这在数据集成平台中也有应用场景——比如增量同步时用 Bitmap 标记已同步的记录 ID，快速判断哪些记录需要同步。"

## 五、关键术语速查（避免面试说错）

| 画像术语 | 含义 | 技术实现 |
|---------|------|---------|
| 标签（Tag） | 描述用户某个维度特征的 KV 对 | 如 `age=25`, `city=beijing` |
| 标签宽表 | 一个用户一行，每个标签一列 | HBase（rowkey=userId）或 ClickHouse |
| 人群包 | 符合某组条件的用户 ID 集合 | RoaringBitmap 或 ID 列表文件 |
| 人群圈选 | 根据标签条件筛选用户 | ClickHouse SQL 或 Bitmap 交并差运算 |
| 标签元数据 | 标签的定义信息（名称、类型、存储位置、负责人） | MySQL 存储，有管理后台 |
| 标签血缘 | 标签依赖的上游数据源和计算逻辑 | DAG 管理 |
| 事实标签 | 直接从原始数据提取，无需计算 | 如性别、注册时间 |
| 统计标签 | 基于行为数据聚合计算 | 如最近7天订单数 |
| 规则标签 | 对统计结果按业务规则分层 | 如消费能力=高/中/低 |
| 算法标签 | 由机器学习模型预测产出 | 如购买意向分 |
| T+1 | 离线批量计算，次日产出 | Spark/Hive 定时任务 |
| 实时标签 | 事件驱动实时更新 | Flink 流处理 |
