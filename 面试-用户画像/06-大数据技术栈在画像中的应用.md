## 2. Flink 在画像中的应用

### 2.1 实时标签计算

```java
/**
 * Flink 实时标签计算作业
 * 消费用户行为事件，实时更新用户标签
 */
public class RealtimeTagJob {

    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();

        // Checkpoint 配置：保证 Exactly-Once
        env.enableCheckpointing(60_000);
        env.getCheckpointConfig().setCheckpointingMode(CheckpointingMode.EXACTLY_ONCE);
        env.setStateBackend(new EmbeddedRocksDBStateBackend());
        env.getCheckpointConfig().setCheckpointStorage("hdfs://namenode/flink/checkpoints");

        // 消费 Kafka 行为日志
        KafkaSource<UserEvent> source = KafkaSource.<UserEvent>builder()
            .setBootstrapServers("kafka:9092")
            .setTopics("user_events")
            .setGroupId("realtime-tag-job")
            .setValueOnlyDeserializer(new UserEventDeserializer())
            .build();

        DataStream<UserEvent> events = env.fromSource(
            source, WatermarkStrategy.forBoundedOutOfOrderness(Duration.ofSeconds(5)),
            "user-events");

        // 按用户分组，计算实时标签
        events
            .keyBy(UserEvent::getUserId)
            .process(new RealtimeTagProcessor())
            .addSink(buildMultiSink());  // 同时写 Redis + HBase + Kafka

        env.execute("Realtime Tag Computation");
    }
}
```

### 2.2 实时标签处理函数

```java
/**
 * 使用 KeyedProcessFunction 实现有状态的实时标签计算
 */
public class RealtimeTagProcessor
        extends KeyedProcessFunction<String, UserEvent, TagUpdate> {

    // 状态：记录用户近1小时的行为计数
    private MapState<String, Integer> hourlyActionCount;
    // 状态：记录用户最近一次访问时间
    private ValueState<Long> lastVisitTime;
    // 状态：记录用户浏览品类计数（用于偏好计算）
    private MapState<String, Integer> categoryViewCount;

    @Override
    public void open(Configuration parameters) {
        hourlyActionCount = getRuntimeContext().getMapState(
            new MapStateDescriptor<>("hourly-count", String.class, Integer.class));
        lastVisitTime = getRuntimeContext().getState(
            new ValueStateDescriptor<>("last-visit", Long.class));
        categoryViewCount = getRuntimeContext().getMapState(
            new MapStateDescriptor<>("category-count", String.class, Integer.class));
    }

    @Override
    public void processElement(UserEvent event, Context ctx, Collector<TagUpdate> out)
            throws Exception {
        String userId = event.getUserId();

        // 更新最近访问时间标签
        lastVisitTime.update(event.getTimestamp());
        out.collect(new TagUpdate(userId, "last_visit_time",
                    String.valueOf(event.getTimestamp())));

        // 更新行为计数
        String actionKey = event.getActionType();
        Integer count = hourlyActionCount.get(actionKey);
        hourlyActionCount.put(actionKey, (count == null ? 0 : count) + 1);

        // 更新品类浏览计数
        if ("view_product".equals(event.getActionType())) {
            String category = event.getCategory();
            Integer catCount = categoryViewCount.get(category);
            categoryViewCount.put(category, (catCount == null ? 0 : catCount) + 1);

            // 每 10 次更新一次品类偏好标签（避免过于频繁）
            if ((catCount == null ? 1 : catCount + 1) % 10 == 0) {
                String topCategories = computeTopCategories(3);
                out.collect(new TagUpdate(userId, "realtime_prefer_category", topCategories));
            }
        }

        // 注册定时器：1小时后清理过期计数
        ctx.timerService().registerEventTimeTimer(
            event.getTimestamp() + Duration.ofHours(1).toMillis());
    }

    @Override
    public void onTimer(long timestamp, OnTimerContext ctx, Collector<TagUpdate> out) {
        // 清理过期的小时级计数
        // 实际实现中会根据 timestamp 判断哪些数据需要清理
    }

    private String computeTopCategories(int topN) throws Exception {
        // 从 categoryViewCount 中取 Top-N
        PriorityQueue<Map.Entry<String, Integer>> pq = new PriorityQueue<>(
            Comparator.comparingInt(Map.Entry::getValue));

        for (Map.Entry<String, Integer> entry : categoryViewCount.entries()) {
            pq.offer(entry);
            if (pq.size() > topN) pq.poll();
        }

        List<String> result = new ArrayList<>();
        while (!pq.isEmpty()) result.add(0, pq.poll().getKey());
        return JSON.toJSONString(result);
    }
}
```

### 2.3 Flink 状态管理在画像中的最佳实践

```
① State Backend 选择
   RocksDB（EmbeddedRocksDBStateBackend）
   原因：画像的状态数据量大（每个用户多个标签的中间状态）
   RocksDB 支持增量 Checkpoint，状态可以超出内存

② State TTL 配置
   对于滑动窗口类标签（近7天、近30天），配置 State TTL
   避免已流失用户的状态一直占用空间

   StateTtlConfig ttlConfig = StateTtlConfig.newBuilder(Time.days(30))
       .setUpdateType(StateTtlConfig.UpdateType.OnReadAndWrite)
       .build();

③ Checkpoint 调优
   间隔：60s（平衡延迟和开销）
   最小间隔：30s（避免 Checkpoint 堆积）
   超时时间：10min
   并发 Checkpoint：1

④ 并行度设计
   按 Kafka Partition 数 × 2 设置并行度
   keyBy(userId) 保证同一用户的事件在同一个 SubTask 处理
```

## 3. Spark 在画像中的应用

### 3.1 离线标签批量计算

```python
# PySpark 离线标签计算示例
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder \
    .appName("offline-tag-computation") \
    .config("spark.sql.adaptive.enabled", "true") \
    .getOrCreate()

# 1. 读取原始数据
orders = spark.sql("""
    SELECT user_id, order_amount, order_time, category
    FROM dwd.orders
    WHERE dt >= date_sub(current_date(), 30)
""")

user_info = spark.sql("""
    SELECT user_id, gender, age, city, register_time
    FROM dim.user_info
    WHERE dt = current_date()
""")

# 2. 计算交易标签
trade_tags = orders.groupBy("user_id").agg(
    F.count("*").alias("order_count_30d"),
    F.sum("order_amount").alias("total_amount_30d"),
    F.avg("order_amount").alias("avg_order_amount"),
    F.max("order_time").alias("last_order_time")
).withColumn("consume_level",
    F.when(F.col("total_amount_30d") >= 5000, "高")
     .when(F.col("total_amount_30d") >= 1000, "中")
     .otherwise("低")
)

# 3. 计算行为标签（品类偏好 Top3）
category_pref = orders.groupBy("user_id", "category") \
    .count() \
    .withColumn("rank", F.row_number().over(
        Window.partitionBy("user_id").orderBy(F.desc("count"))
    )) \
    .filter(F.col("rank") <= 3) \
    .groupBy("user_id") \
    .agg(F.collect_list("category").alias("prefer_categories"))

# 4. 组装标签宽表
tag_wide = user_info \
    .join(trade_tags, "user_id", "left") \
    .join(category_pref, "user_id", "left") \
    .withColumn("dt", F.current_date())

# 5. 写入 Hive 标签宽表
tag_wide.write.mode("overwrite") \
    .partitionBy("dt") \
    .saveAsTable("dw.user_tag_wide")
```

### 3.2 Spark 性能优化

```
画像场景下的 Spark 优化经验：

① 数据倾斜处理
   问题：keyBy(userId) 时某些大客户数据量远超其他用户
   方案：
   - 两阶段聚合：先加随机后缀打散，局部聚合后去掉后缀再全局聚合
   - 或者用 Spark AQE（Adaptive Query Execution）自动处理

② 小文件合并
   问题：标签计算产生大量小文件，影响下游读取性能
   方案：
   - coalesce() 合并分区
   - 配置 spark.sql.adaptive.coalescePartitions.enabled=true

③ 广播 Join 优化
   场景：标签宽表 JOIN 维度表（城市映射表、品类映射表）
   维度表通常很小（< 100MB），使用广播 Join 避免 Shuffle

④ 增量计算
   场景："近30天消费金额" 不需要每天重算30天
   优化：每天只加当天数据，减去第31天数据
   total_amount_30d(T) = total_amount_30d(T-1) + day_T - day_(T-30)
```

### 3.3 Spark 与 Flink 的分工

```
| 维度 | Spark | Flink |
|------|-------|-------|
| 定位 | 离线标签批量计算 | 实时标签流式计算 |
| 触发 | 定时调度（Airflow） | 7x24 持续运行 |
| 延迟 | T+1 | 秒级 |
| 适用标签 | 统计标签、算法标签 | 实时行为标签 |
| 状态 | 无状态（每次全量计算） | 有状态（增量更新） |
| 容错 | 任务失败重跑 | Checkpoint 恢复 |

分工原则：
  能离线的不实时 → 节省资源
  需要实时的用 Flink → 保证时效
  两者产出结果最终合并到统一标签存储
```

## 4. Kafka 在画像中的应用

### 4.1 数据采集通道

```
Kafka 在画像系统中承担三个角色：

① 行为数据采集
   App 埋点 → 日志服务 → Kafka → Flink 实时计算
   Web 埋点 → 日志服务 → Kafka → HDFS 离线存储

② 事件总线
   标签更新事件 → Kafka → 下游系统（推荐、营销）
   人群包变更事件 → Kafka → 下游系统

③ 数据缓冲
   突发流量时 Kafka 起缓冲作用
   下游计算能力不足时，数据在 Kafka 中堆积而不丢失
```

### 4.2 Topic 设计

```
Topic 规范：

行为日志：
  user_events_app      → App 端用户行为
  user_events_web      → Web 端用户行为
  user_events_mini     → 小程序端用户行为

交易事件：
  order_events         → 订单创建/支付/退款
  payment_events       → 支付事件

标签变更：
  tag_updates          → 标签更新事件（Flink 产出）
  crowd_updates        → 人群包变更事件

Partition 策略：
  按 userId hash 分区
  保证同一用户的事件有序到达
  Partition 数 = Flink 并行度的倍数（如 60 个 partition，Flink 30 并行度）
```

### 4.4 Kafka 与 Flink 的 Exactly-Once 配合

```
保证端到端 Exactly-Once 的关键配置：

Flink 消费 Kafka：
  - checkpoint.mode = EXACTLY_ONCE
  - Flink 管理 offset（不依赖 Kafka __consumer_offsets）

Flink 写入 Kafka（标签更新事件）：
  - delivery.guarantee = EXACTLY_ONCE
  - transactional.id.prefix = "tag-update-job"
  - Kafka broker 配置 transaction.max.timeout.ms >= checkpoint.interval * 3

两阶段提交流程：
  ① Flink 开启 Kafka 事务
  ② 处理数据，写入标签更新事件
  ③ Checkpoint 触发 → preCommit（flush，保存事务 ID）
  ④ Checkpoint 完成 → commit（消费者才能看到）
  ⑤ 开启下一个事务
```

## 5. HBase 在画像中的应用

### 5.1 HBase 作为标签在线存储

```
为什么选 HBase：
  ① 动态列：新增标签不需要改表结构
  ② 稀疏存储：用户没有的标签不占空间
  ③ 海量存储：轻松支撑亿级用户
  ④ 随机读写：单用户标签查询 < 10ms
  ⑤ 与 Hadoop 生态无缝集成
```

### 5.2 RowKey 设计详解

```java
/**
 * HBase RowKey 设计
 *
 * 设计目标：
 * ① 避免热点（不能用递增 ID 做前缀）
 * ② 支持按用户 ID 精确查询
 * ③ 支持扫描某一类用户（预留）
 */
public class RowKeyGenerator {

    /**
     * 方案一：反转 + 原始ID
     * 适合 ID 为数字的场景
     */
    public static byte[] buildRowKey_v1(long userId) {
        // 123456789 → "987_123456789"
        String reversed = new StringBuilder(
            String.valueOf(userId).substring(0, 3)).reverse().toString();
        String rowKey = reversed + "_" + userId;
        return Bytes.toBytes(rowKey);
    }

    /**
     * 方案二：Hash 前缀 + 原始ID（我们采用的方案）
     * 分散效果更好
     */
    public static byte[] buildRowKey_v2(long userId) {
        // hash(123456789) % 256 = 0x3f → "3f_123456789"
        int bucket = (MurmurHash.hash(userId) & 0xFF);
        String rowKey = String.format("%02x_%d", bucket, userId);
        return Bytes.toBytes(rowKey);
    }
}
```

### 5.3 HBase 读写优化

```
写入优化：
  ① 批量写入：每天凌晨 Spark → HBase 用 BulkLoad（生成 HFile 直接加载）
     比逐条 Put 快 10 倍以上
  ② WAL 策略：离线批量导入时可关闭 WAL（put.setDurability(Durability.SKIP_WAL)）
  ③ 预分区：建表时按 RowKey 前缀 00-ff 创建 256 个 Region

读取优化：
  ① 指定列族和列名：只读需要的标签，不要 scan 全部列
  ② 使用 MultiGet：批量查询多个用户时用 Table.get(List<Get>)
  ③ BlockCache 调优：标签数据读多写少，适当增大 BlockCache（默认 40%）
  ④ 协处理器：复杂过滤逻辑下推到 RegionServer 执行
```

### 5.4 HBase BulkLoad 流程

```
离线标签导入的标准流程：

Spark SQL 计算标签
    ↓
Spark 生成 HFile（按 RowKey 排序）
    ↓
HBase completeBulkLoad 加载 HFile
    ↓
直接变成 HBase 数据（跳过 MemStore/WAL，速度极快）

代码示例：
  // Spark 生成 HFile
  hbaseRdd.saveAsNewAPIHadoopFile(
      path = "/tmp/hbase-bulkload",
      keyClass = classOf[ImmutableBytesWritable],
      valueClass = classOf[KeyValue],
      outputFormatClass = classOf[HFileOutputFormat2]
  )

  // 加载到 HBase
  LoadIncrementalHFiles loader = new LoadIncrementalHFiles(conf);
  loader.doBulkLoad(new Path("/tmp/hbase-bulkload"), table);

性能对比（1亿用户，50个标签）：
  逐条 Put：~4小时
  BulkLoad：~20分钟
```

## 6. ClickHouse 在画像中的应用

### 6.1 ClickHouse 作为圈选引擎

```
ClickHouse 在画像中的核心角色 = 人群圈选 + 画像分析

为什么不用 MySQL：
  1亿用户的 WHERE 多条件查询 → MySQL 分钟级 → ClickHouse 秒级

为什么不用 Elasticsearch：
  ES 适合全文搜索，不适合数值聚合和多维分析
  ClickHouse 的列式存储 + 向量化执行对 OLAP 查询有碾压优势
```

### 6.2 ClickHouse 集群架构

```
集群拓扑（我们的配置）：

3 Shard × 2 Replica = 6 节点

Shard 1: Node1 (Primary) + Node2 (Replica)
Shard 2: Node3 (Primary) + Node4 (Replica)
Shard 3: Node5 (Primary) + Node6 (Replica)

分片策略：
  按 user_id hash 分片
  保证同一用户的数据在同一个 Shard

副本策略：
  使用 ReplicatedMergeTree 引擎
  自动同步，读写分离

查询分发：
  使用 Distributed 表引擎
  客户端查 Distributed 表 → 自动分发到各 Shard → 合并结果
```

### 6.3 ClickHouse 表引擎选择

```sql
-- 本地表（每个 Shard 上）
CREATE TABLE user_tags_local ON CLUSTER cluster_1
(
    user_id         UInt64,
    gender          LowCardinality(String),
    age             UInt8,
    city            LowCardinality(String),
    consume_level   LowCardinality(String),
    order_count_30d UInt32,
    total_amount_30d Decimal(12, 2),
    churn_prob      Float32,
    dt              Date
)
ENGINE = ReplicatedMergeTree(
    '/clickhouse/tables/{shard}/user_tags_local',
    '{replica}'
)
PARTITION BY dt
ORDER BY (city, consume_level, user_id)
SETTINGS index_granularity = 8192;

-- 分布式表（查询入口）
CREATE TABLE user_tags_distributed ON CLUSTER cluster_1
AS user_tags_local
ENGINE = Distributed(
    cluster_1,
    default,
    user_tags_local,
    sipHash64(user_id)  -- 分片键
);

-- 查询时直接查分布式表
SELECT count() FROM user_tags_distributed
WHERE dt = today() AND city = '北京' AND consume_level = '高';
```

### 6.4 ClickHouse 性能调优

```
① ORDER BY 设计原则
   把圈选条件中出现频率最高的列放在前面
   我们的排序键：(city, consume_level, user_id)
   → 按城市+消费等级圈选时，可以利用主键索引跳过大量数据

② LowCardinality 优化
   对枚举值少（< 10000 种）的列使用 LowCardinality
   内部用字典编码，减少存储空间和比较开销
   gender、city、consume_level 都适合

③ 分区策略
   按 dt（日期）分区
   圈选时只扫描最新分区，历史分区不参与
   定期清理过期分区（ALTER TABLE DROP PARTITION）

④ 物化视图预聚合
   对热门维度组合预计算人数
   运营选条件时先查预聚合结果（< 10ms）
   只有复杂条件才走全表扫描

⑤ 采样查询（预估场景）
   SELECT count() * 10 FROM user_tags_distributed SAMPLE 1/10
   WHERE conditions...
   → 只扫描 1/10 数据，速度快 10 倍，误差 < 5%
```

## 7. Redis 在画像中的应用

### 7.1 Redis 的三种用途

```
① 热标签缓存
   HBase 查询结果缓存到 Redis
   TTL 24h，命中率 60-70%

② 实时标签存储
   Flink 实时计算的标签直接写 Redis
   如：当前浏览品类、实时位置、在线状态
   TTL 2h（实时标签有时效性）

③ 人群包存储
   小型人群包（< 1000万用户）存为 Redis Bitmap 或 RoaringBitmap
   实时判断用户是否在人群中：GETBIT / SISMEMBER
```

### 7.2 Redis 数据结构选型

```
场景一：用户标签（多个标签）→ Hash
  Key:   user:tag:{userId}
  Field: tag_code
  Value: tag_value
  命令：HGET user:tag:100001 consume_level → "高"
        HMGET user:tag:100001 gender age city → ["男", "28", "北京"]

场景二：人群包（判断是否在人群中）→ Bitmap
  Key:   crowd:{crowdId}
  命令：SETBIT crowd:1001 100001 1  → 用户 100001 在人群中
        GETBIT crowd:1001 100001    → 1（在人群中）

场景三：实时计数（如近1小时浏览次数）→ String + INCR
  Key:   rt:view:{userId}:{hourSlot}
  命令：INCR rt:view:100001:2026031319  → 当前小时浏览次数+1
  TTL:  2 小时

场景四：排行榜/TopN（如用户偏好品类）→ Sorted Set
  Key:   pref:cat:{userId}
  命令：ZINCRBY pref:cat:100001 1 "手机"
        ZREVRANGE pref:cat:100001 0 2  → Top3 品类
```

### 7.3 Redis 集群与容量规划

```
集群配置：
  Redis Cluster 模式，6 主 6 从
  每个主节点 32GB 内存

容量估算：
  用户维度标签：
    1000 万活跃用户 × 50 标签 × 50B/标签 = 25GB
    → 分布在 6 个主节点上，每个约 4GB

  人群包：
    500 个活跃人群 × 平均 10MB = 5GB

  实时计数：
    1000 万活跃用户 × 5 个计数器 × 20B = 1GB

  总计：~31GB，6×32GB 的集群绰绰有余

过期策略：
  - 标签缓存：TTL 24h（每天离线更新后刷新）
  - 实时标签：TTL 2h（Flink 持续刷新）
  - 实时计数：TTL 2h
  - 人群包：无 TTL（手动管理生命周期）
```

  dw.user_tag_wide        → 用户标签宽表（最终产出）

### 8.2 数据生命周期管理

```
数据保留策略：

ODS 层：保留 90 天（原始数据体积大）
DWD 层：保留 180 天（清洗后数据）
DWS 层：保留 365 天（汇总数据体积小）
ADS 层：保留 30 天（标签宽表只需最新）

定期清理：
  ALTER TABLE ods.user_event_log DROP PARTITION (dt < '${90天前}');

存储格式：
  ORC 格式（压缩率高、查询快）
  Snappy 压缩（速度优先）
  分区：按 dt（日期）分区
```

### 8.3 增量与全量的权衡

```
全量计算：
  每天重新计算所有用户的标签
  简单可靠，但计算量大
  适用于：基础属性标签、算法标签

增量计算：
  只处理当天的增量数据
  复杂但高效
  适用于：累加型统计标签

示例：近30天消费金额
  全量方式：每天 SELECT SUM WHERE dt >= T-30 → 扫描 30 天数据
  增量方式：昨天的值 + 今天的消费 - 第31天前的消费 → 只扫描 2 天数据

我们的策略：
  70% 标签用全量计算（逻辑简单、不容易出错）
  30% 高频统计标签用增量计算（性能优化）
  每周末做一次全量校验（防止增量误差累积）
```

## 10. 面试高频问题与深度解答

### Q1: 为什么实时标签用 Flink 不用 Spark Streaming？

**回答：**

> 核心原因是**真正的流处理 vs 微批处理**。
>
> Spark Streaming（包括 Structured Streaming）本质是**微批处理**——把流数据切成小批次处理，最小延迟通常在 100ms-1s 级别。而 Flink 是**原生流处理**，每条数据到达就立即处理，端到端延迟可以做到毫秒级。
>
> 对于画像的实时标签，我们需要的是**事件驱动**——用户浏览了一个商品，就立即更新其品类偏好。Flink 的 `KeyedProcessFunction` + State 天然适合这种有状态的事件处理。
>
> 另外 Flink 的 **Checkpoint 机制**更成熟——增量 Checkpoint 配合 RocksDB State Backend，即使状态很大（每个用户几十个标签的中间状态）也能稳定运行。Spark 的 State 管理在大状态场景下有性能问题。
>
> 当然我们也用 Spark，但是用在**离线标签批量计算**上。Flink 和 Spark 各司其职。

### Q2: 标签数据从 Hive 同步到 HBase 和 ClickHouse 怎么保证一致性？

**回答：**

> 我们不追求**强一致性**，而是保证**最终一致性**。
>
> 同步流程是串行的：Hive 标签宽表计算完成 → 同步到 HBase（BulkLoad） → 同步到 ClickHouse → 刷新 Redis 缓存。每一步完成后检查行数一致，不一致则重试。
>
> 具体保障措施：
> 1. **行数校验**：同步完成后对比 Hive 和 HBase/ClickHouse 的行数，误差 < 0.1% 才通过
> 2. **版本标记**：每次同步携带 dt（日期）版本号，查询服务可以判断当前数据是哪天的
> 3. **兜底机制**：如果同步失败，查询服务降级使用前一天的数据
>
> 对于实时标签，走的是另一条链路：Flink → 直接写 Redis/HBase，不经过 Hive，所以不存在同步一致性问题。

### Q3: HBase 和 ClickHouse 为什么不用一个就够了？

**回答：**

> 因为它们擅长的查询模式完全不同。
>
> **HBase 擅长的是点查**：给定一个 user_id，取出这个用户的所有标签。这是在线服务最常见的场景——用户打开 App，推荐系统需要这个用户的标签来做推荐。HBase 单次 Get 延迟 < 10ms。
>
> **ClickHouse 擅长的是 OLAP 扫描**：给定一组条件（城市=北京 AND 消费等级=高），从 1 亿用户中找出符合条件的用户。这是人群圈选的场景。ClickHouse 的列式存储 + 向量化执行对这类查询极其高效。
>
> 如果用 HBase 做圈选：需要全表扫描 1 亿行 × 检查每行条件 → 分钟级甚至更慢。
> 如果用 ClickHouse 做点查：虽然也能做，但 MergeTree 引擎不适合高并发的随机读，而且运维复杂度会增加。
>
> 所以我们用 HBase 服务在线查询，ClickHouse 服务分析圈选，各取所长。

### Q4: Kafka 积压了怎么办？

**回答：**

> Kafka 消费积压通常说明**下游处理能力不足**。分几种情况处理：
>
> **1. Flink 作业处理慢：**
> - 检查是否有数据倾斜（某些 key 的数据量远大于其他）
> - 检查是否有反压（通过 Flink Web UI 查看各算子的 busy/backpressured 比例）
> - 增加 Flink 并行度（需要同时增加 Kafka Partition 数）
>
> **2. 突发流量（如大促）：**
> - Kafka 本身就是缓冲区，短期积压不影响数据完整性
> - 如果积压持续增长，动态扩容 Flink 作业（Reactive Mode 或手动调整并行度）
>
> **3. 长期积压：**
> - 评估是否需要拆分作业（一个大作业拆成多个小作业）
> - 评估是否可以降低计算复杂度（减少标签数、增大计算窗口）
>
> 我们的告警阈值：消费 lag > 100 万条触发预警，> 1000 万条触发紧急告警。

### Q5: 如果让你重新设计，技术选型会有什么不同？

**回答：**

> 如果重新设计，我会考虑以下调整：
>
> **1. 统一流批引擎**：用 Flink 统一离线和实时计算。Flink SQL 现在已经很成熟了，批处理性能接近 Spark。统一引擎可以减少维护成本，而且流批一体的标签计算逻辑可以复用。
>
> **2. 考虑 Apache Doris/StarRocks 替代 ClickHouse**：这些系统同时支持 OLAP 分析和一定程度的高并发点查，可能可以部分替代 ClickHouse + HBase 的组合，减少存储组件数量。
>
> **3. 引入 Iceberg/Hudi 数据湖**：替代传统的 Hive 分区表。数据湖支持 ACID 事务、Schema Evolution、Time Travel，对标签版本管理和数据回溯非常有帮助。
>
> 当然这些都是理想情况，实际项目中还要考虑团队技术栈、迁移成本和历史包袱。
