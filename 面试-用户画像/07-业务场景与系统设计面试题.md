## 1. 如何从零搭建用户画像平台

### 面试问法
> "如果让你从零搭建一个用户画像系统，你会怎么规划？"

### 回答框架（5 步走）

**第一步：需求调研（1-2 周）**
```
和各业务线对齐需求：
  - 运营团队需要什么？→ 人群圈选、用户分层、精准推送
  - 推荐团队需要什么？→ 用户特征、兴趣偏好、实时标签
  - 风控团队需要什么？→ 风险评分、异常行为检测
  - 数据分析需要什么？→ 用户画像报告、群体特征对比

产出：标签需求清单（优先级排序）
  P0：基础属性 + 核心行为标签（30 个）
  P1：交易标签 + 偏好标签（50 个）
  P2：算法标签 + 预测标签（20 个）
```

**第二步：数据基建（2-4 周）**
```
① 数据源梳理与接入
   App 埋点 → Kafka → HDFS/Flink
   服务端日志 → Flume → HDFS
   MySQL 业务库 → DataX/Flink CDC → Hive

② 数据仓库搭建
   ODS → DWD → DWS → ADS 四层建模
   重点：用户行为明细表、交易明细表、用户维度表

③ ID-Mapping
   建立 OneID 体系，打通多端 ID
   优先做确定性匹配（登录绑定）
```

**第三步：标签体系建设（4-6 周）**
```
① 设计标签元数据模型（注册中心）
② 开发标签计算框架
   - 离线：Spark SQL 配置化计算
   - 实时：Flink 流式计算
③ 搭建标签存储
   - HBase：全量标签 KV 存储
   - Redis：热标签缓存
④ 开发标签查询 API
   - 单用户查询
   - 批量查询
```

**第四步：圈选与服务化（3-4 周）**
```
① ClickHouse 部署 + 标签数据同步
② 开发圈选规则引擎
③ Bitmap 预估引擎
④ 前端圈选界面
⑤ 人群包管理
```

**第五步：质量与运营（持续）**
```
① 标签质量监控体系
② 标签生命周期管理
③ 标签使用情况分析
④ 持续优化迭代
```

### 量化交付物

```
MVP（2 个月）：
  - 100+ 基础标签上线
  - 单用户标签查询 API（P99 < 10ms）
  - 基本圈选功能

V1.0（4 个月）：
  - 300+ 标签（含实时标签）
  - 人群圈选（亿级用户 < 1s）
  - 标签质量监控

V2.0（6 个月）：
  - 500+ 标签
  - 算法标签
  - Lookalike 扩量
  - 标签市场（业务方自助创建标签）
```

## 2. 设计一个亿级用户的人群圈选系统

### 面试问法
> "设计一个系统，支持运营人员通过标签组合条件圈选用户，要求亿级用户秒级返回预估人数。"

### 需求澄清

```
功能需求：
  ① 运营在前端配置圈选条件（AND/OR 组合）
  ② 实时预估人群数量（< 1s）
  ③ 确认后生成精确的用户 ID 列表（< 5min）
  ④ 人群包可以推送到下游系统

非功能需求：
  - 用户量：1-2 亿
  - 标签数：500+（枚举 200+，数值 200+，算法 100+）
  - 并发：圈选查询 50 QPS（运营使用频率不高）
  - 预估精度：允许 ±5% 误差
  - 精确圈选：0 误差
```

### 架构设计

```
┌─────────────────────────────────────────────┐
│              前端圈选界面                      │
│  条件配置 → 实时预估显示 → 确认圈选           │
└───────────────────┬─────────────────────────┘
                    │ REST API
                    ▼
┌─────────────────────────────────────────────┐
│           圈选网关服务                        │
│  ┌───────────┐  ┌───────────┐  ┌──────────┐│
│  │ 规则解析   │  │ 路由分发   │  │ 结果缓存  ││
│  └───────────┘  └───────────┘  └──────────┘│
└───────┬──────────────┬──────────────┬───────┘
        │              │              │
   ┌────▼────┐    ┌────▼────┐   ┌────▼────┐
   │ Bitmap  │    │ClickHouse│   │ Spark  │
   │ 预估引擎 │    │ 精确圈选 │   │ 大批量  │
   │ < 200ms │    │ < 3s    │   │ < 5min │
   └─────────┘    └─────────┘   └─────────┘
```

### 核心设计决策

```
决策一：预估用 Bitmap 还是 ClickHouse？
  → Bitmap 做主，ClickHouse 做补
  枚举条件：Bitmap AND/OR → 100ms
  数值条件：降级 ClickHouse → 1s
  混合条件：Bitmap 缩小候选集 → ClickHouse 做精确过滤

决策二：精确圈选用 ClickHouse 还是 Spark？
  → 结果集小（< 100万）用 ClickHouse
  → 结果集大（> 100万）用 Spark 离线导出
  因为 ClickHouse 不适合大结果集的导出（内存压力大）

决策三：人群包存哪里？
  → 小人群（< 100万）：Redis Set
  → 大人群（> 100万）：RoaringBitmap 序列化到 Redis + HDFS 备份

决策四：条件缓存策略？
  → 条件指纹（MD5）做缓存 key，TTL 5分钟
  → 运营反复调整条件时，未变的子条件命中缓存
```

### 关键代码设计

```java
/**
 * 圈选服务核心接口
 */
public interface CrowdSelectService {

    /** 预估人数（秒级） */
    EstimateResult estimate(CrowdSelectRequest request);

    /** 精确圈选（分钟级） */
    CrowdResult select(CrowdSelectRequest request);

    /** 判断用户是否在人群中 */
    boolean contains(Long crowdId, Long userId);
}

/**
 * 路由策略：根据条件类型选择最优引擎
 */
public class EngineRouter {

    public EstimateResult estimate(CrowdSelectRequest request) {
        // 1. 查缓存
        EstimateResult cached = cache.get(request.cacheKey());
        if (cached != null) return cached;

        // 2. 判断条件类型
        if (allEnumConditions(request)) {
            // 纯枚举 → Bitmap 快速路径
            return bitmapEngine.estimate(request);
        } else if (simpleNumericConditions(request)) {
            // 简单数值 → ClickHouse
            return clickHouseEngine.estimate(request);
        } else {
            // 混合 → Bitmap 预过滤 + ClickHouse 精筛
            return hybridEngine.estimate(request);
        }
    }
}
```

## 3. 实时标签系统设计

### 面试问法
> "设计一个实时标签计算系统，要求用户行为发生后秒级更新标签。"

### 架构设计

```
┌──────────┐    ┌──────────┐    ┌──────────────────┐
│ App 埋点  │───→│  Kafka   │───→│  Flink 实时作业   │
│ Web 埋点  │    │ 行为事件  │    │                  │
│ 小程序    │    │          │    │ ┌──────────────┐ │
└──────────┘    └──────────┘    │ │ 行为解析      │ │
                                │ │   ↓          │ │
                                │ │ keyBy(userId) │ │
                                │ │   ↓          │ │
                                │ │ 标签计算       │ │
                                │ │ (有状态)      │ │
                                │ └──────────────┘ │
                                └───────┬──────────┘
                                        │
                        ┌───────────────┼───────────────┐
                        ▼               ▼               ▼
                   ┌────────┐     ┌─────────┐     ┌────────┐
                   │ Redis   │     │  HBase  │     │ Kafka  │
                   │ 实时标签 │     │ 持久化   │     │ 事件流 │
                   └────────┘     └─────────┘     └────────┘
```

### 核心设计点

```
① 实时标签类型
   - 实时行为计数：近1小时浏览次数、近5分钟点击数
   - 实时偏好：当前浏览品类 Top3
   - 实时状态：是否在线、当前页面
   - 实时风险：异常行为评分

② 有状态计算
   使用 Flink KeyedProcessFunction
   每个用户一组 State（MapState、ValueState）
   State Backend：RocksDB（支持大状态）
   增量 Checkpoint 到 HDFS

③ 标签输出
   双写：Redis（实时查询）+ HBase（持久化）
   异步写入：使用 AsyncFunction 或自定义 Sink
   幂等写入：相同 userId + tagCode 覆盖写

④ 延迟保证
   端到端延迟 = Kafka 消费延迟 + Flink 处理延迟 + 写入延迟
   目标 < 3 秒
   Flink 处理延迟通常 < 100ms
   Redis 写入 < 1ms
   主要延迟在 Kafka 消费和网络传输
```

### 容错与高可用

```
① Checkpoint 配置
   间隔：60s
   模式：EXACTLY_ONCE
   Storage：HDFS

② 故障恢复
   Flink 作业挂了 → 从最近 Checkpoint 恢复
   State 恢复后，从 Kafka offset 重新消费
   实时标签会有短暂延迟（~ Checkpoint 间隔），但不会丢数据

③ 背压处理
   Flink 内置背压机制（Credit-Based 流控）
   下游写入慢 → Flink 自动降速 → Kafka 积压
   Kafka 作为缓冲区，不丢数据

④ 监控告警
   Kafka 消费 lag > 10万 → 预警
   Flink Checkpoint 失败 → 告警
   Redis 写入延迟 P99 > 10ms → 告警
```

## 4. AB 实验与画像结合

### 面试问法
> "你们的画像数据怎么和 AB 实验结合的？"

### 设计思路

```
画像 + AB 实验的三种结合方式：

① 画像驱动分流（按人群分桶）
   传统 AB：随机分流 50% / 50%
   画像 AB：高价值用户走实验组，低价值走对照组
   或者：同一人群内再随机分流，保证组间可比

② 画像作为分析维度
   实验结束后，按画像标签切分分析：
   - 整体效果：转化率提升 5%
   - 高消费用户：转化率提升 8%
   - 低消费用户：转化率提升 2%
   → 发现策略对高消费用户更有效

③ 画像优化实验策略
   第一轮实验 → 发现对 "25-35岁女性" 效果最好
   第二轮 → 只对该人群上线策略
   → 画像帮助缩小目标人群，提升 ROI
```

### 技术实现

```java
/**
 * 基于画像的 AB 分流
 */
public class ProfileBasedSplitter {

    /**
     * 判断用户进入哪个实验桶
     */
    public String assignBucket(String userId, String experimentId) {
        // 1. 获取用户画像
        Map<String, String> tags = tagService.getUserTags(userId);

        // 2. 检查是否有人群定向
        Experiment exp = experimentService.getExperiment(experimentId);
        if (exp.hasTargetCrowd()) {
            // 只有目标人群内的用户参与实验
            if (!crowdService.contains(exp.getTargetCrowdId(), userId)) {
                return "default";  // 不在目标人群中，走默认策略
            }
        }

        // 3. 基于 userId + experimentId 做确定性 hash 分桶
        int bucket = Math.abs((userId + experimentId).hashCode()) % 100;
        return exp.getBucketAllocation(bucket);  // "control" or "treatment"
    }
}
```

## 5. 用户增长场景中的画像应用

### 面试问法
> "画像在用户增长中有哪些应用？"

### 场景一：用户分层运营

```
基于用户生命周期做精细化运营：

① 新用户（注册 < 7天）
   标签：is_new_user = true
   策略：新人礼包、引导任务、高补贴优惠券

② 活跃用户（近7天有访问且有交易）
   标签：activity_level = "高活"
   策略：交叉推荐、提升客单价、会员权益

③ 沉默用户（15-30天未访问）
   标签：activity_level = "沉默"
   策略：召回推送、专属优惠、短信触达

④ 流失用户（> 30天未访问）
   标签：activity_level = "流失"
   策略：大额优惠券、好友邀请奖励

⑤ 回流用户（流失后重新活跃）
   标签：is_return_user = true
   策略：回流关怀、专属优惠续费

画像在其中的作用：
  - 自动判断用户所处阶段
  - 实时更新生命周期标签
  - 触发对应的运营策略
```

### 场景二：流失预警

```
提前识别即将流失的用户，主动干预

算法标签：churn_probability（流失概率）

模型输入特征：
  - 近7/14/30天访问频率趋势（下降 → 流失信号）
  - 近7天消费金额（减少 → 流失信号）
  - 最近一次投诉/退货距今天数（近期不满 → 流失信号）
  - 优惠券使用率变化
  - App 使用时长变化

流失干预策略：
  churn_prob > 0.8 → 紧急（电话回访 + 大额优惠）
  churn_prob 0.5-0.8 → 中度（Push + 优惠券）
  churn_prob 0.3-0.5 → 轻度（个性化推荐强化）
```

### 场景三：Lookalike 扩量

```
已知一批高转化的种子用户，找到更多相似用户

① 提取种子用户的画像特征分布
   性别分布：男 70% 女 30%
   年龄分布：25-35 占 60%
   消费等级：高消费 80%

② 在全量用户中找相似的人
   方案一：规则匹配
   SELECT user_id FROM user_tags
   WHERE age BETWEEN 25 AND 35
     AND consume_level IN ('高', '中')
     AND prefer_category = '数码'

   方案二：向量相似度
   将用户标签转为特征向量 → 计算余弦相似度 → 取 Top-N

③ 圈选结果作为广告投放/营销推送的目标人群
```

## 6. 推荐系统与画像的协作

### 面试问法
> "画像系统如何给推荐系统提供数据支撑？"

### 协作架构

```
                    ┌─────────────────────┐
                    │     推荐引擎         │
                    │  召回 → 排序 → 重排   │
                    └──────────┬──────────┘
                               │
               ┌───────────────┼───────────────┐
               ▼               ▼               ▼
        ┌────────────┐  ┌───────────┐  ┌────────────┐
        │ 用户特征    │  │ 物品特征   │  │ 交叉特征    │
        │ (画像标签)  │  │           │  │ (用户×物品) │
        └────────────┘  └───────────┘  └────────────┘
               ↑
        ┌────────────┐
        │  画像系统   │
        │ Redis 实时  │
        │ HBase 全量  │
        └────────────┘

画像提供给推荐的特征：
  - 用户基础属性：年龄、性别、城市
  - 行为偏好：偏好品类、偏好价格区间
  - 实时特征：当前浏览品类、当前会话行为序列
  - 预测特征：购买意向、流失概率
```

### 画像特征的使用方式

```
① 召回阶段
   热门召回：全量用户看同样的热门商品
   画像召回：根据用户偏好品类/品牌召回对应商品
   → 画像帮助推荐系统"缩小候选集"

② 排序阶段
   模型输入 = 用户特征（画像） + 物品特征 + 上下文特征
   画像标签直接作为模型 feature 输入

③ 重排/策略层
   人群分桶策略：高价值用户优先展示高客单价商品
   新人策略：新用户展示爆款引导
   → 画像驱动的策略路由

④ 实时更新
   用户正在浏览 "手机" → 实时更新 realtime_prefer_category
   下一次推荐请求 → 推荐系统拿到最新画像 → 推荐更多手机配件
```

### 接口设计

```java
// 推荐系统调用画像的标准接口
@GetMapping("/api/v1/features/user/{userId}")
public UserFeatures getUserFeatures(
    @PathVariable String userId,
    @RequestParam String scene) {
    // scene: "recommend" / "search" / "ad"
    // 不同场景返回不同特征集合

    return UserFeatures.builder()
        .basicTags(getBasicTags(userId))          // 基础标签
        .behaviorTags(getBehaviorTags(userId))     // 行为标签
        .realtimeTags(getRealtimeTags(userId))     // 实时标签
        .crowdList(getUserCrowds(userId))           // 所属人群
        .build();
}

// 性能要求：
// 推荐链路总 SLA < 50ms
// 画像查询占 < 5ms（Redis 缓存命中）
```

## 7. 广告投放中的 DMP 系统设计

### 面试问法
> "了解 DMP 吗？画像系统和 DMP 什么关系？"

### DMP 核心概念

```
DMP（Data Management Platform）= 广告行业的用户画像系统

核心区别：
  画像系统 → 面向内部（运营、产品、推荐）
  DMP → 面向广告投放（广告主、媒体）

DMP 三种数据类型：
  ① 第一方数据：企业自己的用户数据（CRM、App 行为）
  ② 第二方数据：合作伙伴数据（电商×银行联合建模）
  ③ 第三方数据：外部数据供应商（如运营商标签）
```

### DMP 系统架构

```
┌─────────────────────────────────────────────────┐
│                  广告主控制台                      │
│  创建人群 → 投放配置 → 效果分析                    │
└───────────────────────┬─────────────────────────┘
                        │
┌───────────────────────┴─────────────────────────┐
│                  DMP 核心层                       │
│  ┌──────────┐  ┌───────────┐  ┌───────────────┐│
│  │ 人群管理  │  │ 标签市场   │  │ Lookalike    ││
│  │ 圈选引擎  │  │ 自定义标签  │  │ 扩量引擎     ││
│  └──────────┘  └───────────┘  └───────────────┘│
└───────────────────────┬─────────────────────────┘
                        │
┌───────────────────────┴─────────────────────────┐
│                  数据层                           │
│  第一方数据 + 第二方数据 + 第三方数据               │
│  ID-Mapping 打通                                  │
│  合规脱敏处理                                      │
└─────────────────────────────────────────────────┘
```

### DMP 与画像系统的关系

```
画像系统 是 DMP 的底层基础设施

画像系统提供：
  - 标签计算能力
  - 用户存储与查询
  - 人群圈选引擎
  - ID-Mapping

DMP 在画像之上增加：
  - 广告投放对接（ADX/DSP）
  - 外部数据接入
  - 隐私计算（联邦学习、安全多方计算）
  - 广告效果归因
  - 频次控制（同一用户不重复曝光）
```

### CDP vs DMP

```
CDP（Customer Data Platform）= 企业级客户数据平台

DMP vs CDP：
  DMP 侧重广告场景，主要使用匿名 Cookie/设备 ID
  CDP 侧重客户关系管理，基于实名用户（手机号、会员ID）

CDP 核心能力：
  ① 全渠道数据整合（App + Web + 线下门店 + 客服）
  ② 360° 用户视图（OneID 打通所有触点）
  ③ 客户旅程编排（第 1 天发欢迎邮件 → 第 3 天推荐商品 → 第 7 天优惠券）
  ④ 实时个性化（网站/App 个性化展示）

画像系统同时服务 DMP 和 CDP，提供底层标签和圈选能力。
```

## 8. 数据治理与隐私合规

### 面试问法
> "画像数据涉及用户隐私，你们怎么处理合规问题？"

### 隐私合规框架

```
合规要求：
  中国：《个人信息保护法》（PIPL）
  欧盟：GDPR
  行业：工信部 App 合规检测

核心原则：
  ① 最小必要：只采集业务必需的数据
  ② 知情同意：用户明确授权才能使用
  ③ 目的限制：数据只能用于声明的目的
  ④ 数据安全：传输加密、存储脱敏
  ⑤ 可删除权：用户要求删除时必须响应
```

### 技术实现

```
① 数据分级
  L1 公开数据：用户昵称、头像
  L2 一般数据：城市、年龄段
  L3 敏感数据：手机号、身份证号、精确位置
  L4 高敏数据：生物特征、健康数据

② 脱敏策略
  手机号：138****1234（展示脱敏）
  身份证：存储时 AES-256 加密
  设备 ID：hash 后存储，不存原始值

③ 标签层面的隐私保护
  不生成可以直接定位个人的标签
  例如："住在朝阳区某某小区" → ✗
        "一线城市用户" → ✓

④ 用户数据删除
  用户注销 → 48小时内删除所有标签数据
  涉及：Hive 分区数据 + HBase 行 + Redis Key + ClickHouse 行
  需要完整的数据血缘追踪才能保证删除彻底

⑤ 数据授权管理
  标签查询 API 需要授权
  不同业务线只能访问自己有权限的标签
  敏感标签需要额外审批
```

### 隐私计算（进阶）

```
联邦学习应用场景：
  银行有用户的消费能力数据
  电商有用户的购物偏好数据
  双方想联合建模 → 但数据不能直接交换

联邦学习方案：
  模型训练在各方本地执行
  只交换加密的模型参数（梯度）
  最终得到联合模型，但双方看不到对方原始数据

在画像中的应用：
  与外部数据源（运营商、银行）联合建模
  丰富用户画像 without 交换原始数据
```

## 9. 系统稳定性保障

### 面试问法
> "画像系统挂了会影响什么？怎么保障稳定性？"

### 影响范围

```
画像系统是很多下游系统的基础设施：
  推荐系统 → 拿不到用户特征 → 推荐效果变差
  营销系统 → 圈不了人群 → 无法做精准推送
  风控系统 → 拿不到风险标签 → 风控策略失效
  AB 实验 → 分流条件失效 → 实验结果不可信

所以画像系统的 SLA 要求：
  标签查询 API：99.95%
  圈选服务：99.9%
  标签计算 SLA：T+1 凌晨 3:30 前就绪
```

### 稳定性保障措施

```
① 多级缓存降级
   Redis 挂了 → 降级查 HBase（延迟从 1ms → 10ms，但不中断服务）
   HBase 挂了 → 返回默认标签（部分功能降级）
   整链路超时 → 返回缓存版本的标签（可能是昨天的数据，但不报错）

② 限流熔断
   标签查询 API：Sentinel 限流，单用户 100 QPS
   圈选服务：Sentinel 限流，全局 50 QPS
   ClickHouse 慢查询 → 熔断，返回"请稍后重试"

③ 异步解耦
   标签计算与标签服务完全解耦
   Flink 挂了 → 实时标签暂停更新，但历史标签仍可查询
   Spark 任务失败 → 使用前一天的标签数据

④ 多副本与容灾
   HBase：3 副本
   ClickHouse：2 副本
   Redis：主从 + 哨兵
   跨机房部署：双机房热备
```

### 监控体系

```
四大黄金指标：
  ① 延迟（Latency）：标签查询 P99 < 5ms
  ② 流量（Traffic）：QPS 峰值 5 万
  ③ 错误率（Errors）：< 0.05%
  ④ 饱和度（Saturation）：Redis 内存 < 80%，ClickHouse CPU < 70%

告警规则：
  标签查询 P99 > 50ms → 预警（可能 Redis 热点）
  标签查询错误率 > 1% → 紧急告警
  Kafka 消费 lag > 100 万 → 预警
  Flink Checkpoint 连续 3 次失败 → 紧急告警
  标签 T+1 任务 4:00 未完成 → 紧急告警
```

## 10. 场景题综合实战

### 场景一：大促准备

> **面试官问：双11 大促，画像系统需要做哪些准备？**

```
准备工作（按时间线）：

大促前 2 周：
  ① 性能压测
     - 标签查询 API 压到 10 万 QPS
     - 圈选服务压到 100 并发
     - 识别瓶颈并扩容

  ② 人群提前圈选
     - 运营提前圈好大促目标人群
     - 人群包预计算并缓存
     - 避免大促当天现场圈选

  ③ 资源扩容
     - Redis 扩容到 2 倍内存
     - Flink 增加并行度
     - ClickHouse 预加载热数据

大促前 1 天：
  ④ 标签全量刷新
     - 确保当天标签数据最新
     - Bitmap 预构建完成
     - 所有人群包更新就绪

  ⑤ 预案演练
     - 模拟 Redis 故障 → 验证降级到 HBase
     - 模拟 Flink 故障 → 验证实时标签暂停不影响服务
     - 值班安排

大促当天：
  ⑥ 实时监控
     - 大屏展示关键指标
     - 告警升级（P2 → P1）
     - 值班人员 on-call

  ⑦ 动态调整
     - 如果某个人群包查询量暴增 → 动态预热到本地缓存
     - 如果 Kafka 积压 → 动态扩 Flink 并行度
```

### 场景二：标签突然不准了

> **面试官问：业务反馈用户标签不准确，怎么排查？**

```
排查流程（5 步排查法）：

① 确认问题范围
   - 哪个标签不准？影响多少用户？
   - 是全量不准还是部分用户？
   - 从什么时间开始的？

② 检查标签质量监控
   - 覆盖率是否突然下降？
   - 日环比波动是否异常？
   - 如果质量监控有告警，说明系统已发现

③ 检查上游数据
   - 上游 Hive 表数据是否正常？（行数、非空率）
   - Kafka 消息是否正常？（消息格式、数据量）
   - 是否有上游数据源变更未通知？

④ 检查计算逻辑
   - Spark/Flink 任务是否成功？日志是否有异常？
   - 计算 SQL 是否被人修改？
   - 是否有数据倾斜导致部分用户计算异常？

⑤ 检查同步链路
   - Hive → HBase 同步是否正常？
   - 数据版本是否是最新的？
   - Redis 缓存是否过期未刷新？

常见原因 Top3：
  1. 上游数据源变更（字段含义变了、数据量突降）
  2. 计算任务部分失败（Spark OOM、数据倾斜）
  3. 同步延迟（HBase BulkLoad 失败，使用的是旧数据）
```

### 场景三：新业务线接入

> **面试官问：一个新业务线要接入画像平台，你怎么处理？**

```
接入流程：

① 需求对接（1 天）
   - 梳理新业务需要的标签
   - 区分：已有标签可复用 vs 需要新增标签
   - 确认数据源（新业务有哪些数据可以接入）

② 数据接入（3-5 天）
   - 新数据源接入 Kafka/Hive
   - 新维度表接入（如果是新品类、新业务线）
   - ID 打通（新业务的用户 ID 如何与 OneID 关联）

③ 标签开发（5-10 天）
   - 已有标签开放权限
   - 新标签走标签注册流程：评审 → 开发 → 测试 → 上线
   - 配置质量检查规则

④ 服务开通（1-2 天）
   - 开通标签查询 API 权限
   - 配置查询额度和限流规则
   - 对接文档和 SDK 交付

⑤ 上线验证（2-3 天）
   - 抽样验证标签准确性
   - 性能验证（新增流量是否影响现有服务）
   - 监控配置

总周期：2-3 周
```

## 附录：系统设计面试通用答题框架

```
SNAKE 框架（适用于所有系统设计题）：

S - Scenario（场景）

  性能优化：缓存、异步、预计算

  "这里有个 trade-off..." → 展示深度思考
```
