## 一、画像服务流量特征

### 1.1 核心流量指标

**在线查询（QPS 10万+，P99 < 10ms）**

在线查询是画像系统最核心的流量类型，服务于以下场景：
- 首页推荐：用户打开美团APP时查询兴趣偏好、消费能力、位置偏好等标签
- 搜索排序：结合画像做个性化排序
- 广告投放：实时判断用户是否属于某个人群包
- 风控决策：交易链路中查询用户风险等级标签

流量特点：
- 单次查询涉及20-50个标签维度，对延迟极其敏感
- 高峰时段（午餐/晚餐）可达平时的3-5倍
- 可用性要求99.99%，任何抖动都影响核心业务链路

**批量查询（百万级）**

- 营销系统批量获取目标用户画像、离线模型训练拉取特征
- 单次请求涉及数万到数百万用户
- 延迟要求宽松（秒级到分钟级），对吞吐量要求高
- 容易对在线服务产生资源争抢

**圈选查询（亿级秒级）**

- 运营通过标签组合筛选目标人群（如"北京+25-35岁+近30天下单3次以上"）
- 广告系统创建人群包，数据分析师做用户分群统计
- 条件组合灵活，涉及大量集合运算（交/并/差集）

**实时写入（TPS 数万）**

- 用户行为事件流（浏览、点击、下单）、Flink实时标签计算结果
- 第三方数据同步、标签规则引擎实时判定
- 需保证最终一致性，写入后秒级对查询可见

- 接入层路由：根据请求类型路由到不同集群

## 二、缓存体系设计

### 2.1 多级缓存：本地Caffeine -> Redis -> HBase/ClickHouse

**整体架构**

```
请求 → L1: Caffeine缓存  → L2: Redis分布式缓存 → L3: HBase/ClickHouse
        (进程内, <1ms)     (网络, 1-3ms)          (存储, 5-50ms)
```

**L1 Caffeine 配置与策略**

```java
Cache<String, UserProfile> localCache = Caffeine.newBuilder()
    .maximumSize(500_000)                     // 50万用户, 约250MB
    .expireAfterWrite(Duration.ofSeconds(30))  // 写后30秒过期保证新鲜度
    .expireAfterAccess(Duration.ofSeconds(15)) // 15秒无访问提前淘汰
    .refreshAfterWrite(Duration.ofSeconds(20)) // 20秒后异步刷新,避免过期击穿
    .recordStats()                             // 开启命中率统计
    .executor(cacheRefreshExecutor)            // 自定义刷新线程池
    .build(this::loadFromRedis);
```

关键配置说明：
- `maximumSize`：50万用户 x 500B = 约250MB，控制在堆内存的20%以内
- `refreshAfterWrite`：20秒后触发异步刷新，key未过期时就预加载新数据，避免过期瞬间的缓存击穿
- 选择Caffeine：基于W-TinyLfu算法，命中率显著优于Guava Cache和ConcurrentHashMap
- 命中率预期：热点用户60-70%，整体40-50%

**L2 Redis 配置**
- 集群模式：Redis Cluster，6主6从，每节点32GB，总容量约200GB
- 过期策略：TTL 5-10分钟，高频更新标签TTL短，低频标签TTL长
- 序列化：Protobuf，比JSON节省60%以上空间
- 命中率预期：> 95%，意味着不到5%请求穿透到HBase

**L3 存储层**
- HBase：用户画像持久化存储，支持单用户多标签快速查询
- ClickHouse：圈选查询和分析查询的存储引擎

**各层协作流程**

```
1. 查L1(Caffeine):
   命中 → 直接返回（约40-50%请求在此结束）
   未命中 → 继续
2. 查L2(Redis):
   命中 → 回填L1，返回（约95%剩余请求在此结束）
   未命中 → 继续
3. 查L3(HBase):
   查到 → 回填L2和L1，返回
   未查到 → 返回默认值，记录缺失标签
```

**缓存一致性保证**：
- 写操作先更新HBase，再删Redis缓存
- MQ广播缓存失效事件通知各服务实例清本地缓存
- TTL兜底：即使通知丢失，也能在TTL过期后自动更新

### 2.2 Redis缓存深入设计

**Hash结构存储画像**

```
Key: up:{userId}
Field-Value:
  age       → "25"
  gender    → "M"
  city      → "北京"
  consume   → "high"
  interests → "美食,旅游,电影"
  rfm_score → "4.5"
```

选择Hash的原因：
- 支持按字段读取（HMGET），无需获取完整画像
- 支持按字段更新（HSET），标签更新时只写变化字段
- 字段数<128且单字段值<64字节时，Redis用ziplist编码节省内存
- 支持HSCAN遍历，便于数据导出和清理

**热用户识别与分层策略**

| 类别 | 判定规则 | 缓存策略 |
|------|---------|---------|
| 超热用户 | 近1小时查询>100次 | 常驻L1，TTL 5分钟 |
| 热用户 | 近1小时查询>10次 | 常驻L2，TTL 10分钟 |
| 温用户 | 近1天有查询 | L2缓存，TTL 5分钟 |
| 冷用户 | 超7天未查询 | 不主动缓存，按需加载 |

识别方案：本地滑动窗口计数器（ConcurrentHashMap + AtomicLong）或Redis HyperLogLog统计查询频率。

**容量估算（1亿用户）**

```
单用户画像存储大小：
- Key: up:{userId}（约20字节）
- 50个标签: Field约10字节 + Value约20字节 = 30字节/标签
- Hash开销: ziplist元数据约50字节
- 单用户总计: 20 + 50×30 + 50 ≈ 1,570字节 ≈ 1.5KB

总容量（缓存20%活跃用户）：
- 2000万用户 × 1.5KB = 30GB
- 含碎片率1.2x: 36GB
- 含主从复制: 72GB（双副本）

Redis集群规划：
- 6个主节点，每节点12GB数据
- 6个从节点用于读写分离和故障转移
- 总内存需求: 12节点 × 16GB = 192GB
```

**更新策略（Cache Aside Pattern）**

写操作流程：
1. 更新HBase（数据库）
2. 删除Redis缓存（而非更新，因为删除是幂等的，避免并发写不一致）
3. 通过MQ广播缓存失效事件
4. 各服务实例收到事件后清除本地缓存

**延迟双删策略**

在极端并发场景下防止不一致：

```java
public void updateUserTag(long userId, String tag, String value) {
    // 1. 更新数据库
    hbaseDao.updateTag(userId, tag, value);
    // 2. 第一次删除缓存
    String cacheKey = "up:" + userId;
    redisTemplate.delete(cacheKey);
    // 3. 延迟500ms再删一次（异步）
    delayDeleteExecutor.schedule(
        () -> redisTemplate.delete(cacheKey), 500, TimeUnit.MILLISECONDS);
    // 4. 广播缓存失效
    mqProducer.send("cache_invalidate", cacheKey);
}
```

### 2.3 穿透/击穿/雪崩防护

**缓存穿透防护 — Bloom Filter**

穿透场景：查询不存在的用户，每次都穿透到数据库。

```java
// 1亿容量, 0.01%误判率, 约1.92GB内存, 13个哈希函数
BloomFilter<Long> userIdFilter = BloomFilter.create(
    Funnels.longFunnel(), 100_000_000L, 0.0001);

public UserProfile queryProfile(long userId) {
    // 先过Bloom Filter
    if (!userIdFilter.mightContain(userId)) {
        return UserProfile.empty();  // 一定不存在
    }
    return doQuery(userId);
}
```

维护策略：
- 每天凌晨全量重建（Bloom Filter不支持删除）
- 新注册用户实时添加
- 辅以空值缓存（通过Bloom Filter但HBase查不到时缓存空值，TTL 30秒）
- API网关层userId格式校验过滤明显非法请求

**缓存击穿防护 — 互斥锁 + 逻辑过期**

击穿场景：热点key过期瞬间大量请求同时穿透到数据库。

方案一 — 互斥锁：

```java
public UserProfile queryWithMutex(long userId) {
    String cacheKey = "up:" + userId;
    UserProfile profile = getFromCache(cacheKey);
    if (profile != null) return profile;

    // 获取分布式锁
    String lockKey = "lock:up:" + userId;
    boolean locked = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, "1", Duration.ofSeconds(5));
    try {
        if (locked) {
            profile = hbaseDao.getProfile(userId);
            setToCache(cacheKey, profile != null ? profile : UserProfile.empty(),
                      profile != null ? Duration.ofMinutes(5) : Duration.ofSeconds(30));
            return profile;
        } else {
            Thread.sleep(50);
            return queryWithMutex(userId);  // 重试
        }
    } finally {
        if (locked) redisTemplate.delete(lockKey);
    }
}
```

方案二 — 逻辑过期：

```java
public UserProfile queryWithLogicalExpire(long userId) {
    String cacheKey = "up:" + userId;
    CacheWrapper<UserProfile> wrapper = getFromCache(cacheKey);
    if (wrapper == null) return loadAndCache(userId);

    // 未过期直接返回
    if (System.currentTimeMillis() < wrapper.getLogicalExpireTime()) {
        return wrapper.getData();
    }
    // 已过期：尝试异步更新，但立即返回旧数据
    if (tryLock("lock:up:" + userId)) {
        cacheRefreshExecutor.execute(() -> {
            try { loadAndCache(userId); }
            finally { unlock("lock:up:" + userId); }
        });
    }
    return wrapper.getData();  // 返回旧数据，保证可用性
}
```

| 对比维度 | 互斥锁方案 | 逻辑过期方案 |
|---------|----------|------------|
| 数据一致性 | 强一致 | 短暂不一致 |
| 可用性 | 部分请求需等待 | 高可用，始终有数据 |
| 适用场景 | 一致性要求高 | 可用性要求高 |

画像系统推荐逻辑过期方案：画像数据有一定时效容忍度，优先保可用性。

**缓存雪崩防护 — TTL随机偏移**

雪崩场景：大量key同一时间过期，请求集中穿透到数据库。

```java
public void setToCache(String key, Object value, Duration baseTtl) {
    long randomOffset = ThreadLocalRandom.current()
        .nextLong(0, baseTtl.toMillis() / 5);  // 基础TTL的20%随机偏移
    Duration finalTtl = baseTtl.plusMillis(randomOffset);
    redisTemplate.opsForValue().set(key, serialize(value), finalTtl);
}
// 基础TTL 5分钟 → 最终TTL在5-6分钟之间随机分布
```

额外措施：缓存预热（启动时加载热点数据）、多级缓存兜底、熔断降级、Redis Cluster高可用。

## 三、查询优化

### 3.1 HBase优化

**RowKey设计**

```
RowKey = salt(hash(userId)%16) + "_" + reverse(userId) + "_" + tagCategory
示例: salt=07, userId=123456789 → "07_987654321_basic"
```

设计原则：
- 反转userId避免递增ID导致Region热点
- salt前缀保证数据均匀分布到预创建的16个Region
- 长度控制在16-32字节，过长浪费存储
- 相关数据物理存储在一起减少IO

**MultiGet批量查询**

```java
public Map<Long, UserProfile> batchGetProfiles(List<Long> userIds) {
    List<Get> gets = userIds.stream().map(id -> {
        Get get = new Get(buildRowKey(id));
        get.addColumn(CF_TAGS, COL_AGE);    // 指定具体列减少传输量
        get.addColumn(CF_TAGS, COL_GENDER);
        get.addColumn(CF_TAGS, COL_CITY);
        return get;
    }).collect(Collectors.toList());
    Result[] results = table.get(gets);  // 底层按Region分组并行发送
    // 解析结果...
}
```

- 单次MultiGet建议不超过1000个Get，过多导致RPC包过大
- 尽量指定具体列族和列，减少不必要的数据传输

**预分区**：建表时根据salt值创建16个Region，避免写入时集中在同一Region频繁分裂。

**Bloom Filter**：开启ROW级别Bloom Filter，快速判断RowKey是否在某个HFile中，减少无效磁盘IO。画像单用户查询场景推荐ROW类型。

**BlockCache配置**

```
hfile.block.cache.size = 0.4           # 堆内存40%给BlockCache
hbase.bucketcache.ioengine = offheap   # 堆外内存缓存
hbase.bucketcache.size = 8192          # 堆外8GB

L1 LruBlockCache(堆内): 存储索引块和元数据块
L2 BucketCache(堆外): 存储数据块
画像读多写少, BlockCache命中率目标 > 85%
```

**Compaction策略**

```
# Minor Compaction: 最少3个文件触发, 一次最多合并10个
hbase.hstore.compaction.min = 3
hbase.hstore.compaction.max = 10

# Major Compaction: 关闭自动, 凌晨手动触发避免白天IO抖动
hbase.hregion.majorcompaction = 0
```

### 3.2 ClickHouse优化

**分区裁剪**

```sql
CREATE TABLE user_profile_wide (
    user_id UInt64, dt Date, age UInt8, gender String,
    city String, consume_level String, interests String
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(dt)         -- 按月分区
ORDER BY (city, age, user_id)     -- 排序键 = 稀疏索引
SETTINGS index_granularity = 8192;

-- 查询指定分区条件, 触发分区裁剪只扫描3月数据
SELECT count(DISTINCT user_id) FROM user_profile_wide
WHERE dt = '2024-03-01' AND city = '北京' AND age BETWEEN 25 AND 35;
```

**主键索引**

ORDER BY定义了稀疏索引（每8192行一个索引标记），低基数列放前面、高基数列放后面。查询必须匹配前缀才能利用索引。

**跳数索引（Data Skipping Index）**

```sql
ALTER TABLE user_profile_wide
ADD INDEX idx_consume consume_level TYPE set(100) GRANULARITY 4;  -- 低基数枚举
ALTER TABLE user_profile_wide
ADD INDEX idx_gender gender TYPE minmax GRANULARITY 4;            -- 数值/有序
ALTER TABLE user_profile_wide
ADD INDEX idx_interests interests TYPE tokenbf_v1(10240,3,0) GRANULARITY 4; -- 文本搜索
```

- minmax：记录Granule最小最大值，适合数值型
- set(N)：记录不重复值集合，适合低基数枚举
- tokenbf_v1：Token级Bloom Filter，适合文本搜索

**预聚合（物化视图）**

```sql
CREATE MATERIALIZED VIEW user_count_by_city_age
ENGINE = SummingMergeTree() ORDER BY (city, age_group, gender)
AS SELECT city, multiIf(age<18,'未成年',age<25,'18-24',
    age<35,'25-34',age<45,'35-44','45+') AS age_group,
    gender, count() AS user_count
FROM user_profile_wide GROUP BY city, age_group, gender;
```

热门圈选维度组合预计算，查询快几十倍。

**SAMPLE采样**

```sql
-- 预览阶段: 10%采样快速估算, 误差通常<5%
SELECT count() * 10 AS estimated_count FROM user_profile_wide
SAMPLE 0.1 WHERE city = '北京' AND age BETWEEN 25 AND 35;
```

交互体验亚秒级，确认条件后再全量精确查询。

### 3.3 在线查询优化

**异步并行多源查询**

```java
public UserProfile queryProfile(long userId) {
    CompletableFuture<Map<String,String>> basicF =
        supplyAsync(() -> queryBasicTags(userId), queryExecutor);
    CompletableFuture<Map<String,String>> behaviorF =
        supplyAsync(() -> queryBehaviorTags(userId), queryExecutor);
    CompletableFuture<Map<String,String>> realtimeF =
        supplyAsync(() -> queryRealtimeTags(userId), queryExecutor);

    try {
        CompletableFuture.allOf(basicF, behaviorF, realtimeF)
            .get(8, TimeUnit.MILLISECONDS);  // 总超时8ms
    } catch (TimeoutException e) {
        log.warn("部分查询超时, userId={}", userId);
    }
    // 合并已完成的结果, 未完成的用默认值
    UserProfile profile = new UserProfile(userId);
    mergeIfDone(profile, basicF);
    mergeIfDone(profile, behaviorF);
    mergeIfDone(profile, realtimeF);
    return profile;
}
```

**超时降级**

```java
// 系统高负载时启用降级模式
boolean degraded = systemLoadMonitor.isHighLoad();

if (degraded) {
    return queryCoreTags(userId, timeout);  // 只查核心标签

    return queryAllTags(userId, timeout);   // 查全量标签
}
```

标签优先级：CORE(年龄/性别/城市 必须返回) > IMPORTANT(消费能力/兴趣 尽量返回) > AUXILIARY(设备/渠道 可降级)

**Request Merging（请求合并）**

按时间窗口收集多个不同用户的查询，合并为一次批量查询：

```java
public class BatchRequestMerger {
    private final BlockingQueue<QueryRequest> requestQueue = new LinkedBlockingQueue<>();

    @Scheduled(fixedDelay = 2)  // 每2ms收集一批
    public void processBatch() {
        List<QueryRequest> batch = new ArrayList<>();
        requestQueue.drainTo(batch, 100);  // 最多100个
        if (batch.isEmpty()) return;

        List<Long> userIds = batch.stream().map(QueryRequest::getUserId)
            .distinct().collect(Collectors.toList());
        Map<Long, UserProfile> results = batchQuery(userIds);

        batch.forEach(req -> req.getFuture().complete(results.get(req.getUserId())));
    }
}
```

## 四、Bitmap性能优化

### 4.1 RoaringBitmap深入

**原理**

传统Bitmap：1亿用户需要12.5MB，但稀疏标签（如VIP只有100万人）大部分bit为0，浪费空间。

RoaringBitmap解决方案：
- 将32位整数空间分为高16位（容器索引，最多65536个容器）和低16位（容器内存储）
- 每个容器根据元素数量自动选择最优存储方式

容器类型：
- **ArrayContainer**：元素<4096个，有序short数组，空间=元素数x2字节
- **BitmapContainer**：元素>=4096个，固定8KB位图
- **RunContainer**：连续分布时用(start,length)对编码，空间=区间数x4字节

**画像圈选使用**

```

public class DoubleBufferBitmapStore {

    private Map<String, RoaringBitmap> standbyBuffer;

        return activeBuffer.getOrDefault(tagKey, new RoaringBitmap());

    public void rebuild(Map<String, RoaringBitmap> newBitmaps) {

        warmUp(standbyBuffer);            // 预热

    }
}
```

### 6.1 GC选择

| 服务类型 | GC选择 | 核心参数 | 选择原因 |
|---------|--------|---------|---------|
| 在线查询 | ZGC | `-XX:+UseZGC -Xms16g -Xmx16g -XX:SoftMaxHeapSize=14g` | 停顿<1ms不影响P99 |
| 批量查询 | G1 | `-XX:+UseG1GC -Xms32g -XX:MaxGCPauseMillis=200 -XX:G1HeapRegionSize=16m` | 延迟宽松吞吐优先 |
| Bitmap计算 | Parallel | `-XX:+UseParallelGC -Xms48g -XX:ParallelGCThreads=8` | 计算密集最大吞吐 |

### 6.2 内存规划（在线查询16GB堆）

```
Young Generation (5GB)
  ├── Eden (4GB) — 画像查询临时对象
  ├── S0 (512MB)
  └── S1 (512MB)
Old Generation (11GB)
  ├── 本地缓存 (3GB) — Caffeine
  ├── 连接池对象 (1GB)
  └── 其他长生命周期 (7GB)
Metaspace (512MB) — 类元数据
堆外内存 (4GB) — -XX:MaxDirectMemorySize=4g
  ├── Netty DirectBuffer (2GB)
  ├── Redis客户端Buffer (1GB)
  └── 其他NIO Buffer (1GB)
```

### 6.3 常见GC问题

**Full GC频繁**

排查：`-Xlog:gc*:file=gc.log` 查看GC日志，`jmap -histo:live <pid>` 查看对象分布
原因：本地缓存过大撑满Old区 / 大对象直接进Old区 / 内存泄漏
解决：控制缓存大小Old区<70%、大结果集分页处理、WeakReference包装非核心缓存

**Young GC过长**

原因：Eden区过大单次扫描对象多 / 存活对象过多
解决：减小Eden区增加频率降低单次时间 / 切换ZGC

**堆外内存OOM**

排查：`-XX:NativeMemoryTracking=summary`，`jcmd <pid> VM.native_memory summary`
原因：Netty ByteBuf未释放 / JNI内存泄漏
解决：`-Dio.netty.leakDetection.level=paranoid` 检测泄漏，设置MaxDirectMemorySize限制

## 七、线程模型优化

### 7.1 请求处理线程模型

```
客户端请求 → Netty IO线程(EventLoop, 8线程)
           → 业务线程池(处理逻辑, 64-128线程)
           → 并行查询线程池(128-256线程)
              ├→ Redis查询
              ├→ HBase查询
              └→ 实时标签查询
                    ↓
              结果聚合 → 响应编码 → 客户端
```

关键原则：IO线程不做业务逻辑只做编解码转发，避免阻塞影响所有连接。

### 7.2 线程池配置

```java
// 业务线程池（IO密集型）
ThreadPoolExecutor bizExecutor = new ThreadPoolExecutor(
    64, 128, 60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(10000),
    new NamedThreadFactory("biz-"),
    new CallerRunsPolicy());  // 拒绝策略: 调用者执行, 天然限流

// 并行查询线程池
ThreadPoolExecutor queryExecutor = new ThreadPoolExecutor(
    128, 256, 30, TimeUnit.SECONDS,
    new SynchronousQueue<>(),    // 不排队直接创建新线程
    new NamedThreadFactory("query-"),
    new AbortPolicy());          // 拒绝策略: 抛异常触发降级
```

### 7.3 CompletableFuture编排

```java
public CompletableFuture<UserProfile> queryAsync(long userId) {
    long start = System.currentTimeMillis();

    return supplyAsync(() -> queryCache(userId), queryExecutor)
        .orTimeout(2, MILLISECONDS)
        .exceptionally(e -> CacheResult.miss())
        .thenComposeAsync(cache -> {
            if (cache.isHit()) return completedFuture(cache.getProfile());

            // 并行查多源, 每个带独立超时和异常降级
            var f1 = queryBasicAsync(userId);    // 5ms超时, 异常返回空
            var f2 = queryBehaviorAsync(userId);
            var f3 = queryRealtimeAsync(userId);

            return allOf(f1, f2, f3)
                .orTimeout(remainingTimeout(start), MILLISECONDS)
                .handleAsync((v, ex) -> {
                    UserProfile p = mergeResults(userId, f1, f2, f3);
                    asyncFillCache(userId, p);  // 异步回填缓存
                    return p;
                }, queryExecutor);
        }, queryExecutor);
}
```

### 7.4 线程池参数调优

核心原则：
- IO密集型：核心线程数 = CPU核数 x 2~4（实际通过压测确定）
- 队列选择：SynchronousQueue（快速处理）vs LinkedBlockingQueue（平滑突发）
- 拒绝策略：CallerRunsPolicy（天然限流）vs AbortPolicy（触发降级）

## 九、面试高频问题与参考回答

### 问题1：系统QPS是多少？怎么一步步优化上去的？

我们画像系统在线查询QPS峰值12万，P99控制在8ms以内。这个数字不是一蹴而就的，是经过四个阶段的迭代优化达到的。

最初我们的架构比较简单，应用直接查HBase，QPS只能到2万左右，P99在30ms。瓶颈主要在HBase的网络IO和磁盘IO上。

第一步引入Redis缓存。用Hash结构缓存活跃用户的画像数据，命中率做到95%以上。这一步让QPS直接翻了三倍，到6万。因为大部分请求在Redis就返回了，不需要再走HBase。

第二步加Caffeine本地缓存。在JVM进程内缓存最热的50万用户画像，命中率约50%。本地缓存的访问延迟是微秒级的，几乎不占用网络资源。这一步让P99从12ms降到8ms以下，QPS到8万。

第三步是查询链路优化。我们的画像数据分布在多个数据源（基础标签、行为标签、实时标签），原来是串行查询的。改成CompletableFuture并行查询后，单次查询延迟从多个数据源的RT之和变成了最大RT。同时加了超时降级，总超时控制在8ms，超时的数据源返回默认值。这让QPS进一步到10万以上。

最后是JVM和基础设施优化。从G1切换到ZGC消除了GC停顿导致的毛刺，线程池参数通过多轮压测反复调优。最终稳定在12万QPS，P99在8ms。

### 问题2：缓存怎么设计的？为什么多级缓存？

我们采用三级缓存：L1本地Caffeine、L2 Redis Cluster、L3 HBase。

选择多级缓存的根本原因是延迟预算非常紧张。P99要求10ms以内，单靠Redis的网络往返就要2-3ms，再加上序列化反序列化和业务处理，留给数据获取的时间很少。Caffeine的访问延迟在微秒级，能把40-50%的请求在进程内就解决掉，极大缓解了Redis的压力和延迟。

Caffeine配置了50万条容量、30秒过期、20秒异步刷新。选Caffeine不选Guava Cache，是因为它基于W-TinyLfu淘汰算法，在各种工作负载下的命中率都是最优的。

Redis用Hash结构存画像，每个字段对应一个标签。Hash的好处是支持按字段读写，标签更新时HSET只写变化的字段就行。另外当字段数少于128且单值小于64字节时，Redis内部用ziplist编码，内存效率很高。

更新策略用Cache Aside模式。写操作先更新HBase再删Redis缓存。这里强调"删除"而非"更新"缓存，因为删除是幂等操作。如果用更新的话，两个并发写操作可能导致缓存里存的是旧值——线程A写1、线程B写2，但因为网络延迟，缓存最终可能变成1。删除就没有这个问题。

### 问题3：缓存一致性怎么保证？

我们采用最终一致性方案，因为画像数据本身有一定的时效容忍度，不需要强一致性。

具体做法是三重保障。第一重是主动失效：写操作时先更新HBase，然后删除Redis缓存，再通过MQ广播缓存失效事件通知各服务实例清除本地Caffeine缓存。

第二重是延迟双删，防止极端并发场景下的不一致。场景是：线程A读缓存未命中去查DB得到旧值V1，这时线程B更新了DB为V2并删了缓存，然后线程A用旧值V1回填缓存。解决方案是更新DB后立即删缓存，然后延迟500ms再删一次，把线程A可能回填的旧数据清掉。

第三重是TTL兜底：Redis缓存设置5-10分钟的TTL，本地Caffeine设置30秒TTL。即使MQ消息丢失、延迟双删也失败了，数据最坏也只会不一致这么长时间。

另外我们还有一个定时对账任务，每天凌晨抽样对比Redis和HBase的数据，发现不一致就主动修复并告警。监控上看缓存命中率和对账差异率两个指标。

### 问题4：HBase查询性能怎么优化的？

HBase优化我们做了系统性的工作，主要从五个方面入手。

第一是RowKey设计。我们将userId反转后加上盐值前缀作为RowKey。反转是因为原始userId是递增的，会导致写入和查询集中在最新的几个Region上形成热点。反转后分布更均匀。盐值前缀是hash(userId)%16，配合预分区创建16个Region，保证数据从一开始就是均衡分布的。

第二是查询方式优化。单用户查询用Get，批量查询用MultiGet。MultiGet的好处是HBase客户端会自动按Region分组并行发送RPC请求。同时我们严格指定了需要的列族和列，避免读取不需要的数据增加传输量。

第三是存储层优化。开启了ROW级别的Bloom Filter，让HBase在读取前就能快速判断某个RowKey是否在某个HFile中，避免无效的磁盘IO。

第四是缓存层优化。配置了堆内LRU缓存存放索引块和元数据块，堆外BucketCache 8GB存放数据块。画像是读多写少场景，BlockCache命中率保持在85%以上。

第五是Compaction管理。关闭了自动Major Compaction，改为凌晨3-5点通过定时任务手动触发。这样避免了白天高峰期的IO抖动。另外还启用了HDFS短路读，当RegionServer和DataNode在同一台机器上时直接读本地文件。

### 问题5：ClickHouse圈选怎么做到秒级？

圈选要在亿级用户中按标签组合筛选，做到秒级需要多层优化。

首先是表设计。我们用MergeTree引擎，按月分区，ORDER BY按城市、年龄、用户ID排序。这样设计的好处是：查询中指定了日期条件就能触发分区裁剪，只扫描对应月份的数据；城市和年龄是最常见的圈选条件，放在排序键前面能充分利用稀疏索引。

对于不在排序键中但经常用作过滤条件的字段，我们创建了跳数索引。消费等级这种低基数枚举字段用set索引，性别用minmax索引，兴趣标签这种文本字段用tokenbf_v1索引。

对于热门的圈选维度组合，我们建了物化视图做预聚合。比如按城市、年龄段、性别的组合统计，直接查物化视图比查原始表快几十倍。

还有一个很实用的优化是SAMPLE采样。在运营人员调整圈选条件的"预览"阶段，用10%采样快速返回估算结果，交互体验可以做到亚秒级。误差通常在5%以内，对于调参阶段完全够用。确认条件后再执行全量精确查询。

最后ClickHouse集群是独立部署的，与在线查询完全隔离，大量扫描不会影响在线服务。

### 问题6：Bitmap在人群圈选怎么用？

我们的Bitmap方案是为每个标签值维护一个RoaringBitmap，Bitmap中的每个bit位对应一个userId。圈选操作就转化为多个Bitmap的集合运算，比如"北京且25-34岁且高消费"就是三个Bitmap做AND运算。

选择RoaringBitmap而非传统Bitmap，核心是空间效率。传统Bitmap不管人群大小都占12.5MB（1亿用户），而RoaringBitmap根据数据密度自动选择存储方式。稀疏标签（如VIP 100万人）用ArrayContainer，只需约2MB。密集标签（如性别-男 5000万人）用BitmapContainer固定8KB一个容器。连续ID分布用RunContainer行程编码更加紧凑。

数据流方面，Flink每小时全量构建所有标签的Bitmap。上线采用双Buffer切换策略：备用Buffer在后台构建新Bitmap数据，构建完成后通过volatile变量原子切换为活跃Buffer，整个过程对在线查询完全无感知。切换前还会做预热，包括遍历触发内存页加载和预执行热门组合。

分布式计算方面，我们按用户ID分片。10个计算节点，每个负责1000万用户的所有标签Bitmap。圈选查询广播到所有节点，各节点在本地完成完整的Bitmap运算得到局部结果，协调节点只汇总各节点的计数。这样避免了大量Bitmap数据在网络上传输，而且可以线性扩展节点数量。

### 问题7：系统可用性怎么保证？

可用性保障是多层次的，我们目标是99.99%。

架构层面，三个场景（在线查询、批量查询、圈选）独立集群部署，互不影响。每个集群都是多实例无单点，跨三个可用区部署，任何一个可用区故障都能正常服务。

缓存层面，多级缓存形成了天然的降级链。Redis全挂了本地Caffeine缓存还能撑住40-50%的流量。如果某个用户的缓存全过期了，还有HBase兜底。最差情况返回默认画像，不会返回错误。

熔断方面，我们对HBase、Redis等每个下游依赖都配置了Resilience4j断路器。失败率超过50%时自动触发熔断，直接走降级逻辑不再等待超时。10秒后半开状态放少量请求探测，恢复正常后自动关闭熔断。这样一个下游出问题不会拖垮整个服务。

限流方面，每个业务方有独立的QPS配额。推荐系统5万、广告系统2万、营销系统5千。超出配额直接返回限流响应，保护核心链路。

降级分四个级别，从只裁剪辅助标签到完全返回默认画像，根据实时指标自动判定和切换。

灰度发布保证上线安全，先1-2台机器观察QPS、RT、错误率、缓存命中率等核心指标，无异常再逐步扩大。

### 问题8：限流降级怎么实现的？

我们使用Sentinel作为限流降级框架，配合公司内部的配置中心做规则的动态下发和调整。

限流维度有三层。第一层是系统总QPS限流，保护服务整体不被打垮。第二层是按业务方限流，通过请求头中的appKey识别调用方，每个业务方有独立的QPS配额。第三层是按查询类型限流，圈选查询和导出查询的QPS上限远低于单用户查询，因为它们的资源消耗大得多。

降级也是分级的。Level 1只裁剪设备信息、渠道信息等辅助标签。Level 2只返回年龄、性别、城市等核心标签。Level 3返回过期的缓存数据，即使已经超过TTL也返回旧数据。Level 4返回系统默认画像。级别根据QPS、RT、缓存命中率、下游DB响应时间等指标实时计算。

举一个实际的例子。去年双11期间，推荐系统的QPS突增到平时的5倍。我们的限流策略及时生效，按优先级把营销系统和数据分析的流量降级到Level 2和Level 3，腾出的容量保住了推荐和广告两个核心链路。整个过程是自动的，核心业务方完全无感知。双11结束后流量回落，限流和降级自动恢复正常。

### 问题9：JVM做了哪些调优？

我们针对不同类型的画像服务做了差异化的JVM调优。

在线查询服务对延迟最敏感，我们从G1迁移到了ZGC。G1的Mixed GC偶尔会产生50-100ms的停顿，直接导致P99不稳定，时好时坏。切换到ZGC后GC停顿基本控制在1ms以内，P99从15ms稳定到了8ms以下。堆大小配16GB，SoftMaxHeapSize设为14GB让ZGC有足够的空间做并发回收。ZGC的好处是几乎不需要调优，开箱即用。

批量查询服务用的G1，因为延迟要求宽松（秒级），G1的吞吐量更高。MaxGCPauseMillis设200ms，堆32GB。

内存规划上有几个要点：本地缓存大小控制在堆的20%以内（3GB左右），避免Old区压力过大。堆外内存用MaxDirectMemorySize限制为4GB，主要给Netty和Redis客户端的DirectBuffer用。

遇到过一个具体问题：上线一个新版本后发现Full GC频繁。通过jmap histo分析发现是一个新接口每次查询返回大量数据（上万个用户的完整画像），大对象超过了G1HeapRegionSize的一半直接分配到Old区。解决方案是对查询结果做分页限制，单次最多返回1000个用户。同时增大G1HeapRegionSize到16MB让更多对象走正常的Young GC路径。

### 问题10：线上性能问题怎么排查？

印象最深的一次是某天下午突然收到告警，在线查询P99从8ms飙升到50ms以上。

第一步看监控大盘。发现QPS没有明显变化，排除了流量突增。看RT曲线是跳跃式抖动而不是持续升高，初步怀疑GC问题。

第二步看GC监控。果然Young GC频率从每秒2次变成了每秒5次，而且单次时间从10ms增加到了30ms。这就能解释P99的抖动了。

第三步定位原因。用jstat看堆内存，Eden区几乎一直是满的，而且每次GC后存活对象比例异常高（从正常的5%变成了20%）。这说明有大量对象存活时间变长了。

第四步用arthas的dashboard和thread命令排查。发现有个接口的调用量异常，是一个批量导出接口，一次查询1万个用户的全量画像。这个接口本应走批量查询集群，但被运维同事配路由时配错了地址，打到了在线查询集群。每次请求创建的大量临时对象占满了Eden区。

紧急处理：在网关层封禁了这个误配的路由规则，P99立刻恢复到正常水平。

后续改进措施：第一，加强接入层的流量隔离检查，对请求做特征分析（如单次请求的用户数量），异常请求自动拦截。第二，增加了单请求数据量限制。第三，在网关层增加了异常流量模式的自动识别和告警。

### 问题11：批量查询百万级怎么优化？

批量查询百万级用户画像的核心挑战是平衡吞吐量和对在线服务的影响。

第一个关键点是存储层隔离。批量查询走HBase的离线读副本，和在线查询完全隔离。这样大量扫描不会把在线集群的BlockCache挤掉，也不会抢占在线服务的IO带宽。

第二个关键点是分批并行。100万用户分成1000个batch，每个batch 1000个用户用MultiGet查询。用16-32个线程并行执行多个batch。线程数不是越多越好，过多会对HBase RegionServer产生过大压力。

第三个优化细节是按RowKey排序后分批。让同一个Region的请求尽量集中在同一个batch中，这样RegionServer可以做顺序IO而不是随机IO，吞吐量能提升不少。

第四是限速。批次之间有简单的限速逻辑，通过令牌桶控制每秒最多发出多少个batch请求。如果HBase离线集群的负载已经较高就主动降速。

第五是流式处理。不是等1000个batch全查完再处理，而是每完成一个batch就立即通过回调处理结果，避免内存中同时持有大量画像数据。

经过这些优化，100万用户画像的批量查询可以在20-30秒内完成，同时对在线服务几乎零影响。

### 问题12：容量规划怎么做？

容量规划我们从三个维度来做估算。

存储容量方面：1亿用户，平均50个标签，每个标签约30字节。HBase原始数据量约150GB，乘以3副本是450GB，再考虑HBase的存储放大系数1.5倍（Compaction、WAL等开销），需要约675GB的HDFS存储。Redis缓存按照20%活跃用户估算，2000万用户乘以1.5KB等于30GB，加上碎片和主从约72GB。

计算容量方面：根据压测数据，32核64GB的机器单机可以承载3000-4000 QPS的在线查询。目标12万QPS需要30-40台机器。考虑到容灾冗余——我们要求任何一个可用区挂掉后剩余两个可用区仍能撑住全量流量——所以需要60台机器分布在3个可用区，每个可用区20台。

带宽容量方面：单次请求约200字节，响应约500字节。12万QPS的带宽需求是请求24MB/s加响应60MB/s，共84MB/s。千兆网卡可以承受，但我们用的万兆网卡预留了足够的突发空间。

我们还建立了容量预警机制：CPU使用率超过70%或内存超过80%就告警，超过80%或90%触发扩容流程。每季度做一次容量评审，根据业务增长预测提前采购资源。

### 问题13：缓存穿透怎么防？

缓存穿透在画像系统中是实际存在的问题，比如新注册但还没有画像的用户、被注销的账号、恶意构造的不存在userId等。

我们设计了三道防线。第一道是Bloom Filter，用了Guava的实现，1亿容量、0.01%误判率，内存约1.92GB。每次查询先过Bloom Filter，判定不存在就直接返回空画像。Bloom Filter每天凌晨全量重建一次，新注册用户在写入画像时同步添加。因为不支持删除，注销用户在下次重建时自然消失。

第二道是空值缓存。如果一个userId通过了Bloom Filter但在HBase中确实查不到（Bloom Filter有0.01%的误判率，或者画像数据还没有生成），我们在Redis中缓存一个空值标记，TTL设为30秒。这样同一个不存在的用户在30秒内只会穿透一次。

第三道是请求校验。在API网关层对userId做基本格式校验，比如必须是正整数、不能超过合理范围等，过滤掉明显非法的请求。

实际效果：上线Bloom Filter后，穿透到HBase的无效请求降低了95%以上。

### 问题14：压测怎么做？有什么发现？

压测是我们上线前的必要环节，也是容量规划和参数调优的核心依据。

环境方面，我们有独立的压测环境，机器配置和生产一致。数据从生产导入脱敏数据，数据量完全一致。压测前先做缓存预热模拟真实运行状态。

流量方面，我们录制了一周的线上流量，按不同时段的QPS分布进行回放。比均匀加压更能反映真实情况，因为线上的热点用户分布、标签访问模式都是不均匀的。

场景设计了五类。性能基准测试从100QPS逐步加压到15万QPS找到极限。稳定性测试在目标QPS的80%持续运行2小时观察是否有劣化。混合场景测试在线10万QPS加批量500QPS同时运行。故障注入测试模拟Redis宕机和HBase慢响应验证降级策略。容量预估测试在不同机器数量下测试能承载的QPS。

关键发现有几个值得分享。一是缓存命中率对性能的影响是非线性的：Redis命中率从95%降到85%时P99从8ms飙到30ms，因为穿透到HBase的请求量翻了三倍。二是线程池大小不是越大越好：从64增加到256后上下文切换开销剧增导致P99反而上升。最终通过多轮压测确定64-128是最优区间。三是ZGC在16GB堆下停顿远优于G1（1ms vs 50ms），但在32GB以上两者差距缩小。

### 问题15：从零设计10万QPS画像查询服务？

如果让我从零设计，我会分五个层次来规划。

第一层是存储选型。核心画像存储选HBase，因为它支持按userId的毫秒级点查，支持列级别的读写，和标签模型天然匹配。人群圈选选ClickHouse做分析查询，同时自建RoaringBitmap服务做实时集合运算。

第二层是缓存设计。三级缓存架构：Caffeine做L1热点数据进程内缓存，Redis Cluster做L2分布式缓存承载95%以上的查询，HBase做L3兜底存储。缓存更新用Cache Aside加延迟双删加TTL兜底的组合方案。

第三层是服务架构。按场景做物理隔离，在线查询、批量查询、圈选查询独立集群。在线查询集群用ZGC消除GC停顿，用CompletableFuture做多数据源并行查询，配合分层超时和按标签优先级的降级策略。

第四层是服务治理。接入层按业务方限流，服务层用Sentinel加Resilience4j做限流熔断降级，对每个下游依赖都配置断路器和超时控制。灰度发布保证上线安全。

第五层是容量和监控。以单机3500QPS估算，10万QPS需30台，3可用区容灾共60台。Redis 12节点，HBase 20节点。监控覆盖QPS、RT、缓存命中率、GC、线程池全部核心指标，Prometheus加Grafana做可视化，配合完善的告警规则。

整套架构先在压测环境验证，然后灰度上线，根据实际数据持续调优。
