## 1. 分布式 Bitmap 计算深度解析

### 1.1 为什么需要分布式 Bitmap

```
单机瓶颈分析（1亿用户、200个枚举标签、平均每标签5个取值 = 1000个Bitmap）：

内存需求：
  每个 RoaringBitmap 平均 5-10MB（取决于数据密度）
  1000 个 Bitmap × 8MB ≈ 8GB
  加上双 Buffer → 16GB
  加上 JVM 其他开销 → 需要 24-32GB 堆内存

计算瓶颈：
  单次圈选 3 个 AND 条件：~50ms
  但如果同时有 50 个并发圈选请求：
  50 × 50ms = 2500ms（串行情况下）
  即使用线程池并行，CPU 也会成为瓶颈
  Bitmap AND/OR 运算是 CPU 密集型操作

当用户量增长到 2-5 亿时：
  内存需求翻倍 → 单机 64GB 堆也撑不住
  计算时间线性增长 → 单次圈选可能 200ms+
  → 必须走分布式
```

### 1.2 分片策略对比与选择

```
方案一：按标签分片
  节点1: gender=男, gender=女, age=18-24, age=25-34, ...
  节点2: city=北京, city=上海, city=广州, ...
  节点3: consume_level=高, consume_level=中, ...

  圈选 "北京 AND 高消费 AND 男"：
    ① 从节点2获取 city=北京 的 Bitmap（~10MB 网络传输）
    ② 从节点3获取 consume_level=高 的 Bitmap（~8MB 网络传输）
    ③ 从节点1获取 gender=男 的 Bitmap（~6MB 网络传输）
    ④ 协调节点做 AND 运算

  问题：
    网络传输量巨大（每次圈选传输 20-30MB Bitmap 数据）
    协调节点成为计算瓶颈（所有 AND/OR 运算集中在一个节点）
    标签数量增长时节点负载不均（热门标签如 city 数据量远大于冷门标签）

方案二：按用户 ID 分片（推荐）
  节点1: userId 0~999万 的所有标签 Bitmap
  节点2: userId 1000万~1999万 的所有标签 Bitmap
  ...
  节点10: userId 9000万~9999万 的所有标签 Bitmap

  圈选 "北京 AND 高消费 AND 男"：
    ① 广播查询条件到所有 10 个节点（传输量 ~1KB）
    ② 每个节点在本地执行完整的 Bitmap AND 运算
    ③ 每个节点返回局部计数（传输量 ~8B × 10 = 80B）
    ④ 协调节点汇总：总人数 = Σ(各节点计数)

  优势：
    网络传输量极小（条件文本 + 数字结果）
    计算完全并行（10个节点同时计算）
    线性可扩展（用户量翻倍，节点数翻倍即可）
    协调节点零计算压力（只做简单加法）
```

**方案对比量化分析：**

| 维度 | 按标签分片 | 按用户 ID 分片 |
|------|-----------|---------------|
| 单次圈选网络传输量 | 20-50MB（传 Bitmap） | < 1KB（传条件+计数） |
| 协调节点 CPU 开销 | 高（执行 Bitmap AND/OR） | 极低（数字求和） |
| 节点间延迟影响 | 大（传输 Bitmap 受带宽限制） | 小（只传数字） |
| 水平扩展方式 | 加标签分片节点（不均匀） | 加用户分片节点（均匀） |
| 单节点故障影响 | 某些标签不可用 | 部分用户数据不可用 |
| 适合场景 | 标签数极少但用户量极大 | 通用场景（推荐） |

### 1.4 协调节点实现

```java
/**
 * 分布式 Bitmap 圈选协调器
 *
 * 核心职责：
 *   1. 将圈选条件广播到所有分片节点
 *   2. 收集各节点的局部结果
 *   3. 处理超时和故障节点
 *   4. 汇总返回最终结果
 */
public class DistributedBitmapCoordinator {

    private final List<BitmapShardClient> shardClients;   // 各分片节点的 RPC 客户端
    private final int totalShards;                         // 总分片数
    private final long shardTimeoutMs = 500;              // 单分片超时
    private final long totalTimeoutMs = 800;              // 总超时

    /**
     * 执行分布式圈选预估
     */
    public EstimateResult distributedEstimate(CrowdCondition condition) {
        long startTime = System.currentTimeMillis();

        // 1. 并行广播到所有分片
        List<CompletableFuture<ShardResult>> futures = new ArrayList<>();
        for (BitmapShardClient client : shardClients) {
            CompletableFuture<ShardResult> future = CompletableFuture
                .supplyAsync(() -> client.localEstimate(condition))
                .orTimeout(shardTimeoutMs, TimeUnit.MILLISECONDS)
                .exceptionally(ex -> {
                    // 单节点失败不影响整体，记录失败分片
                    log.warn("Shard {} failed: {}", client.getShardId(), ex.getMessage());
                    return ShardResult.failed(client.getShardId());
                });
            futures.add(future);
        }

        // 2. 等待所有结果（带总超时）
        CompletableFuture<Void> allDone = CompletableFuture.allOf(
            futures.toArray(new CompletableFuture[0]));
        try {
            long remaining = totalTimeoutMs - (System.currentTimeMillis() - startTime);
            allDone.get(Math.max(remaining, 0), TimeUnit.MILLISECONDS);
        } catch (TimeoutException e) {
            log.warn("Distributed estimate timed out, using partial results");
        } catch (Exception e) {
            log.error("Distributed estimate error", e);
        }

        // 3. 汇总结果
        return aggregateResults(futures);
    }

    /**
     * 结果汇总与补偿
     *
     * 核心逻辑：
     *   如果所有分片都成功 → 精确结果
     *   如果部分分片失败 → 用成功分片的结果做外推补偿
     *   如果超过一半分片失败 → 降级到 ClickHouse
     */
    private EstimateResult aggregateResults(List<CompletableFuture<ShardResult>> futures) {
        long totalCount = 0;
        int successCount = 0;
        int failedCount = 0;
        List<Integer> failedShards = new ArrayList<>();

        for (CompletableFuture<ShardResult> future : futures) {
            ShardResult result = future.getNow(ShardResult.unknown());
            if (result.isSuccess()) {
                totalCount += result.getCount();
                successCount++;
            } else {
                failedCount++;
                failedShards.add(result.getShardId());
            }
        }

        // 超过一半分片失败 → 结果不可信，降级
        if (failedCount > totalShards / 2) {
            return EstimateResult.degraded("Too many shards failed, fallback to ClickHouse");
        }

        // 有部分失败 → 外推补偿
        if (failedCount > 0) {
            // 假设用户在各分片均匀分布（因为是按 userId hash 分片的）
            // 补偿公式：总数 ≈ 成功分片总数 × (总分片数 / 成功分片数)
            double compensated = (double) totalCount * totalShards / successCount;
            return EstimateResult.approximate(
                Math.round(compensated),
                failedShards,
                "Compensated for " + failedCount + " failed shards"
            );
        }

        // 全部成功 → 精确结果
        return EstimateResult.exact(totalCount);
    }
}
```

### 1.5 分片节点实现

```java
/**
 * Bitmap 分片节点
 *
 * 每个节点持有一段用户 ID 范围内所有标签的 RoaringBitmap
 * 例如：节点1 持有 userId 0~2000万 的全部标签 Bitmap
 */
public class BitmapShardNode {

    private final int shardId;
    private final long userIdStart;   // 本分片用户 ID 起始值
    private final long userIdEnd;     // 本分片用户 ID 结束值

    // 双 Buffer 存储
    private volatile BitmapStore activeStore;
    private BitmapStore standbyStore;

    /**
     * 本地执行圈选
     *
     * 在本分片的用户范围内，执行完整的 Bitmap AND/OR 运算
     */
    public ShardResult localEstimate(CrowdCondition condition) {
        BitmapStore store = activeStore;  // volatile 读，获取当前活跃版本
        RoaringBitmap result = evaluate(condition, store);
        return ShardResult.success(shardId, result.getLongCardinality());
    }

    /**
     * 递归求值条件树
     */
    private RoaringBitmap evaluate(CrowdCondition condition, BitmapStore store) {
        if (condition instanceof LogicCondition) {
            LogicCondition logic = (LogicCondition) condition;
            List<RoaringBitmap> childResults = logic.getChildren().stream()
                .map(child -> evaluate(child, store))
                .collect(Collectors.toList());

            if (logic.getOperator() == LogicOp.AND) {
                return fastAnd(childResults);
            } else {
                return fastOr(childResults);
            }
        } else {
            TagCondition tag = (TagCondition) condition;
            return store.getBitmap(tag.getTagKey());
        }
    }

    /**
     * 优化的 AND 运算：先做小 Bitmap 的交集，再与大 Bitmap 求交集
     *
     * 原理：AND 运算结果集不会比任何一个输入大
     *       先让小集合做 AND 得到更小的中间结果
     *       再与大集合做 AND 可以减少扫描量
     */
    private RoaringBitmap fastAnd(List<RoaringBitmap> bitmaps) {
        // 按基数从小到大排序
        bitmaps.sort(Comparator.comparingLong(RoaringBitmap::getLongCardinality));

        RoaringBitmap result = bitmaps.get(0).clone();
        for (int i = 1; i < bitmaps.size(); i++) {
            result.and(bitmaps.get(i));
            // 提前终止：如果中间结果已经为空，不需要继续 AND
            if (result.isEmpty()) {
                return result;
            }
        }
        return result;
    }

    /**
     * OR 运算：直接合并（无法提前终止）
     */
    private RoaringBitmap fastOr(List<RoaringBitmap> bitmaps) {
        return RoaringBitmap.or(bitmaps.toArray(new RoaringBitmap[0]));
    }
}
```

### 1.6 双 Buffer 切换详细流程

```
双 Buffer 切换的目标：Bitmap 数据更新时，对在线查询零影响

  T+0 03:30  Spark 输出 Bitmap 文件到 HDFS
  T+0 03:35  触发 Bitmap 加载任务

  ┌──────────────────────────────────────────────────────────┐
  │ 步骤一：加载到 standby buffer                              │
  │                                                            │
  │   主线程持续使用 active buffer 服务查询                       │
  │   后台线程从 HDFS/Redis 加载新 Bitmap 到 standby buffer      │
  │                                                            │
  │   active  → [v1 Bitmap 数据] ← 查询使用这个                  │
  │   standby → [v2 Bitmap 数据正在加载...]                      │
  └──────────────────────────────────────────────────────────┘

  T+0 03:40  所有节点加载完成

  ┌──────────────────────────────────────────────────────────┐

  │                                                            │
  │   每个节点加载完成后在 ZK 注册：                               │
  │     /bitmap/v2/ready/shard-0 ✓                              │

  │     /bitmap/v2/ready/shard-2 ✓                              │

  ┌──────────────────────────────────────────────────────────┐
  │ 步骤三：原子切换                                            │
  │                                                            │
  │   所有节点收到 ZK Watch 事件后：                              │
```

```java
/**
 * 双 Buffer Bitmap 存储
 *
 * 设计要点：
 *   1. volatile 保证可见性：一个线程的切换对所有线程立即可见
 *   2. 引用切换是原子操作：Java 引用赋值天然原子
 *   3. 延迟清理保证安全：正在执行的查询不受影响
 */
public class DoubleBufferBitmapStore {

    // volatile 保证多线程可见性
    private volatile BitmapStore activeStore;
    private volatile BitmapStore standbyStore;

    // 版本追踪
    private volatile String activeVersion;
    private final ReadWriteLock switchLock = new ReentrantReadWriteLock();

    /**
     * 查询入口：始终读 active store
     */
    public RoaringBitmap getBitmap(String tagKey) {
        return activeStore.get(tagKey);
    }

    public String getActiveVersion() {
        return activeVersion;
    }

    /**
     * 后台线程：加载新版本到 standby
     */
    public void loadNewVersion(String version, Map<String, byte[]> serializedBitmaps) {
        BitmapStore newStore = new BitmapStore();

        // 反序列化所有 Bitmap（耗时操作，在后台完成）
        for (Map.Entry<String, byte[]> entry : serializedBitmaps.entrySet()) {
            RoaringBitmap bitmap = new RoaringBitmap();
            bitmap.deserialize(ByteBuffer.wrap(entry.getValue()));
            bitmap.runOptimize();  // 优化存储（尝试 RunContainer 压缩）
            newStore.put(entry.getKey(), bitmap);
        }

        // 预热：触发内存页加载和 JIT 编译
        warmUp(newStore);

        standbyStore = newStore;
        log.info("Standby store loaded with version {}, {} bitmaps",
                 version, serializedBitmaps.size());
    }

    /**
     * 协调指令：执行原子切换
     */
    public void switchBuffers(String newVersion) {
        BitmapStore oldActive = activeStore;
        activeStore = standbyStore;      // volatile 写 → 所有线程立即可见
        activeVersion = newVersion;
        standbyStore = null;             // 先置空，防止意外使用

        log.info("Switched to version {}", newVersion);

        // 延迟 5 分钟后释放旧版本引用
        // 等待所有正在进行的查询完成
        ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor();
        scheduler.schedule(() -> {
            // oldActive 的引用在此 lambda 执行完后释放
            // 如果没有其他引用，GC 可以回收
            log.info("Old version eligible for GC");
        }, 5, TimeUnit.MINUTES);
    }

    /**
     * 预热策略
     *
     * 目的：
     *   1. 触发操作系统内存页加载（避免切换后首次查询 page fault）
     *   2. 触发 JVM JIT 编译优化（Bitmap 运算方法被编译为机器码）
     *   3. 预计算热门组合并缓存
     */
    private void warmUp(BitmapStore store) {
        // 1. 遍历所有 Bitmap，触发内存页加载
        store.forEach((key, bitmap) -> bitmap.getLongCardinality());

        // 2. 预执行 TOP 20 热门圈选组合
        List<CrowdCondition> hotConditions = conditionStatsService.getTop20Conditions();
        for (CrowdCondition cond : hotConditions) {
            RoaringBitmap result = evaluateLocally(cond, store);
            store.cacheResult(cond.getCacheKey(), result.getLongCardinality());
        }

        // 3. 连续执行多次 AND 运算触发 JIT
        for (int i = 0; i < 100; i++) {
            RoaringBitmap.and(store.getRandomBitmap(), store.getRandomBitmap());
        }

        log.info("Warm-up completed: {} bitmaps loaded, {} hot queries cached",
                 store.size(), hotConditions.size());
    }
}
```

### 1.7 面试深度追问

**Q: 双 Buffer 切换用 volatile 够吗？需不需要加锁？**

> 够了。这里只有 **单写多读** 场景：只有一个切换线程写 active 引用，多个查询线程读。Java 语言规范保证引用赋值是原子操作，volatile 保证可见性。不需要加锁。
>
> 如果是 **多写场景**（比如多个线程同时尝试切换），则需要 CAS 或锁。但我们的设计中切换只由 ZK 协调触发，单线程执行。
>
> **进一步追问：volatile 的性能开销？**
> volatile 读的开销约等于一次 L1 Cache 访问 + 一个内存屏障，大约 1-5ns。相比 Bitmap 运算的 50ms，完全可以忽略。volatile 写的开销稍高（需要 StoreStore + StoreLoad 屏障），但切换操作每天只发生 1-2 次。

**Q: 如果 ZooKeeper 本身挂了，所有节点无法协调切换怎么办？**

> 1. **短期（<5分钟）**：所有节点继续使用当前 active 版本，圈选服务完全不受影响。ZK 挂了只影响版本切换，不影响查询。
> 2. **中期**：ZK 集群恢复后，自动触发延迟切换。
> 3. **兜底方案**：如果 ZK 长时间不可用，通过运维命令手动触发各节点独立加载最新版本。虽然各节点切换时间可能不一致（最多相差几秒），但因为新旧版本的数据差异通常很小（T 和 T+1 的标签变化比例 <5%），短暂不一致对预估结果的影响在可接受范围内。

**Q: 分片节点扩容时，如何做数据重新分布？**

> 我们使用 **一致性哈希** 来分配用户 ID 到分片，而不是简单的取模。
>
> 扩容步骤：
> 1. 新节点上线，加入一致性哈希环
> 2. 只需要迁移受影响范围的 Bitmap 数据（约 1/N 的数据量，N 为总节点数）
> 3. 迁移期间，旧节点和新节点都能响应查询（旧节点返回完整数据，新节点返回部分数据）
> 4. 迁移完成后更新路由表
>
> 实际中我们倾向于在低峰期做 **全量重建**，因为 Bitmap 本身每天重建一次，扩容时只需在新的节点分配策略下重新构建即可，代价不大。

```
       ↓ Bitmap 服务不可用
  Level 1：ClickHouse 同时承担预估和精确圈选
       ↓ ClickHouse 不可用
  Level 2：返回缓存的上一次预估结果 + 标注"数据非实时"
       ↓ Redis 缓存不可用
  Level 3：提示"服务暂时不可用" + 触发 P0 告警
```

### 2.3 降级链实现代码

```java
/**
 * 圈选服务降级控制器
 *
 * 核心设计思想：
 *   每个下游依赖都有独立的断路器
 *   断路器状态自动驱动降级链
 *   降级不需要人工干预，全自动完成
 */
@Service
public class CrowdSelectServiceImpl implements CrowdSelectService {

    // 各组件的断路器
    private final CircuitBreaker bitmapCircuitBreaker;
    private final CircuitBreaker clickHouseCircuitBreaker;
    private final CircuitBreaker redisCircuitBreaker;

    // 各引擎
    private final BitmapCrowdEngine bitmapEngine;
    private final ClickHouseCrowdEngine ckEngine;
    private final SparkCrowdEngine sparkEngine;

    // 缓存
    private final Cache<String, EstimateResult> estimateCache;

    // 降级指标
    private final Counter degradationCounter;

    @Override
    public EstimateResult estimate(CrowdSelectRequest request) {
        String cacheKey = request.buildCacheKey();

        // === 尝试缓存 ===
        EstimateResult cached = tryGetFromCache(cacheKey);
        if (cached != null) {
            return cached.withSource("cache");
        }

        // === Level 0: 正常路径 ===
        if (allEnumConditions(request) && bitmapCircuitBreaker.getState() == CLOSED) {
            try {
                EstimateResult result = CircuitBreaker.decorateSupplier(
                    bitmapCircuitBreaker,
                    () -> bitmapEngine.estimate(request)
                ).get();
                cacheResult(cacheKey, result);
                return result.withSource("bitmap");
            } catch (Exception e) {
                log.warn("Bitmap estimate failed, falling back to ClickHouse", e);
                degradationCounter.increment("bitmap_to_ck");
            }
        }

        // === Level 1: ClickHouse 降级路径 ===
        if (clickHouseCircuitBreaker.getState() != OPEN) {
            try {
                EstimateResult result = CircuitBreaker.decorateSupplier(
                    clickHouseCircuitBreaker,
                    () -> ckEngine.estimate(request)
                ).get();
                cacheResult(cacheKey, result);
                return result.withSource("clickhouse");
            } catch (Exception e) {
                log.warn("ClickHouse estimate failed, falling back to cache", e);
                degradationCounter.increment("ck_to_cache");
            }
        }

        // === Level 2: 缓存降级路径 ===
        // 即使 TTL 过期，也尝试返回旧数据
        EstimateResult staleResult = estimateCache.getIfPresent(cacheKey);
        if (staleResult != null) {
            return staleResult.withSource("stale_cache").withWarning("数据非实时，仅供参考");
        }

        // 尝试从最近的相似条件中找近似结果
        EstimateResult similar = findSimilarCachedResult(request);
        if (similar != null) {
            return similar.withSource("similar_cache").withWarning("基于相似条件估算");
        }

        // === Level 3: 完全降级 ===
        degradationCounter.increment("total_degradation");
        alertService.sendP0Alert("圈选服务全部降级", request.toString());
        return EstimateResult.unavailable("服务暂时不可用，请稍后重试");
    }

    /**
     * 精确圈选同样有降级链
     */
    @Override
    public CrowdResult select(CrowdSelectRequest request) {
        long estimatedCount = estimate(request).getCount();

        // 根据预估人数选择引擎
        if (estimatedCount < 1_000_000) {
            // 小批量：走 ClickHouse
            return selectWithFallback(
                () -> ckEngine.select(request),              // 首选
                () -> sparkEngine.selectAsync(request),      // 降级：Spark 异步
                request
            );
        } else {
            // 大批量：走 Spark
            return selectWithFallback(
                () -> sparkEngine.selectAsync(request),      // 首选
                () -> ckEngine.selectWithLimit(request, 1_000_000), // 降级：CK 限量
                request
            );
        }
    }

    private CrowdResult selectWithFallback(
            Supplier<CrowdResult> primary,
            Supplier<CrowdResult> fallback,
            CrowdSelectRequest request) {
        try {
            return primary.get();
        } catch (Exception e) {
            log.warn("Primary select engine failed, trying fallback", e);
            try {
                return fallback.get();
            } catch (Exception e2) {
                log.error("Both select engines failed", e2);
                return CrowdResult.failed("圈选服务异常，请稍后重试");
            }
        }
    }
}
```

```java
/**
 * 复杂度感知的限流器
 *
 * 不同复杂度的圈选请求消耗的资源差异巨大：
 *   简单条件（3个AND）：Bitmap 50ms，ClickHouse 200ms
 *   复杂条件（10个条件嵌套）：Bitmap 200ms，ClickHouse 3s
 *   超复杂条件：可能导致 ClickHouse OOM
 *
 * 所以不能用统一的 QPS 限流，需要按复杂度分级
 */
@Component
public class ComplexityAwareRateLimiter {

    // 各复杂度级别的信号量
    private final Semaphore simpleSlots = new Semaphore(100);   // 简单查询最多 100 并发
    private final Semaphore complexSlots = new Semaphore(20);   // 复杂查询最多 20 并发
    private final Semaphore heavySlots = new Semaphore(5);      // 超重查询最多 5 并发

    public <T> T executeWithLimit(CrowdSelectRequest request, Supplier<T> action) {
        QueryComplexity complexity = analyzeComplexity(request);
        Semaphore semaphore = getSemaphore(complexity);
        long timeout = getTimeout(complexity);

        boolean acquired = false;
        try {
            acquired = semaphore.tryAcquire(timeout, TimeUnit.MILLISECONDS);
            if (!acquired) {
                throw new RateLimitException(
                    "圈选并发超限，当前复杂度级别：" + complexity
                    + "，可用槽位：" + semaphore.availablePermits());
            }
            return action.get();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new ServiceException("请求被中断");
        } finally {
            if (acquired) {
                semaphore.release();
            }
        }
    }

    /**
     * 分析查询复杂度
     */
    private QueryComplexity analyzeComplexity(CrowdSelectRequest request) {
        int conditionCount = countConditions(request.getCondition());
        int nestingDepth = maxNestingDepth(request.getCondition());
        boolean hasSubQuery = hasSubQuery(request.getCondition());
        boolean hasArrayOp = hasArrayOperation(request.getCondition());

        if (hasSubQuery || conditionCount > 10 || nestingDepth > 4) {
            return QueryComplexity.HEAVY;
        } else if (conditionCount > 3 || nestingDepth > 2 || hasArrayOp) {
            return QueryComplexity.COMPLEX;
        } else {
            return QueryComplexity.SIMPLE;
        }
    }

    private Semaphore getSemaphore(QueryComplexity complexity) {
        switch (complexity) {
            case SIMPLE:  return simpleSlots;
            case COMPLEX: return complexSlots;
            case HEAVY:   return heavySlots;
            default:      return complexSlots;
        }
    }

    private long getTimeout(QueryComplexity complexity) {
        switch (complexity) {
            case SIMPLE:  return 100;   // 简单查询等 100ms 就放弃
            case COMPLEX: return 500;   // 复杂查询等 500ms
            case HEAVY:   return 2000;  // 重查询等 2s（排队）
            default:      return 500;
        }
    }
}
```

## 3. 数据一致性挑战与解决方案

### 3.1 圈选系统中的一致性问题全景

```
圈选系统涉及多个数据源，它们之间的数据一致性是核心挑战。

数据流向：

  Hive 标签宽表 (T+1)
       │
       ├──→ Spark 构建 Bitmap ──→ Redis/JVM 内存
       │
       ├──→ DataX 同步到 ClickHouse
       │
       └──→ Spark 构建人群包 ──→ Redis/HDFS

  Flink 实时标签
       │
       ├──→ Redis 实时标签
       │
       └──→ Kafka 标签变更事件 ──→ 实时人群包更新

一致性问题点（至少 5 处）：

  ① Bitmap vs ClickHouse：两者从同一个 Hive 表导出，但导出时间可能不同
     → 用户在 Bitmap 预估 100 万，ClickHouse 精确圈选只有 95 万

  ② 实时标签 vs 离线标签：Flink 实时更新了 Redis，但 Bitmap/CK 还是昨天的数据
     → 用户刚改了城市，实时查标签显示上海，但圈选"上海用户"里没有他

  ③ 人群包 vs 圈选条件：人群包是昨天圈选生成的，今天的标签已经变了
     → 人群包里有些用户已经不满足条件了（幽灵用户）

  ④ 多节点 Bitmap 版本：分布式 Bitmap 的各节点切换时间不同步
     → 有的节点用 v1 有的节点用 v2，汇总结果有微小偏差

  ⑤ 缓存 vs 存储：条件指纹缓存的结果是 5 分钟前的
     → 标签更新后缓存未失效，返回旧数据
```

### 3.2 Bitmap 与 ClickHouse 数据一致性

```
根因：两条数据链路独立运行，完成时间不同

  Hive 标签宽表（dt=2026-03-15）
       │
       ├──→ 链路A：Spark Bitmap 构建任务（03:00 开始，03:30 完成）
       │    → Redis bitmap:city=北京:v20260315
       │
       └──→ 链路B：DataX ClickHouse 同步任务（03:00 开始，04:00 完成）
            → ClickHouse user_tags_wide WHERE dt='2026-03-15'

  时间窗口 03:30 ~ 04:00：
    Bitmap 已经是 3月15日数据
    ClickHouse 还是 3月14日数据
    → 同一个条件，两个引擎返回不同结果
```

**解决方案：版本对齐机制**

```java
/**
 * 数据版本管理器
 *
 * 核心思想：
 *   所有数据源共享一个"可用版本"概念
 *   只有当所有数据源的某个版本都就绪时，才宣告该版本可用
 *   查询时统一使用最新的可用版本
 */
@Service
public class DataVersionManager {

    private final RedisTemplate<String, String> redis;

    // 版本状态键
    private static final String BITMAP_VERSION_KEY = "data:version:bitmap";
    private static final String CK_VERSION_KEY = "data:version:clickhouse";
    private static final String AVAILABLE_VERSION_KEY = "data:version:available";

    /**
     * 各数据链路完成后调用，注册自己的版本
     */
    public void registerVersion(DataSource source, String version) {
        String key = getVersionKey(source);
        redis.opsForValue().set(key, version);

        // 检查是否所有数据源都达到了该版本
        tryPromoteVersion(version);
    }

    /**
     * 尝试提升可用版本
     *
     * 只有当 Bitmap 和 ClickHouse 都准备好同一版本时，
     * 才将该版本设为可用版本
     */
    private void tryPromoteVersion(String candidateVersion) {
        String bitmapVersion = redis.opsForValue().get(BITMAP_VERSION_KEY);
        String ckVersion = redis.opsForValue().get(CK_VERSION_KEY);

        if (candidateVersion.equals(bitmapVersion)
                && candidateVersion.equals(ckVersion)) {
            String oldVersion = redis.opsForValue().get(AVAILABLE_VERSION_KEY);
            redis.opsForValue().set(AVAILABLE_VERSION_KEY, candidateVersion);
            log.info("Data version promoted: {} → {}", oldVersion, candidateVersion);

            // 通知所有服务实例刷新版本
            redis.convertAndSend("data:version:update", candidateVersion);
        } else {
            log.info("Version {} not ready: bitmap={}, ck={}",
                     candidateVersion, bitmapVersion, ckVersion);
        }
    }

    /**
     * 查询时获取当前可用版本
     */
    public String getAvailableVersion() {
        return redis.opsForValue().get(AVAILABLE_VERSION_KEY);
    }

    /**
     * 版本不一致时的降级策略
     */
    public VersionStatus checkVersionConsistency() {
        String bitmapVersion = redis.opsForValue().get(BITMAP_VERSION_KEY);
        String ckVersion = redis.opsForValue().get(CK_VERSION_KEY);
        String availableVersion = redis.opsForValue().get(AVAILABLE_VERSION_KEY);

        if (bitmapVersion.equals(ckVersion)) {
            return VersionStatus.CONSISTENT;
        }

        // 计算版本差距
        long bitmapDate = parseDate(bitmapVersion);
        long ckDate = parseDate(ckVersion);
        long diff = Math.abs(bitmapDate - ckDate);

        if (diff <= 1) {
            // 差 1 天以内：可接受，使用较旧的那个版本
            return VersionStatus.ACCEPTABLE_LAG;
        } else {
            // 差 2 天以上：严重不一致，触发告警
            alertService.sendP1Alert("数据版本严重不一致",
                String.format("bitmap=%s, ck=%s, diff=%d days",
                              bitmapVersion, ckVersion, diff));
            return VersionStatus.INCONSISTENT;
        }
    }
}
```

### 3.3 实时标签与离线标签的一致性

```
场景还原：

  1. 用户张三昨天还在北京（离线标签 city=北京，Bitmap 和 CK 中 city=北京）
  2. 今天上午张三在上海打开 App（Flink 实时更新 Redis city=上海）
  3. 运营下午圈选"上海用户"
     - 查单个用户标签 API → 返回 city=上海（Redis 实时标签）✓
     - Bitmap 预估"上海用户" → 张三不在结果中 ✗（Bitmap 还是昨天的）
     - ClickHouse 圈选 → 张三不在结果中 ✗（CK 也是昨天的）

  矛盾：用户明明在上海，但圈选不出来！

为什么这是可接受的？
  ① 离线标签 T+1 更新，运营已知并接受这个延迟
  ② 对于 1 亿用户，每天城市变化的用户可能不到 0.1%
  ③ 如果真的需要实时圈选"当前在上海的用户"，应该用实时规则引擎而不是离线圈选

但如果业务方确实需要"准实时"圈选？

解决方案：增量 Bitmap 补偿
```

```java
/**
 * 增量 Bitmap 补偿机制
 *
 * 核心思想：
 *   在离线 Bitmap（T+1）的基础上，叠加一层实时增量 Bitmap
 *   增量 Bitmap 记录今天标签发生变化的用户
 *
 * 最终结果 = 离线 Bitmap 结果 + 增量补偿
 */
@Service
public class IncrementalBitmapCompensator {

    // 增量 Bitmap：记录今天标签变化的用户
    // key: "delta:city=上海:add" → 今天新增的"上海用户"Bitmap
    // key: "delta:city=北京:remove" → 今天移出的"北京用户"Bitmap
    private final Map<String, RoaringBitmap> deltaBitmaps = new ConcurrentHashMap<>();

    /**
     * Flink 标签变更事件消费者
     *
     * 当用户标签发生变化时，更新增量 Bitmap
     */
    @KafkaListener(topics = "tag_change_events")
    public void onTagChange(TagChangeEvent event) {
        // event: {userId=12345, tagCode=city, oldValue=北京, newValue=上海}

        int userId = event.getUserId();
        String tagCode = event.getTagCode();

        if (event.getOldValue() != null) {
            // 从旧值的 Bitmap 中移除
            String removeKey = "delta:" + tagCode + "=" + event.getOldValue() + ":remove";
            deltaBitmaps.computeIfAbsent(removeKey, k -> new RoaringBitmap())
                        .add(userId);
        }

        if (event.getNewValue() != null) {
            // 添加到新值的 Bitmap 中
            String addKey = "delta:" + tagCode + "=" + event.getNewValue() + ":add";
            deltaBitmaps.computeIfAbsent(addKey, k -> new RoaringBitmap())
                        .add(userId);
        }
    }

    /**
     * 圈选时叠加增量补偿
     *
     * 补偿后的 Bitmap = (离线 Bitmap - 移出用户) + 新增用户
     *
     * 例如圈选 city=上海：
     *   离线 Bitmap（昨天的上海用户）
     *   - delta:city=上海:remove（今天从上海移出的用户）
     *   + delta:city=上海:add（今天新增的上海用户）
     */
    public RoaringBitmap compensate(String tagKey, RoaringBitmap offlineBitmap) {
        RoaringBitmap result = offlineBitmap.clone();

        // 移除今天不再满足条件的用户
        RoaringBitmap removeBitmap = deltaBitmaps.get("delta:" + tagKey + ":remove");
        if (removeBitmap != null) {
            result.andNot(removeBitmap);
        }

        // 添加今天新满足条件的用户
        RoaringBitmap addBitmap = deltaBitmaps.get("delta:" + tagKey + ":add");
        if (addBitmap != null) {
            result.or(addBitmap);
        }

        return result;
    }

    /**
     * 每天凌晨离线 Bitmap 更新后，清空增量数据
     */
    @Scheduled(cron = "0 0 4 * * ?")
    public void resetDeltaBitmaps() {
        deltaBitmaps.clear();
        log.info("Delta bitmaps cleared after offline bitmap refresh");
    }
}
```

### 3.4 人群包版本切换的一致性

```
场景：人群包正在被营销系统消费，同时人群包在更新

  时间线：
  T=0   营销系统开始读取人群包 crowd:1001（v1 版本，100 万用户）
  T=1s  人群包更新任务开始，写入新版本 crowd:1001:v2
  T=3s  营销系统正在分批读取 v1（已读 50 万）
  T=5s  新版本写入完成，切换版本指针 crowd:1001:latest → v2
  T=6s  营销系统继续读取...如果直接读 crowd:1001 会读到 v2！
        → 前 50 万来自 v1，后 50 万来自 v2，数据混乱

解决方案：版本化读取 + Copy-on-Write
```

```java
/**
 * 版本化人群包管理器
 *
 * 解决"读写并发"问题的核心：
 *   写入时创建新版本（不修改旧版本）
 *   读取时锁定版本（读取过程中版本不变）
 *   旧版本延迟清理（等待所有读取完成）
 */
@Service
public class VersionedCrowdPackageManager {

    /**
     * 开始读取人群包（返回版本化的读取句柄）
     *
     * 消费者必须先调用此方法获取读取句柄，
     * 读取期间使用句柄中的固定版本，不受后续更新影响
     */
    public CrowdReadHandle openRead(Long crowdId) {
        // 获取当前最新版本
        String version = redis.opsForValue().get("crowd:" + crowdId + ":latest");

        // 增加该版本的读取引用计数
        redis.opsForValue().increment("crowd:" + crowdId + ":" + version + ":readers");

        return new CrowdReadHandle(crowdId, version);
    }

    /**
     * 读取完成，释放句柄
     */
    public void closeRead(CrowdReadHandle handle) {
        String refKey = "crowd:" + handle.getCrowdId() + ":"
                        + handle.getVersion() + ":readers";
        Long readers = redis.opsForValue().decrement(refKey);

        // 如果该版本的读取者为 0 且不是最新版本，可以安全清理
        if (readers != null && readers <= 0) {
            String latest = redis.opsForValue().get(
                "crowd:" + handle.getCrowdId() + ":latest");
            if (!handle.getVersion().equals(latest)) {
                scheduleCleanup(handle.getCrowdId(), handle.getVersion());
            }
        }
    }

    /**
     * 更新人群包（Copy-on-Write）
     */
    public void updateCrowdPackage(Long crowdId, RoaringBitmap newUsers) {
        // 1. 生成新版本号
        String newVersion = "v" + System.currentTimeMillis();
        String newKey = "crowd:" + crowdId + ":" + newVersion;

        // 2. 将新数据写入新版本 key（不影响旧版本）
        byte[] serialized = serialize(newUsers);
        redis.opsForValue().set(newKey, serialized);

        // 3. 验证写入成功
        if (redis.opsForValue().get(newKey) == null) {
            throw new DataException("Failed to write new crowd version");
        }

        // 4. 原子切换版本指针
        redis.opsForValue().set("crowd:" + crowdId + ":latest", newVersion);

        // 5. 记录旧版本，稍后清理
        String oldVersion = redis.opsForValue().get("crowd:" + crowdId + ":previous");
        redis.opsForValue().set("crowd:" + crowdId + ":previous",
            redis.opsForValue().get("crowd:" + crowdId + ":latest"));

        log.info("Crowd {} updated: {} → {}", crowdId, oldVersion, newVersion);
    }

    /**
     * 清理旧版本（延迟执行）
     */
    private void scheduleCleanup(Long crowdId, String version) {
        // 延迟 30 分钟后清理，确保所有长查询已完成
        scheduler.schedule(() -> {
            String refKey = "crowd:" + crowdId + ":" + version + ":readers";
            Long readers = redis.opsForValue().get(refKey) != null
                ? Long.parseLong(redis.opsForValue().get(refKey)) : 0;

            if (readers <= 0) {
                redis.delete("crowd:" + crowdId + ":" + version);
                redis.delete(refKey);
                log.info("Cleaned up old crowd version: {}:{}", crowdId, version);
            } else {
                // 还有读取者，再延迟
                log.info("Crowd {}:{} still has {} readers, defer cleanup",
                         crowdId, version, readers);
                scheduleCleanup(crowdId, version);
            }
        }, 30, TimeUnit.MINUTES);
    }
}
```

### 3.5 缓存一致性设计

```
圈选结果缓存的一致性问题：

  场景：
  T=0   运营圈选 "北京 AND 高消费" → 结果 120 万 → 缓存 5 分钟
  T=1m  标签更新（有 1 万用户从北京搬到上海）
  T=2m  运营再次查相同条件 → 返回缓存的 120 万（实际应该是 119 万）
  T=5m  缓存过期，下次查询返回 119 万

  误差 = 1万/120万 ≈ 0.83% → 在允许的 ±5% 范围内

  结论：对于预估场景，5 分钟 TTL 的缓存不一致是可接受的

但有例外情况需要主动失效缓存：
  ① 运营手动触发了标签重算
  ② 发现数据质量问题后修复了标签
  ③ 圈选条件涉及的标签定义发生了变更

主动失效机制：
```

```java
/**
 * 圈选结果缓存管理器
 *
 * 双重过期策略：
 *   1. TTL 过期：5 分钟后自然过期
 *   2. 事件驱动失效：标签变更事件触发相关缓存失效
 */
@Service
public class EstimateCacheManager {

    // L1: JVM 本地缓存
    private final Cache<String, EstimateResult> localCache = Caffeine.newBuilder()
        .maximumSize(10_000)
        .expireAfterWrite(Duration.ofMinutes(5))
        .build();

    // L2: Redis 分布式缓存
    private final RedisTemplate<String, EstimateResult> redis;

    // 标签 → 缓存 key 的反向索引（用于精确失效）
    // key: "city" → value: Set{"md5_abc", "md5_def", ...}
    private final Map<String, Set<String>> tagToCacheKeys = new ConcurrentHashMap<>();

    /**
     * 缓存圈选结果
     */
    public void cacheResult(CrowdSelectRequest request, EstimateResult result) {
        String cacheKey = request.buildCacheKey();

        // 写入缓存
        localCache.put(cacheKey, result);
        redis.opsForValue().set("estimate:" + cacheKey, result, Duration.ofMinutes(5));

        // 维护反向索引：记录该缓存涉及了哪些标签
        for (String tagCode : request.getInvolvedTagCodes()) {
            tagToCacheKeys.computeIfAbsent(tagCode, k -> ConcurrentHashMap.newKeySet())
                          .add(cacheKey);
        }
    }

    /**
     * 标签变更时，精确失效相关缓存
     *
     * 例如：city 标签发生变化 → 只失效包含 city 条件的缓存
     *       不影响其他缓存（如只包含 gender 条件的缓存）
     */
    @EventListener
    public void onTagMetadataChange(TagMetadataChangeEvent event) {
        String tagCode = event.getTagCode();
        Set<String> affectedKeys = tagToCacheKeys.remove(tagCode);

        if (affectedKeys != null && !affectedKeys.isEmpty()) {
            // 批量失效
            for (String key : affectedKeys) {
                localCache.invalidate(key);
                redis.delete("estimate:" + key);
            }
            log.info("Invalidated {} cache entries for tag {}",
                     affectedKeys.size(), tagCode);
        }
    }

    /**
     * 全量标签刷新时（凌晨 T+1 更新后），清空所有缓存
     */
    @EventListener
    public void onBitmapVersionSwitch(BitmapVersionSwitchEvent event) {
        localCache.invalidateAll();
        // Redis 缓存靠 TTL 自然过期即可（最多 5 分钟后全部过期）
        tagToCacheKeys.clear();
        log.info("All estimate caches invalidated after bitmap switch to {}",
                 event.getNewVersion());
    }
}
```

### 4.2 优先级队列实现

```java
/**
 * 基于 Redis ZSet 的优先级任务队列
 *
 * 为什么用 Redis ZSet？
 *   1. 天然支持优先级排序（score 越小优先级越高）
 *   2. 原子操作保证不会重复消费
 *   3. 持久化不丢任务
 *   4. 多个调度器实例可以安全竞争消费
 */
@Service
public class PriorityTaskQueue {

    private static final String QUEUE_KEY = "crowd:task:queue";
    private static final String PROCESSING_KEY = "crowd:task:processing";

    /**
     * 提交任务到优先级队列
     *
     * 优先级规则（score 越小越优先）：
     *   VIP 用户的任务：score = 1000 + timestamp
     *   普通用户的任务：score = 2000 + timestamp
     *   低优先级任务（如定时刷新）：score = 3000 + timestamp
     *   同优先级内按提交时间 FIFO
     */
    public void submit(CrowdTask task) {
        // 1. 任务持久化到 MySQL
        taskRepository.save(task);

        // 2. 计算优先级 score
        double score = calculateScore(task);

        // 3. 入队
        redis.opsForZSet().add(QUEUE_KEY, task.getTaskId(), score);

        log.info("Task {} submitted with priority score {}", task.getTaskId(), score);
    }

    /**
     * 消费任务（原子操作，防止重复消费）
     *
     * 使用 Lua 脚本保证原子性：
     *   1. 从 ZSet 取出 score 最小的元素
     *   2. 移动到 processing 集合
     *   3. 两步必须原子完成
     */
    public CrowdTask poll() {
        // Lua 脚本：原子地从队列取出并移到处理中集合
        String luaScript =
            "local task = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', '+inf', 'LIMIT', 0, 1) " +
            "if #task > 0 then " +
            "    redis.call('ZREM', KEYS[1], task[1]) " +
            "    redis.call('SADD', KEYS[2], task[1]) " +
            "    return task[1] " +
            "else " +
            "    return nil " +
            "end";

        String taskId = redis.execute(
            new DefaultRedisScript<>(luaScript, String.class),
            Arrays.asList(QUEUE_KEY, PROCESSING_KEY));

        if (taskId == null) return null;

        CrowdTask task = taskRepository.findById(taskId);
        task.setStatus(TaskStatus.PROCESSING);
        task.setStartTime(LocalDateTime.now());
        taskRepository.save(task);

        return task;
    }

    /**
     * 任务完成确认
     */
    public void complete(String taskId, CrowdResult result) {
        redis.opsForSet().remove(PROCESSING_KEY, taskId);

        CrowdTask task = taskRepository.findById(taskId);
        task.setStatus(TaskStatus.COMPLETED);
        task.setEndTime(LocalDateTime.now());
        task.setResult(result);
        taskRepository.save(task);

        // 通知前端
        websocketNotifier.notify(task.getCreatorId(),
            "人群包圈选完成：" + task.getCrowdName() + "，共 " + result.getCount() + " 人");
    }

    /**
     * 僵尸任务检测
     *
     * 场景：执行器拿到任务后宕机，任务停留在 processing 集合中
     * 策略：超过 30 分钟未完成的任务自动回退到队列
     */
    @Scheduled(fixedRate = 60_000)  // 每分钟检查一次
    public void checkZombieTasks() {
        Set<String> processingTasks = redis.opsForSet().members(PROCESSING_KEY);

        for (String taskId : processingTasks) {
            CrowdTask task = taskRepository.findById(taskId);
            if (task.getStartTime().plusMinutes(30).isBefore(LocalDateTime.now())) {
                // 超时，回退到队列
                redis.opsForSet().remove(PROCESSING_KEY, taskId);

                if (task.getRetryCount() < 3) {
                    // 重试次数未超限，重新入队
                    task.setRetryCount(task.getRetryCount() + 1);
                    task.setStatus(TaskStatus.PENDING);
                    taskRepository.save(task);
                    submit(task);
                    log.warn("Zombie task {} re-queued (retry {})", taskId, task.getRetryCount());
                } else {
                    // 重试次数超限，标记失败
                    task.setStatus(TaskStatus.FAILED);
                    task.setErrorMessage("任务执行超时，已重试 3 次");
                    taskRepository.save(task);
                    alertService.sendP1Alert("圈选任务最终失败", taskId);
                }
            }
        }
    }
}
```

### 4.3 幂等性设计

```java
/**
 * 圈选任务幂等控制器
 *
 * 问题场景：
 *   1. 用户重复点击"确认圈选"按钮
 *   2. 前端超时重试
 *   3. 调度器重复分发（ZK 临时节点失效后重平衡）
 *
 * 解决方案：
 *   每个任务有唯一的幂等 key（基于条件 + 用户 + 时间窗口）
 *   相同幂等 key 的重复提交直接返回已有任务 ID
 */
@Service
public class IdempotentTaskController {

    /**
     * 幂等提交任务
     *
     * 幂等 key = MD5(用户ID + 圈选条件JSON + 时间窗口)
     * 时间窗口：取当前时间的 5 分钟整数窗口
     *   例如 14:03 和 14:07 在同一窗口，14:03 和 14:08 不在
     *   这样 5 分钟内对相同条件的重复提交会被去重
     */
    public TaskSubmitResult submitIdempotent(CrowdSelectRequest request, String userId) {
        String idempotentKey = buildIdempotentKey(request, userId);

        // 尝试在 Redis 设置幂等 key（NX = 不存在才设置）
        Boolean isNew = redis.opsForValue().setIfAbsent(
            "idempotent:" + idempotentKey,
            "",
            Duration.ofMinutes(10)
        );

        if (Boolean.TRUE.equals(isNew)) {
            // 首次提交，创建任务
            CrowdTask task = createTask(request, userId);
            // 记录 taskId 到幂等 key
            redis.opsForValue().set("idempotent:" + idempotentKey, task.getTaskId(),
                                    Duration.ofMinutes(10));
            taskQueue.submit(task);
            return TaskSubmitResult.created(task.getTaskId());
        } else {
            // 重复提交，返回已有任务
            String existingTaskId = redis.opsForValue().get("idempotent:" + idempotentKey);
            if (existingTaskId != null && !existingTaskId.isEmpty()) {
                return TaskSubmitResult.duplicate(existingTaskId);
            }
            // 极端情况：key 存在但 taskId 还没写入（并发窗口）
            // 等 100ms 重试一次
            try { Thread.sleep(100); } catch (InterruptedException ignored) {}
            existingTaskId = redis.opsForValue().get("idempotent:" + idempotentKey);
            return TaskSubmitResult.duplicate(existingTaskId);
        }
    }

    private String buildIdempotentKey(CrowdSelectRequest request, String userId) {
        // 5 分钟时间窗口
        long timeWindow = System.currentTimeMillis() / (5 * 60 * 1000);
        String raw = userId + ":" + request.buildCacheKey() + ":" + timeWindow;
        return DigestUtils.md5Hex(raw);
    }
```

### 4.4 分布式锁在圈选中的应用

```
圈选系统中需要分布式锁的场景：

  ① Bitmap 版本切换
     多个节点不能同时执行切换，需要协调
     → ZooKeeper 分布式屏障（barrier）

  ② 人群包版本指针更新
     更新 crowd:1001:latest 指针必须原子操作
     → Redis SETNX 分布式锁 + Lua 脚本

  ③ 定时任务调度
     人群包定时刷新任务不能被多个实例重复执行
     → Redis 分布式锁 + 释放保护（只有持锁者能释放）

  ④ 并发控制
     同一人群包不能同时被两个更新任务修改
     → 基于 crowdId 的细粒度分布式锁
```

```java
/**
 * 人群包更新分布式锁
 *
 * 设计要点：
 *   1. 细粒度锁：按 crowdId 加锁，不同人群包可以并行更新
 *   2. 可重入：同一个线程可以重复获取锁（防止递归调用死锁）
 *   3. 自动续期：避免任务执行时间超过锁的过期时间
 *   4. 安全释放：只有持锁者能释放锁（用唯一标识验证）
 */
@Component
public class CrowdUpdateLock {

    private static final String LOCK_PREFIX = "lock:crowd:update:";
    private static final long DEFAULT_LEASE_MS = 30_000;  // 30 秒

    /**
     * 获取锁并执行更新操作
     */
    public <T> T executeWithLock(Long crowdId, Supplier<T> action) {
        String lockKey = LOCK_PREFIX + crowdId;
        String lockValue = UUID.randomUUID().toString();  // 唯一标识

        boolean acquired = false;
        try {
            // 尝试获取锁
            acquired = tryLock(lockKey, lockValue, DEFAULT_LEASE_MS);
            if (!acquired) {
                throw new ConcurrentUpdateException(
                    "人群包 " + crowdId + " 正在被其他任务更新，请稍后重试");
            }

            // 启动自动续期（看门狗机制）
            ScheduledFuture<?> watchdog = startWatchdog(lockKey, lockValue);

            try {
                return action.get();
            } finally {
                watchdog.cancel(false);
            }
        } finally {
            if (acquired) {
                releaseLock(lockKey, lockValue);
            }
        }
    }

    /**
     * 获取锁（Lua 脚本保证原子性）
     */
    private boolean tryLock(String lockKey, String lockValue, long leaseMs) {
        String luaScript =
            "if redis.call('SET', KEYS[1], ARGV[1], 'NX', 'PX', ARGV[2]) then " +
            "    return 1 " +
            "else " +
            "    return 0 " +
            "end";

        Long result = redis.execute(
            new DefaultRedisScript<>(luaScript, Long.class),
            Collections.singletonList(lockKey),
            lockValue, String.valueOf(leaseMs));

        return result != null && result == 1;
    }

    /**
     * 安全释放锁（只有持锁者能释放）
     */
    private void releaseLock(String lockKey, String lockValue) {
        String luaScript =
            "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
            "    return redis.call('DEL', KEYS[1]) " +
            "else " +
            "    return 0 " +
            "end";

        redis.execute(
            new DefaultRedisScript<>(luaScript, Long.class),
            Collections.singletonList(lockKey),
            lockValue);
    }

    /**
     * 看门狗：自动续期
     *
     * 每 10 秒续期一次，续期到 30 秒
     * 如果持锁线程挂了，看门狗也会停止，锁自动过期释放
     */
    private ScheduledFuture<?> startWatchdog(String lockKey, String lockValue) {
        return scheduler.scheduleAtFixedRate(() -> {
            String luaScript =
                "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
                "    return redis.call('PEXPIRE', KEYS[1], ARGV[2]) " +
                "else " +
                "    return 0 " +
                "end";
            redis.execute(
                new DefaultRedisScript<>(luaScript, Long.class),
                Collections.singletonList(lockKey),
                lockValue, String.valueOf(DEFAULT_LEASE_MS));
        }, 10, 10, TimeUnit.SECONDS);
    }
}
```

## 5. 大规模故障场景与恢复策略

### 5.1 故障等级定义与响应 SLA

```
故障等级定义（针对圈选服务）：

  P0 — 圈选服务完全不可用
    影响：运营无法创建人群包，营销活动无法执行
    SLA：15 分钟内响应，30 分钟内恢复
    触发条件：
      - 三条圈选路径（Bitmap + CK + Cache）全部不可用
      - 人群包判断接口（contains）全部超时
    响应人：值班 SRE + 服务 Owner + 架构师

  P1 — 圈选服务严重降级
    影响：预估功能不可用或延迟大幅增加，但精确圈选可用
    SLA：30 分钟内响应，2 小时内恢复
    触发条件：
      - Bitmap 服务不可用（降级到 CK）
      - ClickHouse 响应时间 > 10s
      - 人群包更新延迟 > 2 小时
    响应人：值班 SRE + 服务 Owner

  P2 — 圈选服务部分降级
    影响：部分功能受限，核心功能正常
    SLA：2 小时内响应，24 小时内恢复
    触发条件：
      - 缓存命中率下降到 50% 以下
      - 单个 Bitmap 分片节点不可用（结果近似补偿）
      - 人群包数据非实时（使用旧版本）
    响应人：服务 Owner

  P3 — 性能抖动
    影响：性能指标超阈值但功能正常
    SLA：24 小时内处理
    触发条件：
      - 圈选预估 P99 > 500ms（正常 200ms）
      - CK 慢查询比例 > 5%
    响应人：值班开发
```

### 5.2 Redis 集群故障场景详解

```
场景一：Redis 单节点故障（最常见）

  现象：某个 Redis 主节点宕机
  影响：该节点上的数据暂时不可读写
  自动恢复：Redis Sentinel 在 30 秒内完成主从切换
  人工干预：通常不需要

  圈选服务的应对：
    ① 断路器感知到 Redis 部分超时
    ② 超时的 key 降级到 ClickHouse 查询
    ③ 30 秒后 Sentinel 完成切换，自动恢复
    ④ 整个过程用户可能感知到 1-2 次预估变慢（200ms → 2s）

场景二：Redis Cluster 脑裂

  现象：网络分区导致部分客户端连到旧主，部分连到新主
  影响：可能读到过期数据（旧主的数据）或写入丢失
  这对圈选的影响：
    人群包 contains 判断可能出错（在旧主上读到已被删除的用户）
    但因为人群包本身是 T+1 数据，短暂不一致可以接受

  防护措施：
    ① Redis 配置 min-replicas-to-write 1
       → 主节点必须至少有 1 个从节点才能写入，防止脑裂时旧主接受写入
    ② 客户端配置重试策略
       → 写入失败时退避重试，优先连接新主
    ③ 应用层版本校验
       → 读取人群包时检查版本号，版本不一致说明读到了旧数据

场景三：Redis Cluster 全部不可用

  现象：整个 Redis 集群不可达（机房网络故障/全部 OOM）
  影响范围：
    ① Bitmap 数据存储层不可用
    ② 人群包缓存不可用
    ③ 条件指纹缓存不可用
    ④ 分布式锁不可用
```

```java
/**
 * Redis 全集群故障应急预案
 *
 * 设计思路：
 *   Redis 在我们的架构中是"加速层"而非"唯一数据源"
 *   所有关键数据都有其他存储的备份
 *   Redis 全挂时降级到备份链路
 */
@Service
public class RedisDisasterRecovery {

    private final DoubleBufferBitmapStore localBitmapStore;
    private final ClickHouseCrowdEngine ckEngine;
    private final HdfsBitmapStore hdfsBitmapStore;
    private final LocalFileBitmapCache localFileCache;

    /**
     * Redis 故障时的预估降级链
     */
    public EstimateResult estimateWhenRedisDown(CrowdSelectRequest request) {

        // 降级路径1：JVM 内存中的 Bitmap（如果之前已加载）
        if (localBitmapStore.isLoaded()) {
            try {
                RoaringBitmap result = localBitmapStore.evaluate(request.getCondition());
                return EstimateResult.approximate(
                    result.getLongCardinality(),
                    "来源：JVM 本地 Bitmap（可能非最新版本）"
                );
            } catch (Exception e) {
                log.warn("Local bitmap estimate failed", e);
            }
        }

        // 降级路径2：ClickHouse
        try {
            return ckEngine.estimate(request);
        } catch (Exception e) {
            log.warn("ClickHouse estimate also failed", e);
        }

        // 降级路径3：本地文件缓存
        EstimateResult cachedResult = localFileCache.getLatestResult(request.buildCacheKey());
        if (cachedResult != null) {
            return cachedResult.withWarning("历史缓存数据，非实时结果");
        }

        return EstimateResult.unavailable("服务降级中，请稍后重试");
    }

    /**
     * Redis 恢复后的数据重建
     */
    public void rebuildRedisData() {
        log.info("Starting Redis data rebuild...");

        // 1. 从 HDFS 恢复 Bitmap 数据
        Map<String, byte[]> bitmapData = hdfsBitmapStore.loadLatestVersion();
        for (Map.Entry<String, byte[]> entry : bitmapData.entrySet()) {
            redis.opsForValue().set("bitmap:" + entry.getKey(), entry.getValue());
        }
        log.info("Rebuilt {} bitmap entries from HDFS", bitmapData.size());

        // 2. 从 MySQL 恢复人群包元数据
        List<CrowdPackage> activeCrowds = crowdRepository.findByStatus(CrowdStatus.ACTIVE);
        for (CrowdPackage crowd : activeCrowds) {
            byte[] crowdData = hdfsBitmapStore.loadCrowdPackage(crowd.getCrowdId());
            if (crowdData != null) {
                String version = "v" + System.currentTimeMillis();
                redis.opsForValue().set(
                    "crowd:" + crowd.getCrowdId() + ":" + version, crowdData);
                redis.opsForValue().set(
                    "crowd:" + crowd.getCrowdId() + ":latest", version);
            }
        }
        log.info("Rebuilt {} crowd packages from HDFS", activeCrowds.size());
    }
}
```

### 5.3 ClickHouse 故障场景详解

```
场景一：单个 Shard 不可用

  ClickHouse 集群配置：3 Shard × 2 Replica = 6 节点
  单个 Shard 的一个 Replica 挂了：
    → CK 自动路由到同 Shard 的另一个 Replica，查询完全透明

  单个 Shard 的两个 Replica 都挂了：
    → 该 Shard 数据不可查询，圈选结果缺失 1/3 用户

  应对策略：
    ① 检测到分布式查询报错 → 自动切换到降级模式
    ② 用可用 Shard 结果做外推：
       预估人数 ≈ 可用 Shard 结果 × (总 Shard / 可用 Shard)
    ③ 精确圈选降级到 Spark 任务

场景二：ClickHouse OOM（查询打爆内存）

  常见原因：
    ① 超复杂条件（20+ 个 OR 嵌套）导致中间结果集爆炸
    ② 大规模 GROUP BY（按高基数字段分组）
    ③ 多个复杂查询同时执行，内存叠加

  预防措施：
    ① 查询前做条件复杂度检查
       → 条件数 > 10 或嵌套深度 > 4 → 拒绝，走 Spark
    ② CK 配置内存限制
       → max_memory_usage = 10G（单查询）
       → max_memory_usage_for_all_queries = 40G（全部查询合计）
    ③ 查询超时 max_execution_time = 30（30 秒）
```

```java
/**
 * ClickHouse 查询安全网
 */
@Component
public class ClickHouseQueryGuard {

    public void validate(String sql, CrowdSelectRequest request) {
        // 1. 条件复杂度检查
        int conditionCount = countConditions(request.getCondition());
        if (conditionCount > 15) {
            throw new QueryTooComplexException(
                "圈选条件过于复杂（" + conditionCount + " 个），请简化或分步圈选");
        }

        // 2. 嵌套深度检查
        int nestingDepth = maxNestingDepth(request.getCondition());
        if (nestingDepth > 5) {
            throw new QueryTooComplexException(
                "条件嵌套层级过深（" + nestingDepth + " 层），请简化逻辑");
        }

        // 3. SQL 长度检查
        if (sql.length() > 10_000) {
            throw new QueryTooComplexException("生成的 SQL 过长，请简化条件");
        }

        // 4. 并发数检查
        int currentConcurrency = ckConcurrencyCounter.get();
        if (currentConcurrency >= 30) {
            throw new RateLimitException(
                "ClickHouse 并发已满（" + currentConcurrency + "/30），请稍后重试");
        }
    }

    public <T> T executeWithGuard(Supplier<T> queryAction) {
        ckConcurrencyCounter.incrementAndGet();
        long startTime = System.currentTimeMillis();
        try {
            return queryAction.get();
        } finally {
            ckConcurrencyCounter.decrementAndGet();
            long elapsed = System.currentTimeMillis() - startTime;
            if (elapsed > 3000) {
                slowQueryLogger.log("CK slow query: {}ms", elapsed);
            }
            if (elapsed > 10000) {
                alertService.sendP2Alert("CK 超慢查询", elapsed + "ms");
            }
        }
    }
}
```

### 5.4 人群包数据丢失与恢复

```
场景：Redis 中的人群包数据丢失（误操作/bug 导致 key 被删除）

恢复方案（按速度排序）：

  方案 A：从 HDFS 备份恢复（推荐，5-10 分钟）
    人群包每次生成时都同步备份到 HDFS
    1. 从 HDFS 读取最新的人群包文件
    2. 反序列化为 RoaringBitmap
    3. 重新写入 Redis + 重建版本指针

  方案 B：重新执行圈选任务（10-30 分钟）
    从 MySQL 元数据中获取圈选条件，重新提交

  方案 C：从 Redis RDB 恢复（最慢，但数据最全）
    适用于大面积数据丢失

预防措施：
  ① 写入 Redis 同时备份到 HDFS
  ② 操作审计日志（记录谁删了什么 key）
  ③ 定期对账（MySQL 记录 vs Redis 实际存在）
```

```java
/**
 * 人群包备份与恢复管理器
 */
@Service
public class CrowdBackupManager {

    /**
     * 写入时同时备份到 HDFS
     */
    public void saveCrowdPackage(Long crowdId, String version, RoaringBitmap bitmap) {
        byte[] serialized = serializeBitmap(bitmap);

        // 写入 Redis（主存储）
        redis.opsForValue().set("crowd:" + crowdId + ":" + version, serialized);

        // 写入 HDFS（备份）
        String hdfsPath = String.format("/data/crowd_backup/%d/%s/data.bitmap", crowdId, version);
        hdfsClient.write(hdfsPath, serialized);

        // 更新版本指针
        redis.opsForValue().set("crowd:" + crowdId + ":latest", version);

        // 记录元数据
        CrowdBackupRecord record = new CrowdBackupRecord();
        record.setCrowdId(crowdId);
        record.setVersion(version);
        record.setUserCount(bitmap.getLongCardinality());
        record.setHdfsPath(hdfsPath);
        record.setCreatedAt(LocalDateTime.now());
        backupRecordRepository.save(record);
    }

    /**
     * 从 HDFS 恢复
     */
    public void restoreFromHdfs(Long crowdId) {
        CrowdBackupRecord latest = backupRecordRepository
            .findTopByCrowdIdOrderByCreatedAtDesc(crowdId);
        if (latest == null) {
            throw new DataException("未找到人群包 " + crowdId + " 的备份记录");
        }

        byte[] data = hdfsClient.read(latest.getHdfsPath());
        redis.opsForValue().set(
            "crowd:" + crowdId + ":" + latest.getVersion(), data);
        redis.opsForValue().set("crowd:" + crowdId + ":latest", latest.getVersion());
        log.info("Crowd {} restored from HDFS. Version={}, Count={}",
                 crowdId, latest.getVersion(), latest.getUserCount());
    }

    /**
     * 每天对账：MySQL 记录 vs Redis 实际存在
     */
    @Scheduled(cron = "0 0 6 * * ?")
    public void reconcile() {
        List<CrowdPackage> activeCrowds = crowdRepository.findByStatus(CrowdStatus.ACTIVE);
        int missingCount = 0;

        for (CrowdPackage crowd : activeCrowds) {
            String latestVersion = redis.opsForValue().get(
                "crowd:" + crowd.getCrowdId() + ":latest");

            if (latestVersion == null) {
                missingCount++;
                try {
                    restoreFromHdfs(crowd.getCrowdId());
                    log.warn("Auto-restored missing crowd {}", crowd.getCrowdId());
                } catch (Exception e) {
                    log.error("Failed to restore crowd {}", crowd.getCrowdId(), e);
                }
            }
        }

        if (missingCount > 0) {
            alertService.sendP2Alert("人群包对账异常",
                "缺失 " + missingCount + " 个人群包，已自动恢复");
        }
    }
}
```

## 6. 弹性扩缩容与容量治理

### 6.1 圈选服务的容量模型

```
容量规划核心公式：

  Bitmap 路径：
    单节点容量 = JVM 堆 × 60% / 平均 Bitmap 大小
    例：32GB × 60% = 19.2GB → 可承载 ~2400 个 Bitmap

    单节点 QPS = CPU 核数 × (1000 / 单次耗时ms)
    例：16 核 × (1000 / 50) = 320 QPS

  ClickHouse 路径：
    单 Shard 并发 ≈ CPU 核数 / 查询占用核数
    例：32 核 / 4 = 8 并发，平均 1s/查询 → QPS ≈ 8
    3 Shard → 总 QPS ≈ 24

  Spark 精确圈选：
    单任务：2 Executor × (4核+8GB) = 8核+16GB
    YARN 队列 100 核 → 最多 12 并发任务
    单任务 5min → 吞吐 144 任务/小时

容量水位线：
  绿色（< 60%）：正常
  黄色（60-80%）：预警，评估扩容
  红色（> 80%）：紧急扩容
```

### 6.2 扩缩容策略

```
Bitmap 扩容：

  垂直扩容（加内存）：
    适用于用户量增长但在单机范围内
    简单无数据迁移，但有上限

  水平扩容（加分片节点）：
    推荐方案：下次凌晨全量重建时使用新分片数
    紧急方案：在线数据迁移（从旧节点复制受影响 Bitmap）

ClickHouse 扩容：

  短期：加 Replica（读 QPS 提升 50%，自动数据同步）
  长期：加 Shard（存储和并行度翻倍，需重建分布式表）

Spark 扩容：
  增加 YARN 队列资源配额
  或动态扩容 YARN 节点
```

### 7.2 容灾演练

```java
/**
 * 容灾演练框架
 *
 * 定期模拟故障场景，验证降级策略是否生效
 */
@Service
public class DisasterDrill {

    public enum DrillScenario {
        REDIS_SINGLE_NODE_DOWN("Redis 单节点宕机", Duration.ofMinutes(5)),
        REDIS_CLUSTER_DOWN("Redis 集群全部不可用", Duration.ofMinutes(10)),
        CK_SINGLE_SHARD_DOWN("CK 单 Shard 不可用", Duration.ofMinutes(5)),
        CK_ALL_DOWN("CK 全部不可用", Duration.ofMinutes(10)),
        BITMAP_SERVICE_DOWN("Bitmap 服务全部不可用", Duration.ofMinutes(5)),
        NETWORK_PARTITION("机房间网络分区", Duration.ofMinutes(15)),
        SLOW_DEPENDENCY("所有下游延迟 10 倍", Duration.ofMinutes(10));

        final String description;
        final Duration duration;
        DrillScenario(String d, Duration dur) { description = d; duration = dur; }
    }

    public DrillReport executeDrill(DrillScenario scenario) {
        log.info("Starting drill: {}", scenario.description);

        MetricsSnapshot baseline = collectMetrics();
        FaultInjector injector = createInjector(scenario);
        injector.inject();

        // 故障期间持续采集指标
        List<MetricsSnapshot> duringFault = new ArrayList<>();
        long start = System.currentTimeMillis();
        while (System.currentTimeMillis() - start < scenario.duration.toMillis()) {
            duringFault.add(collectMetrics());
            sleep(5000);
        }

        injector.remove();
        sleep(60_000);
        MetricsSnapshot afterRecovery = collectMetrics();

        return DrillReport.builder()
            .scenario(scenario)
            .baseline(baseline)
            .duringFault(duringFault)
            .afterRecovery(afterRecovery)
            .degradationWorked(duringFault.stream()
                .allMatch(m -> m.getErrorRate() < 0.05 && m.getP99Latency() < 5000))
            .build();
    }
}
```

```java
 * 圈选服务自愈控制器
 *
 * 根据监控指标自动执行恢复操作
 * 减少人工介入，提升 MTTR（平均恢复时间）

@Service

    /**
     * 缓存命中率持续低于阈值 → 自动预热

    @EventListener
    public void onCacheHitRateLow(CacheHitRateLowEvent event) {
        if (event.getHitRate() < 0.3 && event.getDuration().toMinutes() > 5) {
            log.warn("Cache hit rate {} for {} minutes, triggering warm-up",
                     event.getHitRate(), event.getDuration().toMinutes());

            hotConditions.forEach(key -> {
                try {
                    estimateService.estimateAndCache(key);
                } catch (Exception e) {
                    // 预热失败不影响正常服务
                }
            });
        }
    }

    /**
     * Bitmap 版本过旧 → 自动触发重建
     */
    @Scheduled(cron = "0 30 4 * * ?")  // 凌晨 4:30 检查
    public void checkBitmapFreshness() {
        String activeVersion = bitmapStore.getActiveVersion();
        String expectedVersion = "v" + LocalDate.now().format(DateTimeFormatter.BASIC_ISO_DATE);

        if (!expectedVersion.equals(activeVersion)) {
            log.warn("Bitmap version stale: active={}, expected={}",
                     activeVersion, expectedVersion);

            // 检查是否是 Spark 构建任务失败
            boolean sparkJobFailed = sparkMonitor.isJobFailed("bitmap-build-daily");
            if (sparkJobFailed) {
                log.info("Triggering bitmap rebuild due to Spark job failure");
                sparkSubmitter.submit("bitmap-build-daily");
                alertService.sendP2Alert("Bitmap 自动重建",
                    "Spark 构建任务失败，已自动重新提交");
            }
        }
    }

    /**
     * 人群包对账异常 → 自动恢复
     */
    @EventListener
    public void onCrowdPackageMissing(CrowdPackageMissingEvent event) {
        Long crowdId = event.getCrowdId();
        log.warn("Crowd package {} missing, attempting auto-restore", crowdId);

        try {
            crowdBackupManager.restoreFromHdfs(crowdId);
            log.info("Crowd package {} auto-restored successfully", crowdId);
        } catch (Exception e) {
            log.error("Auto-restore failed for crowd {}", crowdId, e);
            alertService.sendP1Alert("人群包自动恢复失败",
                "crowdId=" + crowdId + ", error=" + e.getMessage());
        }
    }

    /**
     * 线程池接近饱和 → 动态扩容
     */
    @Scheduled(fixedRate = 10_000)
    public void checkThreadPoolSaturation() {
        ThreadPoolExecutor executor = (ThreadPoolExecutor) queryExecutor;
        double utilization = (double) executor.getActiveCount() / executor.getMaximumPoolSize();

        if (utilization > 0.8 && executor.getMaximumPoolSize() < 512) {
            int newMax = Math.min(executor.getMaximumPoolSize() * 2, 512);
            executor.setMaximumPoolSize(newMax);
            log.warn("Thread pool expanded: {} → {}, utilization was {}%",
                     executor.getMaximumPoolSize() / 2, newMax, utilization * 100);
        }
    }
```

## 9. 综合场景面试题与深度解答

### Q1: 大促准备——圈选系统需要做哪些高可用准备？

**回答：**

> 大促对圈选系统的挑战是**运营集中圈选 + 营销系统高频判断用户是否在人群中**。我们的准备工作分四个阶段：
>
> **T-14 天（压测验证）：**
> 用线上录制的流量做全链路压测。重点验证：预估 API 在 200 QPS 下的 P99，contains 接口在 5 万 QPS 下的 P99，以及 Bitmap + CK + Spark 三条路径的降级链是否正常工作。压测中我们发现过 CK 在高并发下 P99 飙升到 10s，通过增加 Replica 解决。
>
> **T-7 天（资源扩容）：**
> Redis 扩容到双倍内存（人群包数据量会翻倍）。ClickHouse 增加 1 组 Replica。Spark YARN 队列预留大促专用资源。Bitmap 分片节点确认内存充足。
>
> **T-1 天（数据预热）：**
> 运营提前圈好大促人群包（避免大促当天现场圈选）。Bitmap 全量重建并预热。热门人群包预加载到 JVM Caffeine 缓存。条件指纹缓存预填充 Top 200 常见条件组合。
>
> **T-0 天（实时保障）：**
> 值班人员 on-call，监控大盘实时关注。限流策略调整：低优先级业务方的配额降低，保障核心链路。非紧急的大批量导出任务自动延迟到凌晨。准备好一键降级开关（手动触发 L1/L2 降级）。

### Q2: 圈选预估和精确圈选结果差异很大，怎么排查和解决？

**回答：**

> 这个问题我们实际遇到过。运营反馈 Bitmap 预估 150 万，但 ClickHouse 精确圈选只有 120 万，差异 20%。
>
> **排查过程：**
>
> 第一步检查**数据版本**。发现 Bitmap 是 3 月 14 日的数据，ClickHouse 已经更新到 3 月 15 日。原因是 Spark Bitmap 构建任务在 3 月 15 日凌晨失败了（Spark executor OOM），导致 Bitmap 停留在旧版本。
>
> 第二步检查**条件转换**。发现圈选条件中有一个"消费金额 > 3000"，Bitmap 对数值条件做了分桶处理（[3000-5000] OR [5000+]），而 ClickHouse 是精确比较。分桶边界问题导致边界值用户（恰好 3000 的用户）处理不一致。
>
> **解决方案：**
>
> 1. **版本对齐机制**：引入 DataVersionManager，只有 Bitmap 和 CK 都准备好同一版本时才宣告可用。版本不一致时统一降级到较旧版本，并触发告警。
> 2. **分桶边界对齐**：确保 Bitmap 分桶的边界逻辑与 CK 的比较逻辑一致。"金额 > 3000"在 Bitmap 中映射为 [3001-5000] OR [5000+]（开区间），与 CK 的 `amount > 3000` 语义一致。
> 3. **对账监控**：每天自动抽样 100 个条件组合，对比 Bitmap 和 CK 的结果，差异 > 5% 触发告警。
> 4. **前端提示**：如果检测到两个引擎版本不一致，前端预估结果标注"数据可能有 1 天延迟"。

### Q3: 人群包在多个下游系统（营销/推荐/风控）之间怎么保证一致性？

**回答：**

> 这是分布式系统中的**数据分发一致性**问题。核心挑战是：人群包更新后，所有下游系统需要同时看到新版本，否则会出现"营销系统认为用户在人群中，推荐系统认为不在"的情况。
>
> 我们的方案是 **版本化 + 通知 + 最终一致性**：
>
> **第一步：版本化存储。** 人群包每次更新都生成新版本号。新旧版本共存于 Redis，通过 `latest` 指针指向最新版本。
>
> **第二步：变更通知。** 人群包更新完成后，发送 Kafka 消息通知所有下游系统。消息内容包含 `{crowdId, newVersion, oldVersion, changeType}`。下游系统消费消息后刷新本地缓存的版本指针。
>
> **第三步：拉取兜底。** 下游系统每次查询人群包时，检查本地缓存的版本与 Redis `latest` 指针是否一致。不一致时主动拉取新版本。这样即使 Kafka 消息丢失，也能在下次查询时自动纠正。
>
> **最终一致性窗口：** 从人群包更新到所有下游看到新版本，通常 < 1 秒（Kafka 消费延迟）。极端情况下（Kafka 积压），最多 5 分钟（依赖主动拉取）。
>
> **一致性级别选择：** 我们与各业务方约定了不同的一致性要求。风控系统要求 < 1 秒（直接从 Redis 读最新版本，不走本地缓存）。推荐系统容忍 < 5 分钟。营销系统容忍 < 1 小时（因为营销活动有预设时间）。

### Q4: 设计一个可以水平扩展到 10 亿用户的圈选系统

**回答：**

> 当前架构在 1-2 亿用户时工作良好，扩展到 10 亿用户需要解决三个核心瓶颈：
>
> **瓶颈一：Bitmap 内存。**
> 1 亿用户时 1000 个 Bitmap 约 8GB。10 亿用户约 80GB，单机放不下。
> 解决：水平分片从 5 个节点扩展到 50 个节点，每个节点 2000 万用户。或者只对高频使用的 Top 200 标签建 Bitmap（覆盖 90% 的圈选场景），其余走 CK。
>
> **瓶颈二：ClickHouse 扫描量。**
> 10 亿行的标签宽表，即使有分区和索引，复杂条件的全量扫描也很慢。
> 解决：
> 1. 按用户活跃度分层存储：近 30 天活跃用户（约 3 亿）放主表，非活跃用户放冷表。90% 的圈选只针对活跃用户。
> 2. 增加 Shard 数量（从 3 个到 10 个），提高并行度。
> 3. 更激进地使用物化视图预聚合。
>
> **瓶颈三：人群包存储。**
> 10 亿用户的大人群包（比如"全量活跃用户" 3 亿人），RoaringBitmap 序列化后约 100-300MB。
> 解决：分段存储。将人群包按 userId 范围分成 100 段，每段独立存储。查询 contains 时用 userId 路由到对应段，O(1) 查询。
>
> **架构演进方向：**
> 从单集群 → 按地域分集群（华北、华东、华南各一套完整的圈选服务）。用户按注册地域路由到对应集群，每个集群只需处理 3-4 亿用户。跨地域的圈选（如"全国高消费用户"）由协调层合并各集群结果。

### Q5: 线上出现圈选预估延迟突然飙升到 5 秒，如何快速定位？

**回答：**

> 我用一个实际排查过程来回答。
>
> **第一步：看监控趋势（30 秒）。**
> 打开 Grafana 看圈选预估延迟曲线。发现不是所有请求都慢，而是 P99 从 200ms 飙到 5s，P50 基本正常（50ms）。说明是部分请求慢，不是全面劣化。
>
> **第二步：看降级指标（30 秒）。**
> 发现"Bitmap→CK 降级次数"突增。说明部分请求的 Bitmap 路径失败或超时，降级到了 ClickHouse。CK 的 1-3s 延迟拉高了整体 P99。
>
> **第三步：看 Bitmap 服务指标（1 分钟）。**
> 5 个 Bitmap 分片节点中，shard-3 的响应时间从 30ms 飙到 800ms，超过了 300ms 的断路器阈值，触发了熔断。
>
> **第四步：登录 shard-3 排查（2 分钟）。**
> `jstat -gcutil` 发现 Full GC 频繁（每分钟 2-3 次，每次 500ms+）。`jmap -histo:live` 发现 `byte[]` 对象异常多。进一步排查发现是凌晨的 Bitmap 重建任务有 bug——某个标签的 Bitmap 数据异常大（500MB，正常应该 10MB），加载到 JVM 后占满了 Old 区。
>
> **第五步：紧急修复（5 分钟）。**
> 临时方案：重启 shard-3，跳过异常标签的 Bitmap 加载。断路器自动恢复，P99 回落到正常。
> 根因修复：修复 Bitmap 构建逻辑中的 bug（标签数据清洗缺少空值过滤，导致生成了巨大的 Bitmap）。
>
> **复盘改进：**
> 1. 增加 Bitmap 大小监控：单个 Bitmap > 50MB 触发告警
> 2. 加载前校验：Bitmap 反序列化后检查基数是否合理
> 3. 节点健康检查：包括 GC 频率、堆内存使用率

### Q6: 如何做到人群包的 Exactly-Once 投递？

**回答：**

> 场景是：人群包更新后通过 Kafka 通知下游系统。需要保证每个下游系统恰好处理一次更新通知，不能重复也不能遗漏。
>
> **挑战分析：**
> 1. Kafka 消息可能重复投递（生产者重试、消费者 rebalance）
> 2. 消费者处理完消息后、提交 offset 前宕机 → 重启后重复消费
> 3. 网络抖动导致同一条消息被消费两次
>
> **解决方案：At-Least-Once + 消费端幂等**
>
> 1. **生产端：** 开启 Kafka 幂等生产者（`enable.idempotence=true`）。每条消息带上 `crowdId + version` 作为业务唯一键。
>
> 2. **消费端幂等：** 下游系统维护一个"已处理版本"表。处理消息前先检查 `(crowdId, version)` 是否已处理过。已处理则跳过（幂等）。处理和记录在同一个数据库事务中完成。
>
> 3. **兜底对账：** 即使 Kafka 消息丢失，下游系统每 5 分钟主动检查 Redis 中人群包的 `latest` 版本与本地版本是否一致。不一致时主动拉取，相当于"拉模式"补偿"推模式"的遗漏。
>
> 实际效果：Kafka 层面是 At-Least-Once，加上消费端幂等后，业务层面实现了 Exactly-Once 语义。

## 10. 高频追问与连环炮应对

### 10.1 追问链一：Bitmap 深入

```
面试官：你们用 RoaringBitmap 做圈选？
回答：是的，对枚举标签预构建 Bitmap，圈选转为 Bitmap AND/OR 运算...

追问1：Bitmap 怎么存的？内存还是 Redis？
回答：双层存储——Redis 持久化 + JVM 双 Buffer 内存加速。
     查询时直接从 JVM 内存读（纳秒级），Redis 用于节点重启后的数据恢复。

追问2：双 Buffer 切换时如果有查询正在执行怎么办？
回答：Java 引用赋值是原子操作。切换只是改变了 volatile 指针。
     正在执行的查询已经拿到了旧 Buffer 的引用，不受切换影响。
     旧 Buffer 延迟 5 分钟后才清理，保证正在执行的查询安全完成。

追问3：5 分钟够吗？如果有个查询执行了 6 分钟呢？
回答：圈选预估的单次查询不会超过 3 秒（超时机制）。5 分钟的延迟
     是为了保证极端情况（比如多次重试、GC 停顿）。实际上查询拿到
     引用后，即使 Buffer 引用被置 null，Java GC 也不会回收正在被
     引用的对象。5 分钟只是让代码更安全，实际 GC 保证了引用安全。

追问4：分布式 Bitmap 怎么保证各节点数据一致？
回答：ZooKeeper 协调的 barrier 机制。所有节点加载完新版本后
     在 ZK 注册就绪状态，全部就绪后统一切换。如果某节点加载
     失败，不切换到新版本，继续使用旧版本。
```

### 10.2 追问链二：一致性深入

```
面试官：你说用最终一致性，那不一致窗口是多久？
回答：取决于场景——
     Bitmap 与 CK 之间：通常 < 1 小时（等两条链路都完成）
     人群包与标签之间：最多 24 小时（T+1 更新）
     实时标签与 Bitmap 之间：最多 24 小时，但有增量 Bitmap 补偿

追问1：增量 Bitmap 补偿精确吗？
回答：不完全精确。增量 Bitmap 只能处理枚举标签的变更（city 从北京
     变为上海）。数值标签的变更（消费金额从 2000 变为 5000）无法
     用增量 Bitmap 表示。所以增量补偿只是"尽力而为"，最终靠每天
     凌晨的全量重建保证准确性。

追问2：有没有考虑过强一致性方案？
回答：考虑过但放弃了。强一致性意味着每次标签更新都要同步更新
     Bitmap 和 CK，这需要分布式事务。1 亿用户每天有几千万次标签
     更新，分布式事务的开销不可接受。而且圈选本身是运营分析场景，
     对实时性的要求是"秒级预估 + 分钟级精确"，不是"毫秒级精确"。
     最终一致性完全满足业务需求，代价小得多。

追问3：如果运营就是要求"我改了标签，立刻能圈出来"呢？
回答：如果是这个需求，不应该用离线圈选，应该用实时圈选路径。
     实时路径直接查 Redis 实时标签 + 内存规则引擎判断，延迟 < 5ms。
     但实时路径只适合"给定一个用户判断是否在人群中"，不适合
     "从 1 亿用户中筛选出满足条件的所有用户"。
     后者天然是批量操作，秒级响应已经是极致优化。
```

### 10.3 追问链三：高可用深入

```
面试官：你说有三级降级，验证过吗？
回答：验证过。我们每月做一次容灾演练：
     ① 模拟 Redis 单节点宕机 → 验证 Sentinel 自动切换 + 断路器降级
     ② 模拟 CK 全部不可用 → 验证降级到缓存结果
     ③ 模拟 Bitmap 服务超时 → 验证降级到 CK 路径
     演练在预发环境进行，每次产出演练报告。

追问1：演练中发现过问题吗？
回答：发现过两个关键问题：
     ① 断路器阈值设置不合理——Bitmap 的慢调用阈值设得太高（1s），
        导致 Bitmap 超时后断路器迟迟不打开，用户感知到持续的慢。
        调整为 300ms 后问题解决。
     ② CK 降级路径的缓存为空——因为正常情况下很少走 CK 预估，
        CK 路径的结果缓存几乎是空的。降级到 CK 时每个请求都要
        实时计算。解决方案是定期用 CK 做影子计算（shadow traffic），
        保持缓存热度。

追问2：99.99% 可用性怎么计算的？
回答：99.99% 意味着每年最多 52 分钟不可用。
     我们的计算方式：
       可用性 = 1 - (降级到 L3 的时间 / 总时间)
     只有完全不可用（L3 降级）才算不可用。
     部分降级（L1 返回 CK 结果、L2 返回缓存结果）都算可用，
     因为用户仍然能拿到结果（虽然可能不是最新的或有近似误差）。

追问3：如果真的达不到 99.99% 怎么办？
回答：首先定位短板。去年我们的可用性是 99.95%，差距来自两次
     CK 集群升级引起的计划内停机（每次 15 分钟）。
     改进措施：CK 升级改为滚动升级（逐 Replica 重启，不停服务）。
     今年到目前为止没有出现非计划停机。
```

### 10.4 追问链四：分布式协调

```
面试官：为什么用 ZooKeeper 协调 Bitmap 切换，不用其他方案？
回答：ZK 提供了我们需要的两个原语——
     ① Watch 机制：所有节点注册就绪后统一触发切换
     ② 临时节点：节点宕机时自动删除注册信息，方便检测故障
     其他方案如 Redis Pub/Sub 也能做，但不如 ZK 可靠
     （Redis Pub/Sub 没有持久化，消息丢失无法重放）

追问1：ZK 成为了单点依赖？
回答：ZK 本身是 3 节点集群，容忍 1 节点故障。
     即使 ZK 全挂，也只影响 Bitmap 版本切换，不影响查询。
     查询始终使用当前 active 版本。最坏情况是今天用昨天的 Bitmap，
     对业务影响很小。

追问2：如果要去掉 ZK 依赖呢？
回答：可以用 "分布式时间窗口" 替代 ZK 协调：
     ① 所有节点约定在固定时间点切换（如 03:50:00）
     ② 每个节点独立检查本地 standby 是否加载完成
     ③ 到了约定时间且本地就绪 → 独立切换
     ④ 各节点切换时间最多差几秒（NTP 同步误差），可以接受
     这个方案简单，但失去了"全部就绪才切换"的保证。
     如果某个节点加载失败，它不会切换，导致版本不一致。
     需要加上版本校验和自动修复来兜底。
```
