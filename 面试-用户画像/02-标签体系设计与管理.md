## 1. 标签体系整体架构

### 1.1 标签体系在画像平台中的位置

```
数据采集层 → 数据清洗/加工层 → 标签计算层 → 标签存储层 → 标签服务层 → 应用层
                                    ↑
                              标签管理平台（元数据、质量、生命周期）
```

### 1.2 核心设计原则

| 原则 | 说明 | 实践 |
|------|------|------|
| **统一性** | 全公司一套标签体系，避免烟囱式建设 | 统一标签注册中心，标签ID全局唯一 |
| **可扩展性** | 新业务线能快速接入新标签 | 标签模板 + 标签工厂模式 |
| **可度量** | 每个标签有质量指标 | 覆盖率、准确率、时效性三大指标 |
| **可治理** | 过期标签能下线，重复标签能合并 | 生命周期管理 + 血缘追踪 |

### 1.3 我负责的核心工作

```
1. 设计标签元数据模型（标签注册中心）
2. 开发标签计算框架（Flink + Spark 双引擎）
3. 搭建标签质量监控体系
4. 设计标签存储层（HBase + Redis + ClickHouse）
5. 提供标签查询 API（单用户查询 + 批量人群圈选）
```

## 2. 标签分类与层级设计

### 2.1 按数据类型分类

#### 事实标签（Fact Tag）
```
定义：直接从原始数据中提取，无需计算
示例：性别、年龄、注册时间、手机品牌
特点：准确率高、计算成本低
更新频率：通常一次性或低频更新
```

#### 统计标签（Statistical Tag）
```
定义：基于用户行为数据聚合计算
示例：最近7天订单数、月均消费金额、最常访问品类
特点：需要定期计算、有时间窗口
更新频率：T+1 离线计算为主，部分实时计算
```

#### 规则标签（Rule-Based Tag）
```
定义：基于业务规则对统计结果进行分层
示例：
  消费能力：高（月均>5000）/ 中（1000-5000）/ 低（<1000）
  活跃度：高活（日均打开>3次）/ 中活 / 低活 / 流失（>30天未登录）
特点：规则可配置、需要业务方参与定义
```

#### 算法标签（Algorithm Tag）
```
定义：通过机器学习模型预测
示例：流失概率、购买意向、价格敏感度、兴趣偏好 Top-N
特点：准确率依赖模型质量、需要定期重训
更新频率：模型定期重训后批量更新
```

### 2.2 按实时性分类

| 类型 | 时效 | 计算引擎 | 示例 |
|------|------|---------|------|
| 离线标签 | T+1 | Spark/Hive | 消费等级、用户价值分层 |
| 准实时标签 | 小时级 | Flink 微批 | 最近1小时浏览品类 |
| 实时标签 | 秒级 | Flink 流处理 | 当前正在浏览的商品、实时位置 |

### 2.3 标签层级结构设计

```
一级类目（域）
├── 基础属性
│   ├── 人口属性（性别、年龄、城市）
│   ├── 设备属性（手机品牌、操作系统、分辨率）
│   └── 账号属性（注册时间、认证状态、会员等级）
│
├── 行为特征
│   ├── 访问行为（日均访问次数、最近访问时间、访问时段分布）
│   ├── 搜索行为（搜索关键词 Top-N、搜索频率）
│   ├── 浏览行为（浏览品类偏好、浏览深度、停留时长）
│   └── 交互行为（点赞、收藏、分享、评论频率）
│
├── 交易特征
│   ├── 消费能力（月均消费、客单价、消费频率）
│   ├── 消费偏好（偏好品类、偏好品牌、价格区间）
│   ├── 支付特征（偏好支付方式、优惠券敏感度）
│   └── 售后特征（退货率、投诉率）
│
├── 社交特征
│   ├── 社交活跃度（发帖频率、互动率）
│   ├── 影响力（粉丝数、被转发数）
│   └── 社交圈层（所属社群、社交关系链）
│
└── 预测标签
    ├── 流失预警（流失概率、预计流失时间）
    ├── 购买意向（近期购买概率、意向品类）
    └── 生命周期（新客/活跃/沉默/流失/回流）
```

### 2.4 面试话术

> **面试官问：你们的标签体系是怎么设计的？**
>
> 我们的标签体系采用 **"域-类目-标签"** 三级结构。一级是域（基础属性、行为特征、交易特征等），二级是类目（消费能力、浏览行为等），三级是具体标签。
>
> 标签按生产方式分为四类：**事实标签**直接从用户资料提取；**统计标签**通过 Spark/Flink 聚合计算；**规则标签**基于业务规则做分层映射；**算法标签**由 ML 模型产出。
>
> 按时效性分为**离线**（T+1，Spark）、**准实时**（小时级，Flink 微批）和**实时**（秒级，Flink 流处理）三种。大概 70% 是离线标签，20% 准实时，10% 实时，因为大部分标签不需要秒级更新。

## 3. 标签元数据管理

### 3.1 标签注册中心设计

```java
// 标签元数据核心模型
public class TagMeta {
    // 基本信息
    private Long tagId;              // 全局唯一标签ID
    private String tagCode;          // 标签编码，如 user.trade.monthly_amount
    private String tagName;          // 标签名称，如 "月均消费金额"
    private String tagDesc;          // 标签描述

    // 分类信息
    private String domain;           // 域：基础属性/行为特征/交易特征
    private String category;         // 类目：消费能力/浏览行为
    private Integer level;           // 标签层级

    // 技术属性
    private TagType tagType;         // FACT/STATISTICAL/RULE/ALGORITHM
    private DataType dataType;       // STRING/LONG/DOUBLE/ENUM/JSON
    private TimelType timeType;      // OFFLINE/NEAR_REALTIME/REALTIME
    private String computeEngine;    // SPARK/FLINK/HIVE
    private String computeLogic;     // SQL 或 计算逻辑描述

    // 质量属性
    private Double coverageRate;     // 覆盖率
    private Double accuracyRate;     // 准确率
    private String updateFrequency;  // 更新频率：DAILY/HOURLY/REALTIME
    private LocalDateTime lastComputeTime; // 最近计算时间

    // 管理属性
    private String owner;            // 标签负责人
    private String bizLine;          // 所属业务线
    private TagStatus status;        // DRAFT/ONLINE/OFFLINE/DEPRECATED
    private LocalDateTime createTime;
    private LocalDateTime onlineTime;
    private LocalDateTime offlineTime;

    // 血缘信息
    private List<String> upstreamTables; // 依赖的上游数据表
    private List<String> downstreamTags; // 下游依赖此标签的标签
}
```

### 3.2 标签编码规范

```
格式：{domain}.{category}.{tag_name}

示例：
  user.base.gender                    → 用户-基础-性别
  user.trade.monthly_amount           → 用户-交易-月均消费
  user.behavior.visit_count_7d        → 用户-行为-近7日访问次数
  user.predict.churn_probability      → 用户-预测-流失概率

命名规则：
  - 全小写，下划线分隔
  - 带时间窗口的标签后缀：_7d / _30d / _90d
  - 布尔标签前缀：is_（is_new_user, is_vip）
  - 枚举标签：用明确的枚举值，不用 0/1/2
```

### 3.3 标签注册流程

```
① 业务方提需求 → 填写标签需求表（名称、口径、更新频率、预期覆盖率）
② 数据团队评审 → 检查是否已有类似标签、数据源是否可获取
③ 开发与测试 → 编写计算逻辑、验证准确性
④ 标签上线 → 注册到元数据中心、挂载到标签体系树
⑤ 质量监控 → 持续监控覆盖率、准确率、计算时效
```

### 3.4 血缘追踪

```
目的：当上游数据源变更时，自动识别受影响的标签

实现：
  上游表 orders → 标签 monthly_amount → 标签 consume_level → 人群包 "高消费用户"

  如果 orders 表结构变更：
  ① 通过血缘关系找到下游标签 monthly_amount
  ② 通知标签负责人检查计算逻辑
  ③ 标记可能受影响的人群包

技术实现：
  - 解析 Spark/Flink SQL 的 AST，自动提取表级血缘
  - 每次标签计算任务完成后，上报血缘关系到元数据中心
  - Atlas / 自研血缘系统
```

### 4.3 标签计算框架设计

```java
/**
 * 标签计算抽象框架
 * 所有标签计算任务实现此接口，框架负责调度、质量检查、结果写入
 */
public interface TagComputeTask {

    /** 标签元信息 */
    TagMeta getTagMeta();

    /** 依赖的上游数据是否就绪 */
    boolean isDataReady(String dt);

    /** 执行计算（返回 user_id -> tag_value 映射） */
    Dataset<Row> compute(SparkSession spark, String dt);

    /** 质量校验规则 */
    List<QualityRule> qualityRules();
}

// 使用示例：月均消费标签
public class MonthlyAmountTag implements TagComputeTask {

    @Override
    public Dataset<Row> compute(SparkSession spark, String dt) {
        return spark.sql(
            "SELECT user_id, " +
            "       AVG(order_amount) as monthly_avg_amount " +
            "FROM dwd.orders " +
            "WHERE dt >= date_sub('" + dt + "', 30) " +
            "GROUP BY user_id"
        );
    }

    @Override
    public List<QualityRule> qualityRules() {
        return Arrays.asList(
            new CoverageRule(0.6),        // 覆盖率 >= 60%
            new NullRateRule(0.05),        // 空值率 <= 5%
            new FluctuationRule(0.2)       // 日环比波动 <= 20%
        );
    }
}
```

### 4.4 标签加工 SQL 配置化

```yaml
# 标签可通过配置文件定义，无需写代码
- tag_code: user.trade.consume_level
  tag_name: 消费等级
  compute_type: SQL
  engine: SPARK
  schedule: "0 1 * * *"   # 每天凌晨 1 点
  sql: |
    SELECT
      user_id,
      CASE
        WHEN avg_amount >= 5000 THEN '高'
        WHEN avg_amount >= 1000 THEN '中'
        ELSE '低'
      END as tag_value
    FROM (
      SELECT user_id, AVG(order_amount) as avg_amount
      FROM dwd.orders
      WHERE dt >= date_sub(current_date(), 30)
      GROUP BY user_id
    )
  quality:
    min_coverage: 0.5
    max_null_rate: 0.05
  depends_on:
    - dwd.orders
```

## 5. 实时标签与离线标签

### 5.1 实时标签架构

```
                         ┌──────────────┐
Kafka 行为日志 ──────────→│  Flink 作业   │──→ Redis（实时标签缓存）
                         │              │──→ HBase（持久化）
Kafka 交易事件 ──────────→│  实时标签计算  │──→ Kafka（下游消费）
                         └──────────────┘
                               ↑
                         标签规则配置中心
```

### 5.2 Flink 实时标签计算示例

```java
/**
 * 实时计算用户近1小时浏览品类偏好
 */
public class RealtimeCategoryPreference {

    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
        env.enableCheckpointing(60_000);

        // 消费行为日志
        DataStream<UserAction> actions = env
            .addSource(new FlinkKafkaConsumer<>("user_actions", ...))
            .filter(a -> "view_product".equals(a.getActionType()));

        // 按用户分组，1小时滑动窗口，步长5分钟
        actions
            .keyBy(UserAction::getUserId)
            .window(SlidingEventTimeWindows.of(Time.hours(1), Time.minutes(5)))
            .process(new CategoryPreferenceFunction())
            .addSink(new RedisSink<>(redisConfig, new TagRedisMapper()));
    }
}

/**
 * 窗口函数：计算用户在窗口内浏览最多的 Top3 品类
 */
public class CategoryPreferenceFunction
        extends ProcessWindowFunction<UserAction, TagResult, String, TimeWindow> {

    @Override
    public void process(String userId, Context ctx,
                       Iterable<UserAction> actions, Collector<TagResult> out) {
        // 统计每个品类的浏览次数
        Map<String, Integer> categoryCount = new HashMap<>();
        for (UserAction action : actions) {
            categoryCount.merge(action.getCategory(), 1, Integer::sum);
        }

        // 取 Top3
        List<String> top3 = categoryCount.entrySet().stream()
            .sorted(Map.Entry.<String, Integer>comparingByValue().reversed())
            .limit(3)
            .map(Map.Entry::getKey)
            .collect(Collectors.toList());

        out.collect(new TagResult(userId, "realtime_prefer_category",
                                  JSON.toJSONString(top3)));
    }
}
```

### 5.3 Lambda 架构：离线修正 + 实时补充

```
设计理念：
  离线标签 → 准确性高、覆盖面广、但时效性差（T+1）
  实时标签 → 时效性好、但可能有计算偏差

合并策略：
  ① 查询时合并（Query-time merge）
     先查 Redis（实时标签），查不到则查 HBase（离线标签）

  ② 写入时合并（Write-time merge）
     离线标签每天凌晨批量覆盖 HBase
     实时标签实时更新 Redis，设置 TTL
     两层独立，查询时 Redis 优先

  ③ 混合策略（我们采用的方案）
     - 纯离线标签（性别、年龄）→ 只在 HBase
     - 纯实时标签（当前浏览品类）→ 只在 Redis，TTL 2小时
     - 混合标签（消费等级）→ HBase 存离线版本，Redis 存实时版本
       查询时 Redis 优先，miss 后降级 HBase
```

### 5.4 实时标签 vs 离线标签对比

| 维度 | 离线标签 | 实时标签 |
|------|---------|---------|
| 时效性 | T+1 | 秒级 ~ 分钟级 |
| 计算引擎 | Spark / Hive | Flink |
| 准确性 | 高（全量计算） | 较高（窗口聚合） |
| 成本 | 低（批处理） | 高（7x24 运行） |
| 覆盖率 | 高（全量用户） | 低（只覆盖活跃用户） |
| 存储 | Hive → HBase | Redis / HBase |
| 适用场景 | 用户分层、离线营销 | 实时推荐、实时风控 |

## 6. 标签存储方案设计

### 6.1 多层存储架构

```
┌─────────────────────────────────────────────────┐
│                   查询服务层                      │
│            TagQueryService API                   │
└───────┬──────────────┬──────────────┬────────────┘
        │              │              │
   ┌────▼────┐   ┌─────▼─────┐  ┌────▼──────┐
   │  Redis   │   │   HBase   │  │ ClickHouse │
   │ 热数据   │   │  全量KV   │  │  圈选OLAP  │
   │ 实时标签  │   │  在线查询  │  │  人群分析   │
   └─────────┘   └───────────┘  └───────────┘

   场景：单用户实时查询   单用户全量标签查询    批量人群圈选
   延迟：< 1ms           < 10ms               < 1s（亿级用户）
```

### 6.2 HBase 标签存储设计

```
RowKey 设计：
  反转用户ID（避免热点） + 用户ID
  例如：321_123456789  （123456789 反转前3位 → 321）

  或者：Hash(userId) % 256 的十六进制 + userId
  例如：3f_123456789

Column Family 设计：
  cf:base    → 基础属性标签（读频率高、数据量小）
  cf:behavior → 行为标签（读频率中、数据量中）
  cf:trade   → 交易标签（读频率中、数据量中）
  cf:predict → 预测标签（读频率低、数据量小）

Column Qualifier：
  标签编码作为列名
  例如：cf:base:gender, cf:trade:monthly_amount

优势：
  - 稀疏存储，用户没有的标签不占空间
  - 单用户查询 O(1) 时间复杂度
  - 新增标签无需改表结构（动态列）
```

```java
// HBase 标签写入示例
public class TagHBaseWriter {

    public void writeUserTags(String userId, Map<String, String> tags) {
        Put put = new Put(Bytes.toBytes(buildRowKey(userId)));

        for (Map.Entry<String, String> tag : tags.entrySet()) {
            String[] parts = tag.getKey().split("\\.");
            // user.trade.monthly_amount → cf=trade, qualifier=monthly_amount
            String cf = parts[1];
            String qualifier = parts[2];
            put.addColumn(
                Bytes.toBytes(cf),
                Bytes.toBytes(qualifier),
                Bytes.toBytes(tag.getValue())
            );
        }

        table.put(put);
    }

    private String buildRowKey(String userId) {
        // 反转前3位 + 原始 userId，分散热点
        String reversed = new StringBuilder(userId.substring(0, 3)).reverse().toString();
        return reversed + "_" + userId;
    }
}
```

### 6.3 Redis 标签缓存设计

```
数据结构选择：Hash

Key:   tag:{userId}
Field: 标签编码
Value: 标签值

示例：
  tag:123456789
    gender      → "男"
    age         → "28"
    consume_level → "高"
    churn_prob  → "0.15"

过期策略：
  - 实时标签：TTL 2小时（实时计算持续刷新）
  - 缓存标签：TTL 24小时（离线数据的热缓存）
  - 不设 TTL 的标签：基础属性（性别、年龄，变化极少）

内存估算：
  单用户 50 个标签，平均每个标签 key 30B + value 20B = 50B
  50 个标签 × 50B = 2.5KB/用户
  1000 万活跃用户 × 2.5KB = 25GB
  → 一台 64GB Redis 实例可以承载
```

## 7. 标签质量保障体系

### 7.1 质量指标定义

```
① 覆盖率 = 有标签值的用户数 / 总用户数
   - 性别标签覆盖率应 > 90%
   - 消费标签覆盖率 > 50%（未消费用户可以没有）

② 准确率 = 抽样验证正确的标签数 / 抽样总数
   - 事实标签准确率应 > 99%
   - 规则标签准确率应 > 95%
   - 算法标签准确率应 > 80%

③ 时效性 = 标签实际产出时间 - 预期产出时间
   - 离线标签应在 T+1 凌晨 3 点前就绪
   - 实时标签端到端延迟 < 30 秒

④ 稳定性 = 标签值的日环比变化幅度
   - 日环比波动 > 20% 需要告警排查
   - 防止因数据源异常导致标签突变
```

### 7.2 质量检查流水线

```java
public class TagQualityChecker {

    public QualityReport check(String tagCode, String dt) {
        QualityReport report = new QualityReport(tagCode, dt);

        // 1. 覆盖率检查
        long totalUsers = getTotalUserCount();
        long taggedUsers = getTaggedUserCount(tagCode, dt);
        double coverage = (double) taggedUsers / totalUsers;
        report.setCoverage(coverage);

        // 2. 空值率检查
        long nullCount = getNullValueCount(tagCode, dt);
        double nullRate = (double) nullCount / taggedUsers;
        report.setNullRate(nullRate);

        // 3. 日环比波动检查
        long yesterdayCount = getTaggedUserCount(tagCode, yesterday(dt));
        double fluctuation = Math.abs((double)(taggedUsers - yesterdayCount) / yesterdayCount);
        report.setFluctuation(fluctuation);

        // 4. 枚举值分布检查（防止异常值）
        if (isEnumTag(tagCode)) {
            Map<String, Long> distribution = getValueDistribution(tagCode, dt);
            report.setDistribution(distribution);
        }

        // 5. 判定是否通过
        report.setPass(
            coverage >= getMinCoverage(tagCode) &&
            nullRate <= getMaxNullRate(tagCode) &&
            fluctuation <= getMaxFluctuation(tagCode)
        );

        return report;
    }
}
```

### 7.3 质量监控告警

```
告警规则：
  ① 覆盖率低于阈值 → 钉钉/飞书告警 + 标签降级
  ② 日环比波动过大 → 人工审核后决定是否更新
  ③ 计算任务超时 → 重试 + 告警
  ④ 上游数据源异常 → 阻断下游标签计算

降级策略：
  当质量检查不通过时：
  - 不更新线上标签（继续使用前一天的数据）
  - 标记该标签为"降级中"
  - 通知标签负责人排查
```

## 9. ID-Mapping 与 One ID

### 9.1 问题背景

```
同一个用户可能有多个 ID：
  - 手机号：13800001234
  - 设备ID（IDFA/OAID）：abc-def-123
  - 微信 OpenID：wx_xxxx
  - App 登录 UID：100001
  - Cookie ID：cookie_yyyy

问题：
  同一用户在 App 上浏览了商品（UID=100001），
  在微信小程序下了单（OpenID=wx_xxxx），
  如何知道这是同一个人？如何合并标签？
```

### 9.2 ID-Mapping 方案

```
方案一：确定性匹配（Deterministic）
  通过登录行为建立绑定关系
  用户用手机号在 App 登录 → UID 和手机号绑定
  用户用同一手机号在小程序登录 → OpenID 和手机号绑定
  → UID 和 OpenID 通过手机号关联

方案二：概率性匹配（Probabilistic）
  通过设备指纹、IP、行为特征等推断
  同一设备 ID + 相似行为 → 大概率是同一人
  准确率较低（80-90%），一般作为补充手段

我们采用的方案：以确定性匹配为主
  核心ID：手机号 → 生成全局唯一 OneID
  映射表：id_mapping(id_type, id_value, one_id, bindTime)
```

### 9.3 OneID 数据模型

```sql
-- ID 映射表
CREATE TABLE id_mapping (
    one_id      BIGINT    COMMENT '全局唯一用户ID',
    id_type     VARCHAR(20) COMMENT 'PHONE/UID/DEVICE_ID/OPENID/COOKIE',
    id_value    VARCHAR(128) COMMENT 'ID值',
    confidence  DOUBLE    COMMENT '置信度 0-1',
    bind_time   DATETIME  COMMENT '绑定时间',
    source      VARCHAR(50) COMMENT '绑定来源：LOGIN/REGISTER/INFER',
    PRIMARY KEY (id_type, id_value),
    INDEX idx_one_id (one_id)
);

-- 查询示例：通过任意 ID 找到 OneID
SELECT one_id FROM id_mapping
WHERE id_type = 'OPENID' AND id_value = 'wx_xxxx';
```

### 9.4 ID 冲突处理

```
场景：两个已有 OneID 的用户被发现是同一人

例如：
  OneID=1001 绑定了 PHONE=138xxx
  OneID=1002 绑定了 UID=500001
  某天用户用手机号 138xxx 登录了 App，产生了 UID=500001

处理策略：
  ① 合并（Merge）：将 1002 的所有 ID 和标签合并到 1001
  ② 选择保留更早创建的 OneID 作为主 ID
  ③ 标签合并规则：
     - 事实标签：取最新值
     - 统计标签：求和或取最大值
     - 算法标签：重新计算
  ④ 在 id_mapping 表中更新映射关系
```

## 11. 面试高频问题与深度解答

### Q1: 你们标签存储用什么方案？为什么不用 MySQL？

**回答：**

> 我们用 **HBase + Redis + ClickHouse** 三层存储。
>
> **不用 MySQL 的核心原因是标签的"宽表"特性：**
> 一个用户可能有几百个标签，而且标签会不断新增。MySQL 的列数有上限（1000+），每次加标签都要 ALTER TABLE，对亿级大表做 DDL 是不可接受的。
>
> HBase 天然支持**动态列**——列名就是标签编码，新增标签不需要改表结构。同时 HBase 是**稀疏存储**的，用户没有的标签不占空间，非常适合标签场景。
>
> Redis 用于热数据缓存，实时标签直接写 Redis。ClickHouse 用于多条件人群圈选，列式存储对 "city = '北京' AND consume_level = '高'" 这类查询有极好的性能。

### Q2: 标签覆盖率怎么保证？

**回答：**

> 标签覆盖率保证分三个层面：
>
> **1. 数据源覆盖：** 接入尽可能多的数据源（App 埋点、服务端日志、第三方数据），通过 ID-Mapping 将散落在各渠道的行为归到同一用户下。
>
> **2. 计算逻辑优化：** 对于可以"推断"的标签，用默认值填充。比如用户没填性别，但根据浏览和购买行为可以用模型预测。注册城市没填，但有 IP 地址可以做地域映射。
>
> **3. 质量监控：** 每个标签有最低覆盖率阈值，低于阈值会触发告警。比如我们的性别标签要求覆盖率 > 90%，如果某天降到 85%，会阻断下游计算并通知排查。

### Q3: 实时标签和离线标签不一致怎么办？

**回答：**

> 不一致是正常的，因为两者的计算口径和时间窗口不同。
>
> **我们的策略是"实时优先、离线修正"：**
>
> 查询时，先查 Redis（实时标签），有则返回实时版本。没有则降级查 HBase（离线标签）。
>
> 每天凌晨，离线计算会**全量覆盖** HBase，相当于做一次"修正"。比如实时计算的"近7天消费金额"可能因为窗口边界等原因有微小误差，离线的全量 Spark 计算会修正这个值。
>
> 对于**决策敏感的标签**（如风控相关），我们会在代码中明确标注查询来源，让业务方知道这个值是实时计算的还是离线的，由业务方决定是否需要等离线修正后再使用。

### Q4: One ID 怎么处理手机号换绑？

**回答：**

> 手机号换绑是 ID-Mapping 中最棘手的问题之一。
>
> **我们的处理策略：**
> - 旧手机号与 OneID 的绑定关系标记为"已失效"，但保留历史记录
> - 新手机号绑定到同一个 OneID
> - 如果新手机号之前已经绑定了另一个 OneID，触发**合并流程**
>
> 合并时有一条核心原则：**UID（App登录ID）的权重最高**。因为手机号可以换，设备可以换，但 App 账号通常是稳定的。合并后标签取最新值，行为数据全部归到主 OneID 下。
>
> 为了减少合并冲突，我们还加了一个**冷却期**：手机号解绑后 7 天内，如果被新用户注册，不会立即建立绑定关系，而是标记为"待确认"。

### Q5: 标签计算任务失败怎么办？

**回答：**

> 我们有完整的**容错和降级机制**：
>
> **1. 自动重试：** Spark/Flink 任务失败后自动重试 3 次，间隔递增（1分钟、5分钟、15分钟）。
>
> **2. 上游阻断：** 如果是上游数据源异常（比如 Hive 分区没就绪），标签计算任务会等待而不是用不完整的数据计算。超时后告警。
>
> **3. 降级保护：** 如果重试全部失败，线上服务继续使用前一天的标签数据。标签带有版本号和计算时间戳，查询方可以判断标签是否过期。
>
> **4. 补算机制：** 问题修复后，支持指定日期范围的批量补算。补算会覆盖当天的标签值并重新做质量检查。

### Q6: 标签数据量大了之后怎么优化？

**回答：**

> 从三个维度优化：
>
> **1. 计算优化：**
> - Spark 任务做好分区裁剪，只计算增量数据
> - 标签依赖关系做 DAG 调度，并行计算无依赖的标签
> - 统计标签用增量计算（比如"近30天消费"，每天只加当天减去31天前的）
>
> **2. 存储优化：**
> - HBase 做预分区（256个region），避免热点
> - ClickHouse 合理设计分区键和排序键
> - Redis 只存热标签（最近24小时有查询的用户），冷数据不缓存
>
> **3. 查询优化：**
> - 三级缓存：Caffeine → Redis → HBase
> - 批量查询用 HBase MultiGet
> - 圈选查询用 ClickHouse 物化视图预聚合
