## 1. 人群圈选概述

### 1.1 什么是人群圈选

```
人群圈选 = 根据用户标签组合条件，从全量用户中筛选出符合条件的用户集合

典型场景：
  运营人员想推送一批优惠券给 "北京 + 近30天消费>500 + 非会员" 的用户
  → 输入：标签组合条件
  → 输出：符合条件的用户 ID 列表（人群包）
```

### 1.2 圈选的两大核心需求

```
① 人群预估（秒级）
   用户在配置圈选条件时，实时显示预估人数
   要求：亿级用户 → 秒级返回预估人数
   精度：允许 5-10% 误差

② 人群导出（分钟级）
   确认条件后，生成精确的用户 ID 列表
   要求：精确无误、可下载/推送到下游系统
   延迟：分钟级可接受
```

### 1.3 系统整体架构

```

│                   前端圈选界面                           │
│  ┌──────────────────────────────────────────────────┐  │

│  └──────────────────────────────────────────────────┘  │

│  │ 规则解析引擎  │  │ 预估计算引擎  │  │ 精确圈选引擎  │ │
│  └─────────────┘  └──────────────┘  └───────────────┘ │
```

## 2. 离线圈选架构设计

### 2.1 基于 ClickHouse 的圈选方案

```
为什么选 ClickHouse：
  ① 列式存储：圈选条件只扫描涉及的列，不读无关列
  ② 向量化执行：SIMD 指令加速 filter 操作
  ③ 数据压缩：同一列数据类型相同，压缩比高
  ④ 分区裁剪：按日期分区，只扫描最新数据
  ⑤ 支持复杂条件：AND / OR / IN / BETWEEN 原生支持
```

### 2.2 ClickHouse 表设计

```sql
-- 标签宽表（用于圈选）
CREATE TABLE user_tags_wide ON CLUSTER cluster_1
(
    user_id            UInt64,
    -- 基础属性
    gender             LowCardinality(String),
    age                UInt8,
    city               LowCardinality(String),
    province           LowCardinality(String),
    -- 行为标签
    visit_count_7d     UInt32,
    visit_count_30d    UInt32,
    last_visit_date    Date,
    -- 交易标签
    order_count_30d    UInt32,
    total_amount_30d   Decimal(12, 2),
    consume_level      LowCardinality(String),
    -- 兴趣标签
    prefer_categories  Array(String),
    -- 预测标签
    churn_prob         Float32,
    -- 分区字段
    dt                 Date
)
ENGINE = ReplicatedMergeTree('/clickhouse/tables/{shard}/user_tags_wide', '{replica}')
PARTITION BY dt
ORDER BY (city, consume_level, user_id)
SETTINGS index_granularity = 8192;

-- ORDER BY 设计原则：
-- 把圈选条件中最常出现的维度放在前面
-- city + consume_level 是高频圈选条件
-- 这样 ClickHouse 可以利用主键索引快速跳过不相关的数据块
```

### 2.3 ClickHouse 圈选查询生成

```java
/**
 * 将前端圈选条件转换为 ClickHouse SQL
 */
public class CrowdSelectSqlBuilder {

    public String buildCountSql(CrowdSelectRequest request) {
        StringBuilder sql = new StringBuilder();
        sql.append("SELECT count(DISTINCT user_id) FROM user_tags_wide WHERE dt = '")
           .append(latestDt).append("'");

        for (TagCondition condition : request.getConditions()) {
            sql.append(" AND ");
            sql.append(buildCondition(condition));
        }

        return sql.toString();
    }

    private String buildCondition(TagCondition condition) {
        switch (condition.getOperator()) {
            case EQ:
                return condition.getTagCode() + " = '" + condition.getValue() + "'";
            case IN:
                return condition.getTagCode() + " IN ("
                    + condition.getValues().stream()
                        .map(v -> "'" + v + "'")
                        .collect(Collectors.joining(","))
                    + ")";
            case BETWEEN:
                return condition.getTagCode() + " BETWEEN "
                    + condition.getMinValue() + " AND " + condition.getMaxValue();
            case GT:
                return condition.getTagCode() + " > " + condition.getValue();
            case ARRAY_CONTAINS:
                // ClickHouse Array 查询
                return "has(" + condition.getTagCode() + ", '" + condition.getValue() + "')";
            default:
                throw new IllegalArgumentException("Unknown operator: " + condition.getOperator());
        }
    }
}
```

### 2.4 圈选结果导出

```
两种导出方式：

① 小批量（< 100万用户）→ 直接查 ClickHouse
   SELECT user_id FROM user_tags_wide
   WHERE dt = '2026-03-12' AND city = '北京' AND consume_level = '高'
   → 结果写入 Redis Set 或直接返回

② 大批量（> 100万用户）→ 提交 Spark 任务
   ClickHouse 不适合大批量导出（内存压力大）
   将条件传给 Spark，从 Hive 标签宽表做全量扫描
   结果写入 HDFS，生成人群包文件
```

## 3. 实时圈选架构设计

### 3.1 实时圈选的场景

```
场景一：营销活动实时判断
  用户进入 App → 检查是否属于"高消费+近期活跃"人群 → 弹窗推送

场景二：实时风控
  用户发起交易 → 实时判断是否属于"高风险"人群 → 拦截

场景三：实时推荐
  用户正在浏览 → 实时判断所属人群 → 匹配推荐策略

关键区别：
  离线圈选 = 给定条件，找到所有符合的用户（批量）
  实时圈选 = 给定一个用户，判断是否符合条件（单点）
```

### 3.2 实时圈选架构

```
方案一：规则前置（推荐）
  用户请求 → 查询用户标签 → 在内存中执行规则匹配 → 返回结果

  优点：延迟低（< 5ms）、逻辑清晰
  实现：Redis 存标签 + 内存规则引擎

方案二：人群包预计算
  离线圈选 → 生成人群包 → 存入 Redis Set / Bloom Filter
  用户请求 → 查 Redis SISMEMBER → 返回是否在人群中

  优点：实时查询 O(1)
  缺点：标签更新后人群包需要重算

我们的选择：混合方案
  - 变化频率低的人群包（如"高价值用户"）→ 方案二，定时预计算
  - 变化频率高或条件复杂的 → 方案一，实时规则匹配
```

### 3.3 规则匹配引擎

```java
/**
 * 实时规则匹配引擎
 * 给定一个用户的标签，判断是否符合人群条件
 */
public class RealtimeRuleEngine {

    /**
     * 判断用户是否属于指定人群
     */
    public boolean match(Map<String, Object> userTags, CrowdRule rule) {
        return evaluate(userTags, rule.getRootCondition());
    }

    private boolean evaluate(Map<String, Object> tags, Condition condition) {
        if (condition instanceof LogicCondition) {
            LogicCondition logic = (LogicCondition) condition;
            if (logic.getOperator() == LogicOp.AND) {
                return logic.getChildren().stream()
                    .allMatch(c -> evaluate(tags, c));
            } else {
                return logic.getChildren().stream()
                    .anyMatch(c -> evaluate(tags, c));
            }
        } else {
            TagCondition tagCond = (TagCondition) condition;
            Object value = tags.get(tagCond.getTagCode());
            if (value == null) return false;
            return tagCond.getComparator().compare(value, tagCond.getExpected());
        }
    }
}
```

## 4. Bitmap 与 RoaringBitmap 核心原理

### 4.1 为什么用 Bitmap

```
传统方案的问题：
  "北京用户" 1000万 → SELECT user_id WHERE city='北京' → 1000万个 ID
  "高消费用户" 500万 → SELECT user_id WHERE consume_level='高' → 500万个 ID
  求交集 → 两个千万级 Set 求交集 → 内存大、速度慢

Bitmap 方案：
  "北京用户" → 一个 Bitmap，第 i 位为 1 表示用户 i 在北京
  "高消费用户" → 一个 Bitmap
  求交集 → 两个 Bitmap 做 AND 运算 → CPU 位运算，极快

性能对比（1亿用户）：
  HashSet 交集：~10秒，内存 ~2GB
  Bitmap AND：  ~100ms，内存 ~12.5MB（1亿 bit = 12.5MB）
```

### 4.2 普通 Bitmap 的问题

```
如果用户 ID 范围很大（比如 0 ~ 100亿），但实际用户只有 1 亿：
  普通 Bitmap 需要 100亿 bit = 1.25GB → 空间浪费严重

RoaringBitmap 的核心思想：分桶 + 自适应容器

将 32 位整数分为两部分：
  高 16 位 → 桶号（最多 65536 个桶）
  低 16 位 → 桶内的值

每个桶根据数据密度选择不同的容器类型：
  - ArrayContainer：元素少（< 4096个）→ 排序数组，省空间
  - BitmapContainer：元素多（≥ 4096个）→ 65536 bit 的 bitmap
  - RunContainer：连续区间多 → 用 (start, length) 对存储
```

### 4.3 RoaringBitmap 在圈选中的应用

```java
/**
 * 基于 RoaringBitmap 的人群圈选引擎
 */
public class BitmapCrowdEngine {

    // 每个标签值对应一个 Bitmap
    // key: "city=北京" → Bitmap（所有在北京的用户 ID）
    // key: "consume_level=高" → Bitmap（所有高消费用户 ID）
    private Map<String, RoaringBitmap> tagBitmaps;

    /**
     * 执行圈选
     * 条件：city ∈ [北京,上海] AND consume_level = 高
     */
    public RoaringBitmap select(List<CrowdCondition> conditions) {
        RoaringBitmap result = null;

        for (CrowdCondition cond : conditions) {
            RoaringBitmap condBitmap = getConditionBitmap(cond);

            if (result == null) {
                result = condBitmap.clone();
            } else {
                // AND 条件 → Bitmap 求交集
                result.and(condBitmap);
            }
        }

        return result;  // result.getCardinality() = 人群数量
    }

    private RoaringBitmap getConditionBitmap(CrowdCondition cond) {
        if (cond.getOperator() == Operator.IN) {
            // IN 条件 → 多个 Bitmap 求并集
            RoaringBitmap union = new RoaringBitmap();
            for (String val : cond.getValues()) {
                String key = cond.getTagCode() + "=" + val;
                RoaringBitmap bm = tagBitmaps.get(key);
                if (bm != null) {
                    union.or(bm);
                }
            }
            return union;
        } else {
            // EQ 条件
            String key = cond.getTagCode() + "=" + cond.getValue();
            return tagBitmaps.getOrDefault(key, new RoaringBitmap());
        }
    }
}
```

### 4.4 Bitmap 预构建流程

```
离线预构建（每天凌晨）：

① Spark 扫描标签宽表
② 对每个枚举标签的每个值，构建 RoaringBitmap
③ 序列化后存储到 Redis / 本地文件

预构建示例：
  标签 gender：
    gender=男 → RoaringBitmap{1, 3, 5, 7, ...}
    gender=女 → RoaringBitmap{2, 4, 6, 8, ...}
  标签 city：
    city=北京 → RoaringBitmap{1, 2, 5, 100, ...}
    city=上海 → RoaringBitmap{3, 4, 7, 200, ...}
  标签 consume_level：
    consume_level=高 → RoaringBitmap{1, 5, 100, ...}

存储大小估算（1亿用户）：
  假设 50 个枚举标签，每个平均 5 个枚举值 = 250 个 Bitmap
  每个 Bitmap 平均大小 ~5MB（RoaringBitmap 压缩后）
  总计 250 × 5MB = 1.25GB → 可以全部加载到内存
```

### 4.5 Bitmap 方案的局限

```
适用于枚举标签的精确匹配：city = '北京'
不适用于：
  ① 数值范围查询：amount > 5000 → 需要离散化或用 ClickHouse
  ② 高基数标签：用户姓名、手机号 → Bitmap 数量爆炸
  ③ 实时更新：用户标签变化后需要更新 Bitmap

我们的解决方案：
  枚举标签（性别、城市、消费等级）→ Bitmap 预计算，秒级预估
  数值标签（消费金额、访问次数）→ ClickHouse 实时查询
  混合条件 → 先用 Bitmap 缩小候选集，再用 ClickHouse 做精确筛选
```

### 5.2 规则解析器实现

```java
/**
 * 规则 DSL 解析器
 * 将 JSON 规则转换为可执行的条件树
 */
public class RuleParser {

    public Condition parse(JsonNode ruleNode) {
        String type = ruleNode.get("type").asText();

        if ("AND".equals(type) || "OR".equals(type)) {
            LogicCondition logic = new LogicCondition();
            logic.setOperator("AND".equals(type) ? LogicOp.AND : LogicOp.OR);

            List<Condition> children = new ArrayList<>();
            for (JsonNode child : ruleNode.get("conditions")) {
                children.add(parse(child));
            }
            logic.setChildren(children);
            return logic;
        } else {
            // TAG 条件
            TagCondition tag = new TagCondition();
            tag.setTagCode(ruleNode.get("tagCode").asText());
            tag.setOperator(Operator.valueOf(ruleNode.get("operator").asText()));
            if (ruleNode.has("value")) {
                tag.setValue(ruleNode.get("value"));
            }
            if (ruleNode.has("values")) {
                tag.setValues(parseValues(ruleNode.get("values")));
            }
            return tag;
        }
    }
}
```

### 5.3 规则转 SQL

```java
/**
 * 将规则条件树转换为 ClickHouse SQL WHERE 子句
 */
public class RuleToSqlConverter {

    public String convert(Condition condition) {
        if (condition instanceof LogicCondition) {
            LogicCondition logic = (LogicCondition) condition;
            String joiner = logic.getOperator() == LogicOp.AND ? " AND " : " OR ";
            String children = logic.getChildren().stream()
                .map(this::convert)
                .collect(Collectors.joining(joiner));
            return "(" + children + ")";
        } else {
            TagCondition tag = (TagCondition) condition;
            switch (tag.getOperator()) {
                case EQ:  return tag.getTagCode() + " = " + formatValue(tag.getValue());
                case GT:  return tag.getTagCode() + " > " + formatValue(tag.getValue());
                case LT:  return tag.getTagCode() + " < " + formatValue(tag.getValue());
                case IN:  return tag.getTagCode() + " IN (" + formatValues(tag.getValues()) + ")";
                case BETWEEN: return tag.getTagCode() + " BETWEEN "
                              + formatValue(tag.getMinValue()) + " AND "
                              + formatValue(tag.getMaxValue());
                default: throw new UnsupportedOperationException();
            }
        }
    }
}
```

### 5.4 规则引擎的可扩展性设计

```
扩展点：

① 自定义算子
  除了基本的 EQ/GT/LT/IN，支持注册自定义算子
  如：REGEX（正则匹配）、GEO_IN（地理围栏）、TIME_IN（时间段匹配）

② 自定义函数
  支持在条件中使用函数

③ 标签组合

  通过 Semi-Join 实现
```

## 6. 亿级用户秒级预估

### 6.1 预估的核心挑战

```
用户在前端拖拽条件时，需要实时显示预估人数。

挑战：
  - 条件可能有 5-10 个 AND/OR 组合
  - 用户量 1-2 亿
  - 响应时间 < 1 秒
  - 但不要求精确，允许 ±5% 误差
```

### 6.2 方案一：Bitmap 精确计算（推荐）

```
适用于：枚举标签的精确匹配条件

原理：
  预构建每个 "标签值" 对应的 RoaringBitmap
  圈选 = Bitmap 的 AND / OR 运算
  getCardinality() 返回精确人数

性能：
  1亿用户，3个 AND 条件 → ~50ms
  可以实现秒级预估，且结果是精确值

局限：
  不支持数值范围查询（amount > 5000）
  需要离散化：amount 分桶为 [0-1000, 1000-3000, 3000-5000, 5000+]
```

### 6.3 方案二：预聚合统计表

```sql
-- 预先计算常见标签组合的用户数
CREATE TABLE tag_combination_stats (
    tag_conditions  String,   -- 条件签名：'city=北京,level=高'
    user_count      UInt64,
    dt              Date
) ENGINE = MergeTree() PARTITION BY dt ORDER BY tag_conditions;

-- 前端选择条件后，先查预聚合表
SELECT user_count FROM tag_combination_stats
WHERE tag_conditions = 'city=北京,consume_level=高' AND dt = today();

局限：
  标签组合太多，无法穷举
  只能覆盖高频组合（TOP 1000 种组合）
  未命中时降级到 ClickHouse 实时计算
```

### 6.4 方案三：HyperLogLog 近似估算

```
用于估算不同条件之间交集的基数。

原理：
  每个标签值维护一个 HyperLogLog
  交集估算：|A ∩ B| ≈ |A| + |B| - |A ∪ B|
  并集可以通过 HLL merge 计算

优势：
  空间极小（每个 HLL ~12KB）
  合并速度极快

劣势：
  精度较低（标准误差 ~2%）
  多个条件嵌套交集时误差累积

使用场景：
  作为 Bitmap 方案的补充
  当标签基数很高（上千种取值）不适合建 Bitmap 时使用
```

### 6.5 我们的混合预估方案

```
实际方案 = Bitmap + ClickHouse + 缓存

┌──────────────────────────────────────────────────┐
│ 前端输入条件                                       │
└───────────────────────┬──────────────────────────┘
                        │
                        ▼
              ┌───── 条件分析 ─────┐
              │                   │
    全部是枚举标签？          包含数值范围？
         │                       │
         ▼                       ▼
   Bitmap AND/OR            ClickHouse 查询
   （精确，< 100ms）         （精确，< 1s）
         │                       │
         └───────────┬───────────┘
                     │
               结果缓存 5 分钟
               （相同条件不重复计算）
```

```java
/**
 * 混合预估引擎
 */
public class HybridEstimator {

    private final BitmapCrowdEngine bitmapEngine;
    private final ClickHouseClient clickHouseClient;
    private final Cache<String, Long> estimateCache;

    public long estimate(CrowdSelectRequest request) {
        // 1. 查缓存
        String cacheKey = buildCacheKey(request);
        Long cached = estimateCache.getIfPresent(cacheKey);
        if (cached != null) return cached;

        // 2. 判断是否全部是枚举条件
        if (allEnumConditions(request.getConditions())) {
            // 走 Bitmap 快速路径
            RoaringBitmap result = bitmapEngine.select(request.getConditions());
            long count = result.getLongCardinality();
            estimateCache.put(cacheKey, count);
            return count;
        }

        // 3. 包含数值条件，走 ClickHouse
        String sql = new CrowdSelectSqlBuilder().buildCountSql(request);
        long count = clickHouseClient.queryCount(sql);
        estimateCache.put(cacheKey, count);
        return count;
    }
}
```

### 8.1 ClickHouse 查询优化

```sql
-- 优化前：全表扫描

-- 优化后：利用 ORDER BY 主键索引

CREATE MATERIALIZED VIEW mv_tag_count
ENGINE = SummingMergeTree() ORDER BY (dt, city, consume_level)
AS SELECT dt, city, consume_level, count() as cnt
FROM user_tags_wide
GROUP BY dt, city, consume_level;

-- 查预聚合结果
SELECT sum(cnt) FROM mv_tag_count
WHERE dt = today() AND city = '北京' AND consume_level = '高';
-- < 10ms
```

### 8.2 Bitmap 预热与更新

```java
/**
 * Bitmap 预热流程（每天凌晨执行）
 */
public class BitmapPreloader {

    public void preload(String dt) {
        // 1. 从 Hive 读取标签数据
        Dataset<Row> tags = spark.sql(
            "SELECT user_id, gender, city, consume_level FROM user_tags_wide WHERE dt = '" + dt + "'"
        );

        // 2. 为每个枚举标签值构建 Bitmap
        Map<String, RoaringBitmap> bitmaps = new ConcurrentHashMap<>();

        tags.foreachPartition(rows -> {
            while (rows.hasNext()) {
                Row row = rows.next();
                int userId = row.getInt(0);

                addToBitmap(bitmaps, "gender=" + row.getString(1), userId);
                addToBitmap(bitmaps, "city=" + row.getString(2), userId);
                addToBitmap(bitmaps, "consume_level=" + row.getString(3), userId);
            }
        });

        // 3. 序列化到 Redis
        for (Map.Entry<String, RoaringBitmap> entry : bitmaps.entrySet()) {
            byte[] serialized = serialize(entry.getValue());
            redis.set(("bitmap:" + entry.getKey()).getBytes(), serialized);
        }
    }

    private void addToBitmap(Map<String, RoaringBitmap> bitmaps, String key, int userId) {
        bitmaps.computeIfAbsent(key, k -> new RoaringBitmap()).add(userId);
    }
}
```

## 10. 面试高频问题与深度解答

### Q1: 亿级用户，圈选条件很复杂，怎么做到秒级返回？

**回答：**

> 我们用了一个**分层加速**的策略：
>
> **第一层：Bitmap 预计算**
> 对枚举标签（性别、城市、消费等级等），离线预构建 RoaringBitmap。圈选时直接做 Bitmap 的 AND/OR 运算，1亿用户 3 个 AND 条件大约 50-100ms。RoaringBitmap 的压缩率很高，1亿用户的一个标签值 Bitmap 大约 5-10MB。
>
> **第二层：ClickHouse 列式扫描**
> 对数值范围条件（消费金额>5000），走 ClickHouse 查询。通过合理的 ORDER BY 和分区设计，利用主键索引跳过大量数据块，通常 < 1秒。
>
> **第三层：缓存加速**
> 对相同条件的重复查询（运营反复微调），做条件指纹缓存，5分钟内直接返回。
>
> 实际效果：纯枚举条件 < 200ms，混合条件 < 1s，复杂嵌套条件 < 3s。

### Q2: Bitmap 怎么处理数值范围查询？

**回答：**

> Bitmap 原生只支持精确匹配。对于数值范围，我们有两个策略：
>
> **1. 离散化（分桶）：** 将连续值映射到有限的桶。比如消费金额分为 [0-500, 500-1000, 1000-3000, 3000-5000, 5000+] 五个桶，每个桶一个 Bitmap。"消费 > 3000" = "3000-5000 的 Bitmap OR 5000+ 的 Bitmap"。
>
> **2. 降级 ClickHouse：** 当分桶不够精确时（比如 "金额 > 3456.78"），降级到 ClickHouse 查询。
>
> 实践中大部分数值条件都可以分桶处理，因为运营选择条件时通常不会精确到小数点，而是选择"大于1000"、"大于5000"这样的整数边界。

### Q3: RoaringBitmap 和普通 Bitmap 的区别？

**回答：**

> 普通 Bitmap 的问题是**空间浪费**。如果用户 ID 范围是 0 到 100亿，但实际只有 1亿用户，普通 Bitmap 需要 100亿 bit = 1.25GB。
>
> RoaringBitmap 的核心优化是**分桶 + 自适应容器**：
> - 将 32位 ID 分为高 16 位（桶号）和低 16 位（桶内值）
> - 每个桶根据元素密度自动选择容器类型：
>   - **ArrayContainer**：元素少于 4096 个时用排序数组，省空间
>   - **BitmapContainer**：元素多时用 65536 bit 的小 bitmap
>   - **RunContainer**：连续 ID 多时用 (start, length) 对编码
>
> 效果：1 亿用户的 Bitmap，RoaringBitmap 通常只需要 5-20MB，比普通 Bitmap 节省 10-100 倍。
>
> 而且 RoaringBitmap 的 AND/OR 运算是针对同类型容器优化过的，比如两个 BitmapContainer 做 AND 可以用 SIMD 指令加速。

### Q4: 人群包怎么做增量更新？

**回答：**

> 人群包的更新策略取决于业务需求：
>
> **全量更新（大部分场景）：** 每天凌晨重新执行圈选规则，生成新的人群包覆盖旧的。简单可靠，因为标签本身是 T+1 更新的，人群包也 T+1 更新就够了。
>
> **增量更新（实时场景）：** 对于需要实时生效的人群（如风控黑名单），用 Flink 监听标签变更事件。当用户的标签值发生变化时，实时判断是否满足人群条件，如果满足则加入人群包（Redis SADD），不满足则移出（Redis SREM）。
>
> 增量更新的挑战是**最终一致性**——如果标签更新和人群判断之间有延迟，可能出现短暂的不一致。我们的做法是，每天凌晨用全量更新做一次"修正"，保证最终结果是准确的。

### Q5: 如何设计可扩展的规则引擎？

**回答：**

> 我们的规则引擎采用了**条件树 + 策略模式**的设计。
>
> **条件树**：规则被解析为一棵树，内部节点是 AND/OR 逻辑操作，叶子节点是具体的标签条件。这个结构天然支持任意嵌套组合。
>
> **策略模式**：每种操作符（EQ、GT、IN、BETWEEN、CONTAINS 等）都是一个策略类。新增操作符只需要实现 `Comparator` 接口，不修改核心引擎代码。
>
> **扩展点**：
> - 新增标签类型：实现新的 Condition 子类
> - 新增操作符：注册新的 Comparator
> - 自定义函数：支持 DATEDIFF、GEO_DISTANCE 等函数
> - 外部数据源：支持 IN (子查询) 引用外部数据
>
> 规则同时支持两种执行模式：**转 SQL**（批量圈选用 ClickHouse）和**内存求值**（实时判断用标签 Map）。
