## 1. Spring Boot 过滤器与拦截器

### 过滤器（Filter）
- **Servlet 规范**的一部分，工作在 DispatcherServlet **之前**
- 典型用途：编码设置、CORS、JWT Token 校验、请求日志

### 拦截器（Interceptor）
- **Spring MVC** 机制，工作在 DispatcherServlet **之后**、Controller **之前**
- 典型用途：登录校验、权限控制、接口耗时统计
- 能拿到 `HandlerMethod`，知道具体调用哪个 Controller 方法

### 核心区别

| 维度 | Filter | Interceptor |
|------|--------|-------------|
| 规范 | Servlet | Spring MVC |
| 执行位置 | DispatcherServlet 之前 | DispatcherServlet 之后 |
| Spring Bean | 需额外处理 | 天然支持 `@Autowired` |
| 作用范围 | 所有请求（含静态资源） | 仅 Spring MVC 处理的请求 |

### 执行顺序

```
请求 → Filter → DispatcherServlet → Interceptor.preHandle → Controller
                                                              ↓
响应 ← Filter ← DispatcherServlet ← Interceptor.afterCompletion ← Interceptor.postHandle
```

## 2. 接口鉴权用拦截器还是过滤器

**取决于鉴权的层次：**

| 场景 | 推荐方案 |
|------|---------|
| JWT/Token 校验（认证） | **Filter**（Spring Security） |
| 接口级角色/权限校验 | **Interceptor** 或 `@PreAuthorize` |
| 方法级细粒度控制 | **AOP + 自定义注解** |
| 轻量项目，不用 Spring Security | **Interceptor** 最简单 |

### 典型分层

```
Filter 层 → 认证（Authentication）：你是谁？Token 有效吗？
Interceptor 层 → 鉴权（Authorization）：你能访问这个接口吗？
AOP / 方法内 → 数据权限：你能看哪些数据？
```

## 3. 认证是指是否登录吗

**"是否登录"是认证最常见的场景，但认证的本质是"确认你是谁"。**

```
认证（Authentication）：你是谁？  → 门卫检查身份证
鉴权（Authorization）：  你能干嘛？→ 门卫检查你是否有权进某个房间
```

### HTTP 状态码

```
401 Unauthorized  → 实际含义是"未认证"（命名有误导性）
403 Forbidden     → "未授权"，已登录但没权限
```

> **知识点：** HTTP 401 的名字 `Unauthorized` 是历史命名错误，真正含义是 `Unauthenticated`。

## 4. ClientID + Token 接口鉴权方案

### 核心原则：Token 用来签名，永远不在网络上传输

```
业务方用 Token 作为密钥 → 对请求参数做 HMAC-SHA256 签名 → 发送 clientId + sign
服务端用 clientId 查出 Token → 同样算法算 sign → 比对
```

### 请求格式

```http
Headers:
  X-Client-Id: client_001
  X-Timestamp: 1710321600
  X-Nonce: a3f5b8c2
  X-Sign: e5d3a1b9f7c2...（HMAC-SHA256 计算结果）
```

### 防重放攻击
- timestamp 与当前时间差不超过 5 分钟
- nonce 未被使用过（Redis 缓存已使用的 nonce）

### 签名算法
```
待签名字符串 = clientId + timestamp + nonce + 业务参数（按 key 排序）
sign = HMAC-SHA256(待签名字符串, token)
```

> **知识点：** 这和微信支付、支付宝开放平台的签名机制一样。选 HMAC-SHA256 而非 MD5/SHA256，是因为 HMAC 能防止长度扩展攻击。

## 5. 服务端验签要查数据库吗

**是的，但不应该每次都查数据库，要做缓存。**

### 验签逻辑

```java
String clientId = request.getHeader("X-Client-Id");
String token = clientTokenService.getTokenByClientId(clientId); // 查 token
String expectedSign = HmacUtils.hmacSha256Hex(token, data);     // 算 sign
return MessageDigest.isEqual(expectedSign.getBytes(), sign.getBytes()); // 比对
```

### 缓存策略

| 方案 | 适用场景 |
|------|---------|
| 本地 Map/Caffeine 缓存 | 业务方少（几十个），变更不频繁 |
| Redis 缓存 | 多实例部署需要一致性 |
| 数据库直查 | 只在缓存未命中时回源 |

> **知识点：** 比对签名用 `MessageDigest.isEqual()` 而非 `String.equals()`，防止时序攻击（Timing Attack）。

## 6. 分库分表需要分到不同 MySQL 端口吗

**取决于瓶颈在哪：**

```
单表数据量大，查询慢 → 同实例内分表就行（大多数场景）
单机磁盘/IO/CPU/连接数不够 → 必须分到不同实例
只是读压力大 → 读写分离（主从），比分库简单
```

### 规模参考

| 数据规模 | 建议方案 |
|---------|---------|
| 单表 < 2000 万行 | 不分，加好索引 |
| 2000 万 ~ 几亿行，单机性能够 | 同实例分表 |
| TB 级，或 QPS 上万 | 不同实例分库分表 |

> **核心原则：能不分就不分，能少分就少分，能同实例就不跨实例。** 跨实例分库会带来分布式事务、跨库 JOIN、全局 ID 等一系列复杂度。

## 7. Flink MaxParallelism 的作用

**MaxParallelism = KeyGroup 的数量，是状态分配的基础单位。**

### 全链路

```
Key("user_123")
  → hashCode() → murmurHash() → % maxParallelism(128)
  → KeyGroup = 42
  → 42 * parallelism(4) / maxParallelism(128) = 1
  → 路由到 SubTask-1
```

### 源码关键（KeyGroupRangeAssignment.java）

```java
// Key → KeyGroup
MathUtils.murmurHash(keyHash) % maxParallelism

// KeyGroup → SubTask
keyGroupId * parallelism / maxParallelism

// 默认值 = roundUpToPowerOfTwo(parallelism * 1.5)，最小 128，最大 32768
```

### 关键约束
- `1 ≤ parallelism ≤ maxParallelism ≤ 32768`
- 一旦从 Savepoint 恢复，**MaxParallelism 不能改变**
- Rescale 时只有 KeyGroup 的分配变了，编号不变

> **知识点：** 默认取 2 的幂是因为取模可优化为位运算（`hash & (n-1)`），和 HashMap 容量必须是 2 的幂同理。

## 8. SourceFunction Checkpoint 锁机制

### 要解决的问题

```
如果不加锁，Checkpoint 可能插在 collect(B) 和 offset=102 之间：
  → 快照里 offset=101，但数据 B 已经发出去了
  → 恢复后从 101 重读，B 被发两次
```

### 加锁后

```java
synchronized (ctx.getCheckpointLock()) {
    ctx.collect(element);  // 发数据
    offset++;              // 更新偏移量
    // 这两步是原子的，Checkpoint 无法插入中间
}
```

### 框架 vs 用户的分工

- 框架的 `collect()` 内部已经有 `synchronized(checkpointLock)`，保证单步原子
- 但用户自己的 `offset++` 不在 collect 里，所以需要手动加锁把两步包在一起

> **知识点：** 这是旧版 SourceFunction 被废弃的重要原因——把线程安全的责任交给用户太容易出错。

## 9. Checkpoint 锁的完整源码链路

### 同一把锁被传到两个地方

```
SourceStreamTask 创建 new Object() 作为 lock
    │
    ├──► StreamTaskActionExecutor.synchronizedExecutor(lock)
    │      → Checkpoint / Mailbox 操作执行时 synchronized(lock)
    │
    └──► SourceContext
           → 用户代码 ctx.getCheckpointLock() 拿到同一把锁
```

### 关键源码文件

| 文件 | 作用 |
|------|------|
| `SourceStreamTask.java` | 创建锁，传递给两方 |
| `StreamTaskActionExecutor.java` | Checkpoint 侧加锁执行 |
| `StreamSourceContexts.java` | Source 侧 collect 加锁 |

### SourceStreamTask 官方注释（第 51-56 行）

> "checkpointing and the emission of elements must never occur at the same time. The execution must be serial."

## 10. Mailbox 模型介绍

### 核心思想

从"多线程 + 锁"变为"单线程 + 消息队列"：

```
所有操作（数据处理、Checkpoint、定时器、异步回调）
都以 Mail 的形式投递到队列，由单一的 Mailbox 线程串行执行
```

### 主循环（MailboxProcessor.runMailboxLoop）

```java
while (isNextLoopPossible()) {
    processMail(localMailbox, false);                    // 处理 Checkpoint、Timer 等
    mailboxDefaultAction.runDefaultAction(controller);   // 处理数据
}
```

### 双队列优化

```
queue（加锁写入）：外部线程投递 Mail
batch（无锁读取）：Mailbox 线程消费
一次加锁把 queue 全部转移到 batch，后续无锁读取
```

### Checkpoint 在新模型中的执行

```java
// StreamTask.triggerCheckpointAsync()
mainMailboxExecutor.execute(() -> {
    triggerCheckpointAsyncInMailbox(checkpointMetaData, checkpointOptions);
}, "checkpoint ...");
// Checkpoint 作为 Mail 排队，不再需要抢锁
```

> **详细文档见：** `源码分析/18-Mailbox模型源码深度解析.md`

## 11. RocksDBStateBackend vs EmbeddedRocksDBStateBackend

**运行时完全一样，没有性能或功能差异。**

- `RocksDBStateBackend`：旧 API，已 `@Deprecated`，内部委托给 `EmbeddedRocksDBStateBackend`
- `EmbeddedRocksDBStateBackend`：当前推荐的实现类

### 本质区别：Flink 1.13 架构拆分

```
旧 API：RocksDBStateBackend 同时负责本地状态存储 + Checkpoint 持久化（耦合）
新 API：EmbeddedRocksDBStateBackend（本地状态）+ CheckpointStorage（持久化）独立配置
```

### 迁移方式

```java
// 旧写法
env.setStateBackend(new RocksDBStateBackend("hdfs://checkpoints"));

// 新写法
env.setStateBackend(new EmbeddedRocksDBStateBackend());
env.getCheckpointConfig().setCheckpointStorage("hdfs://checkpoints");
```

## 12. CheckpointStorage 与 RocksDB 是谁实现的

### CheckpointStorage 两种

| 类型 | 快照存哪里 | 场景 |
|------|-----------|------|
| `JobManagerCheckpointStorage` | JobManager 堆内存 | 仅测试 |
| `FileSystemCheckpointStorage` | HDFS / S3 | 生产环境 |

### RocksDB 不是 Flink 自己实现的

```
RocksDB = Facebook 开源的 C++ 嵌入式 KV 数据库
Flink 通过 JNI 调用它
Flink 自己实现的是外层封装：序列化、KeyGroup 管理、Checkpoint 快照逻辑
```

### 架构分层

```
Flink Java 代码（序列化、KeyGroup、Checkpoint 逻辑）
    │ JNI 调用
    ▼
RocksDB（C++ 原生库，Facebook 开源）
    │
    ▼
TaskManager 本地磁盘
```

## 13. JNI 是什么

**JNI（Java Native Interface）= Java 调用 C/C++ 代码的桥梁。**

```java
// Java 侧：声明 native 方法
public class RocksDB {
    static { System.loadLibrary("rocksdbjni"); }  // 加载 C++ 动态库
    public native void put(byte[] key, byte[] value);  // 实现在 C++ 那边
}
```

### 常见的 JNI 使用
- `System.arraycopy()` → C 实现
- `FileInputStream.read()` → 操作系统 read()
- Flink 的 RocksDB → Facebook 的 C++ RocksDB
- Hadoop HDFS 客户端 → C 的 libhdfs

> **知识点：** RocksDB 的内存分配在 native 堆，JVM 的 `-Xmx` 管不到它。需要配置 `state.backend.rocksdb.memory.managed: true` 来控制。

## 14. 什么是有状态算子

### 判断标准

```
如果算子挂了重启，是否需要知道"之前处理到哪了"或"之前算出了什么中间结果"？
  需要 → 有状态
  不需要 → 无状态
```

### 常见分类

| 算子 | 有无状态 | 原因 |
|------|---------|------|
| `map(x -> x * 2)` | 无状态 | 每条记录独立处理 |
| `filter(x -> x > 10)` | 无状态 | 只看当前记录 |
| `keyBy().sum()` | **有状态** | 记住每个 key 的累加值 |
| `keyBy().window(5s)` | **有状态** | 缓存窗口内所有数据 |
| Kafka Source | **有状态** | 记住 offset |
| CDC Source | **有状态** | 记住 binlog position |
| `print()` Sink | 无状态 | 直接打印 |
| Kafka Sink（EOS） | **有状态** | 记住预提交事务 ID |

> **知识点：** 无状态算子也参与 Checkpoint Barrier 对齐，但不写入状态数据。Kafka Source 的 offset 存在 Flink 的 Checkpoint 中，不依赖 Kafka 的 `__consumer_offsets`。

## 15. Credit-Based 流控中 buffer 就是 credit 吗

**是的。** 源码直接证明：

```java
// RemoteInputChannel.java:143
this.initialCredit = networkBuffersPerChannel;  // buffers-per-channel 直接赋给 initialCredit
```

### 两种 buffer

```
Exclusive Buffer（独占）= buffers-per-channel = initialCredit
  每个 channel 专属，不会被抢走

Floating Buffer（浮动）
  从共享 buffer pool 动态借用，应对突发流量
```

### 流控流程

```
下游有 4 个 credit → 通知上游
上游发 4 个 buffer → 下游消费 1 个 → 归还 1 credit → 上游再发 1 个
（流水线式持续流动，不是用完再申请）
```

## 16. buffers-per-channel 设 4 个够用吗

**大部分场景够用**，因为 credit 是持续流动的。

### 什么时候不够

```
需要的 buffer 数 ≈ 上游吞吐(buffer/s) × 网络 RTT(s)

同机房 RTT ≈ 0.1ms → 需要 ~1 个 → 4 个绰绰有余
跨机房 RTT ≈ 5ms，高吞吐 → 可能需要 50 个 → 4 个不够
```

### 调优建议

| 场景 | buffers-per-channel |
|------|-------------------|
| 同机房、正常负载 | 2（默认） |
| 高吞吐、低延迟 | 4-8 |
| 跨机房、网络延迟高 | 8-16 |

### 默认值低的原因：内存

```
200 个 channel × 2 buffer × 32KB = 12.8MB（可接受）
200 个 channel × 50 buffer × 32KB = 320MB（内存爆了）
```

> **知识点：** 这和 TCP 的 BDP（带宽延迟积）是同一个道理——buffer 数覆盖"一个 RTT 内能传输的数据量"就够了。

## 17. Flink 向 Kafka 写入如何开启事务

### 配置方式（新版 KafkaSink）

```java
KafkaSink.<String>builder()
    .setDeliveryGuarantee(DeliveryGuarantee.EXACTLY_ONCE)
    .setTransactionalIdPrefix("my-flink-job")
    .build();
```

### 必须同时满足

```
Flink 侧：Checkpoint 开启 + EXACTLY_ONCE + transactionalIdPrefix
Kafka 侧：transaction.max.timeout.ms ≥ Checkpoint 间隔的 2-3 倍
消费侧：isolation.level = read_committed
```

### 两阶段提交流程

```
① 开启 Kafka 事务
② 写数据（预写入，消费者看不到）
③ Checkpoint Barrier → preCommit：flush 数据，保存事务 ID
④ Checkpoint 完成 → commitTransaction()（消费者才能看到）
⑤ 开启下一个事务
```

> **知识点：** Exactly-Once 的端到端延迟 = Checkpoint 间隔。`transactionalIdPrefix` 用于 zombie fencing——恢复后新 Producer 用同样的 transactional.id，Kafka 自动 abort 旧 Producer 的未完成事务。

## 18. Flink 源码中有 "High alignment duration" 日志吗

**没有。** "High alignment duration" 不是 Flink 源码打印的日志。

### Alignment Duration 的暴露方式

```
1. WebUI → Checkpoint 详情页 → 每个 SubTask 的 Alignment Duration 列
2. REST API → /jobs/:jobid/checkpoints/detail/:checkpointid
3. Metrics → checkpointAlignmentTime（可接入 Prometheus/Grafana）
4. DEBUG 日志 → CheckpointStatsTracker 输出完整 JSON（需开 DEBUG 级别）
```

### 如果要告警

```
Flink Metrics → PrometheusReporter → Prometheus → Grafana 告警规则
例如：checkpointAlignmentTime > 30s → 触发告警
```

> **知识点：** Alignment Duration 高说明某些 InputChannel 的 Barrier 到达时间差距大，通常是数据倾斜或反压导致。这也是 Unaligned Checkpoint 被设计出来的原因。

## 19. Checkpoint Lock 在保护什么

**保证"发数据"和"更新偏移量"是原子的，Checkpoint 不会插在中间。**

```java
synchronized (ctx.getCheckpointLock()) {
    ctx.collect(element);  // 第 1 步：发数据（副作用，收不回来）
    offset++;              // 第 2 步：更新状态
}
```

**本质是分布式系统中经典的"状态与副作用不一致"问题：** 如果两步不原子，恢复后无法判断"这条数据到底发没发"。所有 Exactly-Once 系统（Kafka 事务、两阶段提交）都在解决同一个问题。
