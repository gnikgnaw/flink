# 状态机（Finite State Machine）原理与实现

> **适用场景**：理解 Flink Task 生命周期、Checkpoint 协调、作业状态管理等核心机制
> **基于版本**：Flink 1.18

---

## 一、什么是状态机

**状态机（Finite State Machine, FSM）** 是一种数学计算模型，描述一个系统在任意时刻只能处于有限个状态中的一个，并且只能在特定条件（事件/输入）下从一个状态转移到另一个状态。

核心三要素：
- **状态（State）**：系统在某一时刻的"快照"，比如订单的"待支付"、"已支付"、"已发货"
- **事件（Event）**：触发状态转移的外部输入，比如"用户点击支付"、"商家发货"
- **转移（Transition）**：状态 + 事件 → 新状态的映射规则

```
当前状态 + 事件 → 新状态 + (可选的副作用/动作)
```

## 二、为什么需要状态机

### 没有状态机时的代码

```java
// 典型的 if-else 地狱
public void handleEvent(String event) {
    if (status.equals("CREATED") && event.equals("submit")) {
        status = "PENDING";
    } else if (status.equals("PENDING") && event.equals("pay")) {
        status = "PAID";
    } else if (status.equals("PENDING") && event.equals("cancel")) {
        status = "CANCELLED";
    } else if (status.equals("PAID") && event.equals("ship")) {
        status = "SHIPPED";
    }
    // ... 随着状态和事件增多，复杂度爆炸
}
```

**问题**：
1. 状态流转逻辑散落在 if-else 中，无法一眼看清全貌
2. 容易遗漏非法转移的检查（比如"已取消"的订单还能"发货"吗？）
3. 新增状态或事件需要改动大量分支

### 有状态机时的代码

```java
// 声明式定义：清晰、完整、不遗漏
transitions.put(key(CREATED,  SUBMIT),  PENDING);
transitions.put(key(PENDING,  PAY),     PAID);
transitions.put(key(PENDING,  CANCEL),  CANCELLED);
transitions.put(key(PAID,     SHIP),    SHIPPED);
transitions.put(key(SHIPPED,  DELIVER), FINISHED);
// 不在表中的组合 → 自动拒绝，不可能出现非法流转
```

## 三、Flink 中的状态机实例

Flink Task 的执行状态（`ExecutionState`）就是一个典型的状态机：

```
                     RECONCILING
                          │
                          ▼
CREATED ──→ SCHEDULED ──→ DEPLOYING ──→ INITIALIZING ──→ RUNNING ──→ FINISHED
                |              |              |              |
                |              |              |              ▼
                |              |              |          CANCELING ──→ CANCELED
                |              |              |              ▲
                ▼              ▼              ▼              |
              FAILED         FAILED        FAILED ─────────-+
```

源码位置：`flink-runtime/.../execution/ExecutionState.java`

```java
public enum ExecutionState {
    CREATED,
    SCHEDULED,
    DEPLOYING,
    RUNNING,
    FINISHED,      // 终态：成功完成
    CANCELING,
    CANCELED,      // 终态：已取消
    FAILED,        // 终态：失败
    RECONCILING,
    INITIALIZING;

    // 判断是否为终态——到达终态后不可再转移
    public boolean isTerminal() {
        return this == FINISHED || this == CANCELED || this == FAILED;
    }
}
```

## 四、状态机的两种经典实现方式

### 方式一：转移表（Transition Table）

用一个 Map 存储所有合法的 `(当前状态, 事件) → 目标状态` 映射。

**优点**：所有转移规则集中在一处，一目了然
**适用**：状态和事件较多、转移规则复杂时

### 方式二：状态模式（State Pattern）

每个状态是一个独立的类，各自实现对事件的响应。

**优点**：每个状态的行为内聚，符合开闭原则
**适用**：不同状态下的行为差异很大时

### 5.3 组装订单状态机

```java
public class OrderStateMachineDemo {

    public static StateMachine<OrderState, OrderEvent> create() {
        StateMachine<OrderState, OrderEvent> sm = new StateMachine<>(OrderState.CREATED);

        // 正常流程
        sm.addTransition(OrderState.CREATED,  OrderEvent.SUBMIT,  OrderState.PENDING,   ctx ->
            System.out.println("订单已提交，等待支付"));

        sm.addTransition(OrderState.PENDING,  OrderEvent.PAY,     OrderState.PAID,      ctx ->
            System.out.println("支付成功！"));

        sm.addTransition(OrderState.PAID,     OrderEvent.SHIP,    OrderState.SHIPPED,   ctx ->
            System.out.println("商家已发货"));

        sm.addTransition(OrderState.SHIPPED,  OrderEvent.DELIVER, OrderState.FINISHED,  ctx ->
            System.out.println("确认收货，订单完成"));

        // 取消流程
        sm.addTransition(OrderState.PENDING,  OrderEvent.CANCEL,  OrderState.CANCELLED, ctx ->
            System.out.println("订单已取消"));

        sm.addTransition(OrderState.PAID,     OrderEvent.CANCEL,  OrderState.CANCELLED, ctx ->
            System.out.println("已支付订单取消，发起退款"));

        return sm;
    }

    public static void main(String[] args) {
        StateMachine<OrderState, OrderEvent> sm = create();

        System.out.println("当前状态: " + sm.getCurrentState());  // CREATED

        sm.fireEvent(OrderEvent.SUBMIT);   // CREATED → PENDING
        sm.fireEvent(OrderEvent.PAY);      // PENDING → PAID
        sm.fireEvent(OrderEvent.SHIP);     // PAID → SHIPPED
        sm.fireEvent(OrderEvent.DELIVER);  // SHIPPED → FINISHED

        System.out.println("最终状态: " + sm.getCurrentState());  // FINISHED

        // 试试非法转移
        try {
            sm.fireEvent(OrderEvent.PAY);  // FINISHED 状态不能再支付
        } catch (IllegalStateException e) {
            System.out.println("拦截非法操作: " + e.getMessage());
        }
    }
}
```

**预期输出**：
```
当前状态: CREATED
订单已提交，等待支付
支付成功！
商家已发货
确认收货，订单完成
最终状态: FINISHED
拦截非法操作: No transition defined for state=FINISHED, event=PAY
```

## 六、与 Flink 源码的对照

| 概念 | 订单状态机示例 | Flink 中的对应 |
|------|-------------|---------------|
| 状态枚举 | `OrderState` | `ExecutionState`（Task 执行状态） |
| 事件 | `OrderEvent` | 方法调用如 `deploy()`、`cancel()` |
| 转移表 | `Map<String, S>` | `Execution` 类中的 `transitionState()` 方法 |
| 终态判断 | `isTerminal()` | `ExecutionState.isTerminal()` |
| 非法转移 | 抛 `IllegalStateException` | 抛 `IllegalStateException` + 日志 |

Flink 的 `Execution.transitionState()` 本质上就是一个状态机引擎——检查当前状态是否允许转移到目标状态，不允许则记录日志并拒绝。

---

## 七、小结

- 状态机的核心价值是把**隐式的状态流转逻辑**变成**显式的声明式规则**
- 转移表方式适合规则多但行为简单的场景；状态模式适合不同状态行为差异大的场景
- Flink 源码中 Task 生命周期、Job 状态管理、Checkpoint 协调都基于状态机模式
- 面试中能从"订单状态机"类比到 Flink 的 `ExecutionState`，展示对框架内部机制的理解
